# 새 리눅스 커널에서 MongoDB가 뜨지 않아 백엔드 CI가 실패하는 문제

## 개발 목표와 의도

2026-10-27부터 백엔드 CI가 코드와 상관없이 실패한다. PR #130은 두 번, PR #124를 머지할 때의 main도 한 번 실패했다. 셋 다 테스트를 시작하기도 전, MongoDB 컨테이너를 띄우는 단계에서 「container … is unhealthy」로 멈췄다.

원인을 실제 러너에서 확인했다. GitHub이 일부 러너를 리눅스 커널 7.0.0으로 바꿨다. 우리가 쓰는 MongoDB 8.0.29는 커널 6.19~7.0.13에서 시작하자마자 스스로 멈춘다. 같은 실행에서 6.17 커널 러너에 걸린 작업은 통과한다. 그래서 CI가 어느 러너를 받느냐에 따라 통과하거나 실패한다.

사용자의 말 — "이 작업을 여기에서 진행해 주세요: 백엔드 CI의 MongoDB 준비 단계 실패 고치기".

## 기능 목록

| 기능 | 설명 | 왜 필요한가 |
|---|---|---|
| 새 커널에서도 MongoDB 시작 | CI와 로컬 개발용 MongoDB 컨테이너가 커널 7.0 러너에서도 뜨고, 데이터를 쓰고 읽는다. | 지금은 PR마다 CI가 운에 따라 실패한다. 실패가 코드 탓인지 러너 탓인지 매번 로그를 열어 봐야 하고, 이번처럼 빨간 CI를 두고 머지하게 된다. |
| 실패할 때 MongoDB 로그 남기기 | MongoDB 준비 단계가 실패하면 CI 로그에 MongoDB 자신의 오류 줄이 찍힌다. | 이번에는 「unhealthy」 한 줄뿐이라 원인을 찾으려고 진단용 브랜치를 따로 만들어 네 번 돌려야 했다. |

## 개발 목표

- 커널 7.0 러너에서 백엔드 CI의 `verify`가 통과한다: 이 PR의 CI 실행에서 러너 커널과 결과를 같이 확인한다.
- 커널 6.x 러너에서도 그대로 통과한다: 같은 실행의 다른 작업으로 확인한다.
- `pnpm infra:up`으로 띄우는 로컬 MongoDB가 지금처럼 뜨고 `pnpm test:infra`가 통과한다.
- MongoDB 준비 단계를 일부러 실패시키면 CI 로그에 MongoDB의 오류 줄이 보인다.

## 범위 밖과 제약

- 운영 서버의 MongoDB 설정(`infra/compose.server.yaml`)은 이번에 바꾸지 않는다. 바꾸면 다음 배포 때 운영 DB 컨테이너가 다시 만들어진다. 아래 열린 질문을 본다.
- MongoDB 버전을 올리지 않는다. 지금 나와 있는 8.0 릴리스 중 이 커널 문제를 고친 것은 확인되지 않는다.
- 러너를 `ubuntu-22.04`로 고정하지 않는다. 22.04 러너는 커널 6.8이라 지금은 통과하지만, 문제를 피하는 것일 뿐이고 22.04 러너는 언젠가 내려간다.

## 열린 질문

- 운영 서버에도 같은 설정을 넣을까.
  - 이번에는 넣지 않기로 하고 명세를 썼다. 운영 서버는 오늘 배포에서 MongoDB가 정상으로 떴으므로 지금 영향받는 커널이 아니다. 넣으면 다음 배포 때 운영 MongoDB가 몇 초 다시 시작된다.
  - 운영 서버의 커널이 6.19~7.0.13으로 올라가면 운영 MongoDB도 같은 이유로 뜨지 않는다. 그 전에 따로 넣는 것이 안전하다.
