# 자유 생성 파이프라인 실험 — 정제된 컨텍스트와 디자인 스킬

## 개발 목표와 의도

구조화 생성으로 만든 포트폴리오는 사람과 공고가 달라도 화면이 거의 같습니다. 로컬 DB의 구조화 지면 30건 중 19건이 「경력 → 근거」로 끝나고 17건이 첫 화면 바로 뒤에 수치 줄을 둡니다. 요청은 이렇습니다: "구조화 생성은 그대로 두고, 자유 생성 + 정제된 컨텍스트 주입 + 웹사이트 디자인 스킬 사용 이 셋을 적용했을 때 결과물이 더 나은지 실험하자."

자유 생성은 모델이 HTML과 CSS를 직접 쓰는 방식입니다. 지금의 자유 생성은 기록 원문과 설계안 JSON을 그대로 프롬프트에 붙이고, 디자인 방법은 열 줄의 공통 원칙으로만 알려 줍니다. 2026-10-16 비교에서 자유 생성은 수치 강조와 흐름도를 그렸지만 지원자 이름과 경력 · 근거 섹션을 빠뜨렸습니다.

이 작업은 자유 생성에 두 가지를 더한 생성기를 만들고, 더하기 전과 후를 같은 입력으로 나란히 만들어 비교합니다.

## 기능 목록

| 기능 | 설명 | 왜 필요한가 |
|---|---|---|
| 정제된 컨텍스트 | 지면을 쓰기 전에 모델 호출 한 번이 기록 원문에서 직무 · 한 줄 소개 · 섹션별 주장과 본문 · 수치(이전 값 포함) · 단계 · 인용 · 경력 · 근거 목록을 뽑습니다. 지면을 쓰는 호출은 원문 대신 이 정리본을 받습니다. 수치와 기간은 출처에 적힌 글자와 대조합니다. | 원문을 그대로 붙이면 모델이 디자인과 내용 정리를 한 번에 해야 해서 이름 · 경력 · 근거를 빠뜨렸습니다. 어떤 수치와 단계가 있는지 미리 알아야 그 자료에 맞는 표현(막대 · 흐름 · 타임라인)을 고를 수 있습니다. |
| 디자인 스킬 주입 | `frontend-design` 스킬 본문을 지면을 쓰는 호출의 시스템 프롬프트에 넣습니다. 모델은 HTML을 쓰기 전에 색 · 서체 · 배치 계획을 먼저 적습니다. 색과 서체는 사용자가 고른 디자인이 정하고, 스킬은 첫 화면 · 배치 · 글자 다루기를 맡습니다. | 지금 프롬프트는 디자인 방법을 거의 알려 주지 않아 모델이 익숙한 기본 배치로 갑니다. 이 스킬은 주제에서 출발해 배치를 정하고 흔한 기본값을 피하는 절차를 담고 있습니다. |
| 다섯 조건 비교 실행 | 같은 사람 · 같은 디자인으로 지금의 자유 생성(키트 부품으로 조판) · 키트 없이 자유 · 정제만 · 스킬만 · 둘 다, 다섯 가지 지면을 만듭니다. 서로 다른 가상 인물 세 명에 대해 반복하고, 한 칸은 두 번 더 만들어 실행마다의 차이를 봅니다. 구조화 생성 지면도 같은 입력으로 하나씩 만들어 옆에 둡니다. | 두 가지를 한꺼번에 넣으면 어느 쪽이 효과를 냈는지 알 수 없습니다. 지금까지의 비교는 모두 한 번씩만 만들어, 조건의 차이인지 실행마다의 흔들림인지 가릴 수 없었습니다. |
| 비교 화면과 측정 기록 | 모든 지면의 1440px · 390px 스크린샷을 한 화면에 조건별 · 인물별로 늘어놓은 비교 화면을 만듭니다. 지면마다 가로 넘침 · 깨진 이미지 · 이름과 경력 · 근거 유무 · 출처에 없는 수치 · 비용 · 시간을 잰 표를 붙입니다. | "더 다양하고 보기 좋은가"는 눈으로 판단해야 합니다. 판단할 사람이 한 화면에서 나란히 볼 수 있어야 하고, 깨진 지면은 측정으로 먼저 걸러야 합니다. |
| 눈가림 평가 | 조건 이름을 가린 스크린샷을 순서를 섞어 별도 에이전트에게 주고, 인물별로 어느 지면이 나은지와 조건별로 세 인물의 지면이 서로 얼마나 다른지 적게 합니다. | 생성기를 만든 쪽이 직접 고르면 새 조건에 유리하게 봅니다. 최종 판단은 요청자가 비교 화면에서 합니다. |

## 개발 목표

- 다섯 조건의 지면이 열린다: 비교 화면에서 인물 세 명 × 다섯 조건의 지면을 각각 눌러 전체 화면으로 볼 수 있다.
- 조건의 효과가 갈린다: 결과 문서의 표에서 정제만 · 스킬만 · 둘 다가 지금의 자유 생성과 무엇이 다른지(이름 · 경력 · 근거 유무, 넘침, 비용, 눈가림 순위)를 한 줄씩 읽을 수 있다.
- 다양성을 눈으로 확인한다: 같은 디자인을 고른 세 인물의 지면을 한 줄에 놓고, 첫 화면과 배치가 서로 다른지 본다.
- 구조화 생성은 그대로다: `pnpm typecheck`와 `pnpm test`가 통과하고, 제품의 생성 방식 선택(구조화 생성 · 자유 생성)은 이 작업 전과 같게 동작한다.
- 다음 결정을 내릴 수 있다: 결과 문서 끝에 "제품의 자유 생성을 새 생성기로 바꿀지"를 판단할 근거가 정리되어 있다.

## 범위 밖과 제약

- 제품의 자유 생성 경로는 바꾸지 않습니다. 새 생성기는 실험 스크립트에서만 돌고, 제품 연결은 결과를 본 뒤 정합니다.
- 구조화 생성의 코드와 동작은 건드리지 않습니다.
- 그린 화면을 재서 고치는 단계는 넣지 않습니다. 넣으면 무엇이 효과를 냈는지 가릴 수 없습니다.
- 모델 등급은 제품의 자유 생성과 같은 Sonnet으로 고정합니다.
- 입력은 가상 인물만 씁니다. 실제 사용자 기록은 쓰지 않습니다.
- 실제 모델 호출은 지면 22건과 정리 3건, 레시피 2건입니다(CLI 추정 비용 약 $30).

## 열린 질문

- "정제된 컨텍스트"를 위 설명(원문에서 사실을 뽑아 정리한 글)으로 읽었습니다. 공고 요건이나 회사 정보를 더 넣는 뜻이었다면 정리본의 항목이 달라집니다.
- "웹사이트 디자인 스킬"은 이 장비에 설치된 `frontend-design`으로 정했습니다. 다른 스킬을 뜻했다면 스킬 본문만 바꿔 다시 돌립니다.
