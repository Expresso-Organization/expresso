# 첫 화면 3D를 3d-motion-web 엔진으로

## 개발 목표와 의도

지금은 모델이 three.js 장면을 처음부터 짜서, 품질이 지침을 얼마나 따르느냐에 달려 있다. 같은 날 기본 상자를 단색으로 늘어놓은
장면이 나왔고 사용자가 "이런 저퀄리티 박스는 쓰지 않게 해야겠다"고 짚었다. 사용자가 만든 3d-motion-web 스킬의 엔진은 레이마칭
SDF · 안티에일리어싱 · 톤매핑 · 실패 처리를 이미 갖췄고, 저자는 형태(`map`)와 재질(`shadeSurface`)만 쓴다. 이 엔진을 지면이
싣게 해, 크롬 · 유리 · 세라믹 같은 표면이 매번 같은 품질로 나오게 한다. 사용자: "Build in the engine".

## 기능 목록

| 기능 | 설명 | 왜 필요한가 |
|---|---|---|
| 엔진 싣기 | 지면 스크립트가 `MotionWeb.create`를 부르면 문서가 엔진(wgsl-std · hg-sdf 포함)을 함께 싣는다 | 렌더링 배관을 모델이 다시 짜면 같은 자리에서 깨진다 |
| 엔진 쓰는 법 | 지침이 WGSL 계약 · 재질 · 빛 레시피 · 함정을 알린다. 팔레트는 고른 스타일의 색을 uniform으로 넘긴다 | 계약과 레시피를 모르면 셰이더가 컴파일되지 않거나 플라스틱처럼 보인다 |
| 조용한 실패 | WebGPU가 없거나 셰이더가 실패하면 엔진의 붉은 오류 대신 CSS 첫 모습이 남는다 | 방문자에게 오류 상자를 보일 수 없다 |

## 개발 목표

- 같은 네 짝을 다시 그리면 엔진으로 지은 첫 화면이 나오고 움직인다: 보드의 새 칸에서 확인
- 그린 셰이더가 vgpu 검사를 통과하는 비율을 보고에 적는다
- 엔진을 쓰지 않는 지면의 문서는 지금과 같다

## 범위 밖과 제약

- HDRI 환경맵(바깥 파일 fetch)은 쓰지 않는다 — 정책이 바깥 요청을 막는다. 빛은 셰이더 안의 `env()`로 짓는다.
- 서버의 WGSL 검증은 이번에 하지 않는다(vgpu는 90MB가 넘는다). 검증은 이번 점검에서 로컬로만 한다.
- 엔진은 고치지 않는다(스킬의 규칙). 생성 스크립트로 들여온다.

## 열린 질문

- 팔레트를 무엇이 정하나 → 디자인 대화에서 고른 스타일의 바탕 · 글자 · 강조 색. 엔진에는 uniform으로 넘긴다.

## 철회 (2026-11-21)

엔진은 SDF 오브젝트 한 덩어리를 그리는 데만 쓰였다. 라이브러리 견본을 본 사용자가 "의미없는 3D 오브젝트는 그냥 안쓰는게 더 낫겠다"고 정해,
엔진 묶음 · 문서 싣기 · 지침을 걷어냈다. 3D는 효과 라이브러리의 배경 장과 블루프린트 선화로만 쓴다(`intent_page-effects-library.md`).
