# 설계서 7.3 API 설계 확장과 8.2 컬렉션 명세서 자동 생성

## 문제

설계서가 174쪽으로 양식 분량(약 270쪽)에 크게 못 미친다. 그중 코드에 근거가 있는데도 비어
있는 두 곳이 있다.

- 7.3 서비스 REST API 설계는 대표 API 9개뿐이다. 양식은 API 1개 = 1쪽(27쪽)을 요구하고,
  코드에는 HTTP 경로 정의가 163개 있다.
- 8.2 컬렉션 명세서는 대표 문서 몇 개만 적혀 있다. 컬렉션은 마이그레이션 기준 70개 이상이다.
  예전에 손으로 옮긴 명세서는 스키마보다 뒤처졌고, 뽑는 도구가 없어 같은 일이 반복된다.

## 원하는 결과

- 7.3에 주요기능(2.5의 F 32개 · 2.6 관리자) 가운데 대표 API가 없는 것마다 1개씩 더해 25개 안팎이
  된다. 각 API는 기존 9개와 같은 형식(요청 · 응답 방향 그림, 파라메터 표, IN/OUT 전송 예시,
  설명 한 문단)이고, 파라메터와 타입은 `packages/contracts`의 Zod 스키마와 실제 라우트에서 옮긴다.
- 8.2가 모든 컬렉션의 필드(이름 · 타입 · 필수 · 제약)와 인덱스 표로 채워진다. 이 표는 새
  스크립트가 마이그레이션을 적용한 임시 MongoDB에서 읽어 생성하며, `--check`로 문서와 스키마의
  어긋남을 검사할 수 있다.
- 7.2 · 8.1의 개수 표기가 새 내용과 맞고, md 초안 · PDF가 함께 갱신된다. 설계서는 200쪽 이상이 된다.

## 영향 범위

`docs/졸업작품-설계서.html` · PDF · `docs/design-doc/07-API-설계.md` · `08-데이터-설계.md`,
새 스크립트 `scripts/dump-collection-spec.mjs`. 결정 권한은 사용자(팀장).

## 제약

- 계약과 스키마에 없는 필드 · 타입 · 응답을 만들지 않는다. 예시 값만 만들어 적는다.
- 스크립트는 임시 데이터베이스를 만들어 쓰고 지운다. 개발 DB를 건드리지 않는다.
- 스크립트를 돌리려면 MongoDB가 떠 있어야 한다 — Docker를 켜고 `pnpm infra:up`이 필요하다.
- 문체 · 그림 형식은 기존 7.3 · 8장과 같게 한다. 부연 설명 박스와 현황 고지 문장을 쓰지 않는다.

## 범위 밖

- 5.5 관리자 화면 · 6장 시퀀스 추가 · 2.4 유스케이스 명세 · 3장 확장.
- API나 스키마 자체의 수정. 명사형 URI 위반 등은 문서에 있는 그대로 둔다.
- CI에 `--check`를 거는 일.

## 열린 질문

1. Docker Desktop을 제가 켜도 되는가? — 답: 켠다(2026-10-05 사용자 결정). 이어서 `pnpm install` 후
   `pnpm infra:up`은 제가 돌린다.
2. 8.2 표에 MongoDB validator의 제약(pattern · enum · 최대 길이)을 모두 적는가? — 기본안: enum과
   최대 길이는 적고, UUID pattern은 타입 칸에 「UUID 문자열」로 줄여 적는다.
