# 구조화 Spec 생성의 재시도 대상 분리와 프롬프트 형식 설명 단일화

## 문제

2026-10-13 json-render 구현 조사에서 Spec 생성 경로(`services/backend/src/modules/page/structured-generator.ts`)의 결함 두 가지를 확인했습니다.

1. **모델이 고칠 수 없는 오류도 모델에게 다시 요청합니다.** 재시도 고리의 `try`가 Spec 검사와 렌더링(`renderStructuredPortfolio`)을 함께 감쌉니다. 서버 렌더링에서는 json-render의 요소별 오류 경계가 동작하지 않아 컴포넌트 하나의 예외가 렌더링 전체를 실패시킵니다. 수집 원본 어댑터 결함이나 저장 크기 초과(`PAGE_MAX_BYTES`)도 "검사 오류"로 모델에 전달됩니다. 이런 오류는 Spec을 바꿔도 해결되지 않으므로 모델 호출 한 번(PR #57의 Sonnet 실측 89–118초)과 비용이 낭비됩니다. 최종 오류 메시지 "구성 계약 검사를 통과하지 못했습니다"도 원인이 모델 출력인지 렌더러인지 구분하지 않습니다.
2. **Spec 형식 설명의 기준이 두 곳에 있습니다.** 프롬프트가 요소 ID 목록, 요소별 `props` 형태, `$state` 경로, 컨테이너 규칙을 문자열로 직접 적습니다. 같은 내용이 모델 출력 스키마(`structuredModelSchema`)와 카탈로그에도 있습니다. PR #57처럼 Spec 구조를 바꿀 때 한쪽만 고치면 프롬프트와 스키마가 서로 다른 지시를 합니다.

## 원하는 결과

- 렌더러 예외(어댑터 예외, 저장 크기 초과)는 모델을 다시 호출하지 않고 바로 실패합니다. 오류 메시지와 오류 종류가 Spec 검사 실패와 구분됩니다.
- Spec 검사 실패(계약 위반, 원본 역할 불일치, 사용자 스타일 미보존)는 지금처럼 오류를 붙여 한 번 다시 요청합니다.
- 두 경우가 단위 테스트로 고정됩니다. 렌더러 예외의 모델 호출 횟수는 1회, Spec 검사 실패는 2회입니다.
- 프롬프트의 요소 ID 목록과 요소별 `props` 형태 설명을 출력 스키마와 같은 출처에서 생성합니다. Spec 구조를 바꿀 때 프롬프트 문자열을 따로 고치지 않아도 됩니다.
- 생성된 형식 설명이 출력 스키마와 일치하는지 테스트로 확인합니다. 예를 들어 프롬프트에 적힌 요소 ID 집합과 스키마가 허용하는 요소 ID 집합이 같아야 합니다.
- 설명의 출처만 바뀌므로 모델에 전달하는 규칙의 의미는 그대로입니다. 바뀐 프롬프트 전문을 PR에 첨부합니다.
