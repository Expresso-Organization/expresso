    검토 결론

    전환은 가능합니다. 다만 지금 데이터베이스가 지키던 규칙 일부가 응용 코드로 옮겨지고, 질의를 손대야 하는 자리가 천 곳을 넘습니다. 결정을 가르는 것은 기술적 장애물이 아니라 작업량과 규칙 이전입니다.

    CONTEXT

    이 검토는 MySQL 8.4 LTS 이상을 전제로 합니다. 8.0 미만에는 CTE · 윈도 함수 · SKIP LOCKED · check 제약이 없어, 그 아래 버전을 목표로 잡으면 결론이 달라집니다.

    04

    다시 설계할 자리

    이 절이 전환 비용의 대부분입니다

    RETURNING — 249곳

    MySQL에는 returning이 없습니다 — 9.7 기준으로도 마찬가지입니다. 지금은 삽입 · 갱신과 그 결과 읽기가 문장 하나인데, 옮기면 쓰기와 재조회 두 문장이 됩니다. 같은 트랜잭션 안에서 어떤 잠금으로 다시 읽을지를 자리마다 판단해야 합니다. 43개 파일에 걸쳐 있습니다.

    스키마 안의 트리거와 함수

    불변 규칙이 PL/pgSQL로 스키마 안에 들어 있습니다. 소유자가 다른 행을 잇지 못하게 막는 ensure_owned_reference, 기록 속성 검증, 공고 원문 열의 불변 보장 같은 것들입니다. MySQL 저장 프로시저 언어로 다시 쓰면 대부분 옮겨지지만, 두 개는 옮겨지지 않습니다.

    함수하는 일
    retain_portfolio_snapshots스냅샷을 최근 50개만 남기려고 자기 표에서 지웁니다.
    retain_recent_recipe_revisions레시피 이력에 같은 방식을 씁니다.

    MySQL 트리거는 자기가 붙은 표를 고칠 수 없습니다. 이 둘은 응용 코드나 정기 작업으로 옮겨야 하고, 그러면 보관 개수 제한이 데이터베이스의 보장에서 코드의 약속으로 바뀝니다.

    지연 제약 — 1곳

    brew_source_nonempty_selection은 「후보가 있는 제작 세션은 선택된 재료를 적어도 하나 남긴다」를 트랜잭션이 끝날 때 확인합니다. 중간 상태를 허용해야 성립하는 규칙이라 지연 검사가 필요한데, MySQL은 제약을 문장마다 즉시 검사하고 지연 검사가 없습니다. 이 규칙은 응용 코드로 옮깁니다.

    스키마 테스트의 실행 조건

    스키마 테스트는 PGlite로 프로세스 안에서 PostgreSQL을 띄워 마이그레이션을 전부 적용하고 제약을 검사합니다. 컨테이너 없이 pnpm test만으로 돕니다. MySQL에는 이에 해당하는 인프로세스 구현이 없어서, 전환하면 스키마 테스트도 컨테이너를 요구합니다.

    DO NOT

    규칙을 응용 코드로 옮기면서 테스트를 함께 만들지 않는 것. 지금은 트리거와 check 제약이 잘못된 데이터를 입구에서 막고 있고, 그 보장이 사라지는 자리마다 대신 지킬 테스트가 있어야 합니다.

    06

    작업량과 순서

    앞 단계가 끝나야 다음이 검증됩니다
    1. 스키마 번역 지금 스키마 한 벌을 MySQL DDL로 새로 씁니다. 표 74 · 열 705 · 제약과 인덱스가 대상입니다.
    2. 드라이버와 러너 교체 연결 자리와 마이그레이션 러너를 mysql2로 바꿉니다. 자문 잠금은 get_lock()으로 옮깁니다.
    3. 질의 재작성 제품 546곳과 테스트 539곳. returning 249곳은 자리마다 잠금 판단이 필요합니다.
    4. 규칙 이전 트리거 30 · 함수 25를 저장 프로시저로 다시 쓰고, 옮겨지지 않는 셋을 응용 코드와 테스트로 대신합니다.
    5. 시험 환경 통일 스키마 테스트를 컨테이너 기반으로 바꾸고, CI의 순서와 시간을 다시 잽니다.
    6. 데이터 이관 운영 데이터가 있으면 uuid · 타임스탬프 · JSON · 배열을 변환합니다. 되돌리려면 양쪽에 함께 쓰는 기간이 필요합니다.

    3번과 4번이 전체의 대부분입니다. 두 단계는 나눠 맡을 수 있지만, 같은 표를 건드리는 모듈끼리는 규칙 이전이 끝난 뒤에 합쳐야 검증이 됩니다.
