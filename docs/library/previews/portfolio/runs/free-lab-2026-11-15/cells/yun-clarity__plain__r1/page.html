사례 1 · 2024.04 – 2024.11

LCP 3.8초를 1.9초로: 상품 상세 App Router 전환

서버와 클라이언트의 경계를 비용 기준으로 다시 그었고, 그 결과를 배포 기준으로 고정했습니다.

  1. 문제

    오래된 CSR 구조에서 상품 상세 첫 렌더가 느렸습니다.

  2. 판단

    Pages Router에서 App Router로 옮기며 데이터 요청을 서버 컴포넌트로 올렸습니다. 상호작용이 필요한 부분만 클라이언트 컴포넌트로 남겼습니다.

  3. 리스크 관리

    전환 중에도 기존 주소와 SEO 메타를 그대로 유지하는 점진 전환으로 진행했습니다.

  4. 재발 방지

    배포마다 Lighthouse CI로 성능 예산을 검사합니다. 한 번의 개선으로 끝나지 않게 한 장치입니다.

판단 근거를 글로 남겼습니다

「App Router 전환기: 상품 상세 LCP를 절반으로」에 데이터 요청 위치 결정, 캐시 무효화, 점진 전환 방법을 정리했습니다. 이 글로 팀에 판단 근거를 공유했습니다.

사례 2 · 2023.06 – 2024.03

같은 수정을 세 번 하지 않기 위해: 모아 UI

UI를 통일한 것이 아니라, 반복 수정이 생기는 구조를 없앴습니다.

1

진단

화면마다 버튼과 입력 모양이 달라 디자이너와 개발자가 같은 수정을 여러 번 했습니다.

2

토큰 정리

색 · 간격 · 글꼴을 디자인 토큰으로 먼저 정리했습니다.

3

배포

Radix UI 기반, 접근성을 기본으로 갖춘 컴포넌트 48개를 Storybook 문서와 함께 배포했습니다.

시각 회귀 테스트로 변경이 기존 화면을 깨지 않게 했고, 그 결과 신규 화면의 개발 기간은 평균 5일에서 3일로(가상 집계), 공통 컴포넌트 사용 비율은 30%에서 80%로 올랐습니다. 프론트엔드 코드 리뷰 기준 문서도 작성해 팀 기준으로 쓰이고 있습니다.

결제 화면의 접근성은 나중 일이 아니라 기본값

접근성을 한 화면의 수정이 아니라 공통 컴포넌트의 기본값으로 다룹니다.

결제 페이지를 WCAG AA 기준에 맞춰 점검하고 고쳤습니다. 커머스에서 가장 민감한 흐름이라 속도만큼 기준을 둬야 했습니다. 모아 UI의 컴포넌트는 접근성을 기본 속성으로 갖추고 있어, 새 화면이 만들어질 때마다 같은 기준이 따라옵니다.

쓰는 도구와 일하는 방식

React · Next.js · TypeScript를 오래 쓰면서, 품질을 자동으로 검사하는 도구까지 직접 붙여 왔습니다.

React5년서버 컴포넌트와 클라이언트 컴포넌트 경계 설계
Next.js App Router2년Pages Router에서 점진 전환, 데이터 요청 위치와 캐시 무효화 판단
TypeScript5년제네릭과 판별 유니온으로 API 응답 타입을 계약처럼 다룸
품질 도구—Radix UI, Storybook, 시각 회귀 테스트, Lighthouse CI
