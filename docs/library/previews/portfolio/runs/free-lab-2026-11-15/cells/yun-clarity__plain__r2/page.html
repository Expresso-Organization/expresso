01 · 요약

숫자로 본 지난 두 해

속도, 번들, 재사용, 작업 기간이 같은 방향으로 움직였습니다. 행을 누르면 그 수치가 나온 작업으로 내려갑니다.

  1. App Router상품 상세 LCP 가상 측정3.8초 → 1.9초
  2. App Router클라이언트 JS420KB → 180KB
  3. 모아 UI신규 화면의 공통 컴포넌트 사용 비율30% → 80%
  4. 모아 UI신규 화면 개발 기간 평균 가상 집계5일 → 3일

막대는 전환 전 값을 100%로 둔 비율입니다. 사용 비율은 80%를 그대로 길이로 썼습니다.

02 · 사례 · 2024.04 — 2024.11

LCP 3.8초를 1.9초로: 상품 상세 App Router 전환

문제
오래된 CSR 구조에서 상품 상세 첫 렌더가 느렸습니다.
판단
데이터 요청을 서버 컴포넌트로 올리고, 상호작용이 필요한 부분만 클라이언트 컴포넌트로 남겼습니다. 서버와 클라이언트의 경계를 비용 기준으로 다시 그은 것입니다.
리스크 관리
Pages Router에서 App Router로 옮기는 동안에도 기존 주소와 SEO 메타를 그대로 유지했습니다.
재발 방지
배포마다 Lighthouse CI로 성능 예산을 검사해, 한 번 줄인 수치가 다시 늘지 않게 했습니다.
남긴 것: 판단 근거를 글로

「App Router 전환기: 상품 상세 LCP를 절반으로」에 데이터 요청 위치 결정, 캐시 무효화, 점진 전환 방법을 정리했습니다. 수치만이 아니라 왜 그렇게 정했는지를 팀이 읽을 수 있게 하려는 것이었습니다.

03 · 사례 · 2023.06 — 2024.03

같은 수정을 세 번 하지 않기 위해: 모아 UI

화면마다 버튼과 입력 모양이 달라 디자이너와 개발자가 같은 수정을 여러 번 했습니다. UI를 통일하는 데서 그치지 않고, 반복 수정이 생기는 구조를 없애는 쪽으로 풀었습니다.

  1. 1

    진단

    화면마다 다른 버튼 · 입력 · 모달이 반복 수정의 원인이었습니다.

  2. 2

    토큰 정리

    컴포넌트보다 먼저 색 · 간격 · 글꼴을 디자인 토큰으로 정리했습니다.

  3. 3

    배포

    Radix UI 기반, 접근성을 기본으로 갖춘 컴포넌트 48개를 Storybook 문서와 함께 배포했습니다.

  4. ✓

    정착

    시각 회귀 테스트로 변경이 깨지지 않게 하고, 신규 화면의 공통 컴포넌트 사용 비율이 30%에서 80%가 되는 것으로 자리 잡았는지 확인했습니다.

결과 신규 화면 개발 기간 평균 5일 → 3일 (가상 집계)

04 · 품질 기준

결제 화면의 접근성은 나중 일이 아니라 기본값

결제 페이지를 WCAG AA 기준에 맞춰 고쳤습니다. 접근성은 한 화면의 수정으로 끝내지 않고, 모아 UI의 컴포넌트가 처음부터 갖고 있는 속성으로 내려놓는 방식으로 다룹니다.
