# 추천모델 운영 적용 준비 검증

최신 main 기반 통합본의 제품·배포·복구 검증을 마쳤다. 로컬 추천을 사용자가 선택해 실행하는 운영 후보이며, 실제 운영 전환은 수행하지 않았다.

## 통합 범위

- 기준 main: `e51b9839`. 모델 개선: `6a6ae5d5`. 통합 브랜치: `codex/integration-match-release`.
- 최신 탐색의 `ExploreFrame`·`JobSearchFlow`, 커리어 편집기·채팅 연결을 유지하면서 추천·근거 진입점을 연결했다.
- 배포본별 Python 환경과 고정 의존성, 파일별 체크섬, `current`·`previous` 전환, systemd·상태 검사·초기 벡터 준비·실패 복구를 추가했다.
- 전체 준비와 Worker가 겹쳐 체크포인트가 바뀌면 원천을 다시 대조한다. 늦게 도착한 전체 스냅샷이 삭제된 기록의 벡터를 남기는 경합을 회귀 시험으로 확인했다.
- CPU 검사와 배포 안전 검사를 백엔드 CI에 연결했다. GitHub의 원격 CI는 아직 실행하지 않았다.

## Oracle 인증 API 검증

운영 DB에서 모집 중인 공개 공고 729개·저장된 요건 316개·회사 134개를 읽기 전용으로 복사했다. 실제 사용자 기록·인증 정보는 복사하지 않았다. 별도 MongoDB·Redis·API·Worker·추론·SQLite에 가상 계정 6명의 기록 207개를 넣었다. 기록 수는 25/50/3/10/19/100개다.

Oracle ARM64에서 추론을 한 코어·ONNX 1스레드에 고정했다. 시험 MongoDB는 CPU 0.5코어 한도를 사용했다. 측정은 서버 내부 인증 HTTP API 전체 추천 경로이며, 공개 HTTPS·브라우저 렌더링 지연은 포함하지 않는다.

첫 전체 임베딩 준비는 1,780.47초(29분 40초)였고 벡터 3,661개를 생성했다. 추천은 729개를 검사해 한국어 요건을 평가할 수 있는 387개 중 상위 10개를 반환했다. 각 계정의 1위 공고에서 반환한 기록의 소유권과 인용문 원본 위치를 대조했다.

총 156개 요청에서 같은 계정의 결과가 기준 결과와 같았으며 추가 인코딩은 없었다. 단일 공고의 직접 함수 호출 지연인 기존 56.5ms와 측정 범위가 다르다.

### 변경·재시작·장애

- 실제 저장 API로 기록 제목을 바꿨을 때 새 인코딩 5개를 확인했다. 삭제한 기록의 참조가 해제됐고 근거 응답에서 제외됐다.
- Worker 중단 중 저장한 변경을 재시작 후 변경 스트림에서 재처리했다.
- API·Worker·추론을 3회 모두 종료·재시작했다. 재시작 직전과 순위·점수·근거가 같았다. 매번 벡터 3,655개를 복원했고 새 인코딩은 0이었다.
- 준비까지 걸린 시간은 17.45/8.40/8.40초, 재시작 직후 6개 동시 추천은 4.69/4.60/4.63초였다. 공유 VM을 재부팅하지 않았다.
- 추론 중단 시 0.032초에 `unavailable`을 반환했고 API 준비 상태는 정상이었다. 추론 복구 후 이전 결과와 같았다.

## 전환 스크립트와 systemd

운영과 이름·포트·상태 경로를 분리한 실제 systemd 유닛에서 검사했다.

- 강제 종료 후 새 PID로 자동 재시작했고 디스크 벡터를 복원했다. CPU 한 코어 한도와 `ProtectSystem=strict` 적용을 확인했다.
- 첫 활성화에서 DB 연결 실패를 주입하자 `current`와 API·Worker 연결 설정을 회수하고 시험 추론 서비스를 비활성화했다.
- 정상 활성화에서 전체 원천 준비를 통과했고 새 인코딩은 0이었다.
- 기존 모델이 있는 상태에서 준비 실패를 주입하자 기존 선택 링크와 추론 서비스를 복원했다.
- 비활성화 후 선택 링크·연결 설정·시험 유닛을 정리했다. 운영 API·Worker 유닛으로 전환 스크립트를 실행하지 않았다.

## 운영 경로의 비활성 준비

배포 파일은 `/home/ubuntu/expresso/var/match-model/releases/3a6d6fbf131096ce-31dd18d5847ee015`에 준비했다. 파일 해시·실제 CPU 추론·디스크 복원을 검사했다.

운영 원천의 임베딩은 서버 안의 임시 추론 프로세스와 준비 CLI로 생성했다. 정상 런타임 구성으로 DB를 읽었고 기록이나 공고를 수정하지 않았다. 공개 공고 벡터를 재사용한 뒤 운영 원천을 전체 대조해, 유효 기록을 가진 계정 12개·벡터가 있는 공고 420개·벡터 3,783개와 체크포인트 1개를 `/var/lib/expresso-match`에 준비했다. 공고 420개에는 만료된 공고의 캐시가 포함된다.

최종 코드로 다시 부팅·대조했을 때 벡터 3,783개를 복원했고 새 인코딩은 0이었다. 원천 재대조 CLI는 6.09초에 완료됐다. 원문과 인증 정보는 보고서에 넣지 않았으며 벡터 상태는 운영 서버에 보관한다.

`current` 링크와 운영 추론 유닛은 아직 없다. 운영 API·Worker·Web은 `e51b9839`로 실행 중이며 MongoDB·Redis 준비 상태는 정상이다. 임시 준비·시험 서비스는 종료했다.

## 전환 조건

원격 반영·main 머지·실제 배포는 미실행 상태다. main 머지는 자동 배포를 시작하므로 결과 검토 후 진행한다. 모델 가중치와 평가 지표는 이번 통합에서 변경하지 않았다. 독립적인 실제 사용자 품질 평가는 남아 있으며 기존 기본 탐색을 유지한 선택형 로컬 추천으로 공개한다.

배포본 선택, 초기 상태 재대조와 복구 명령은 [추천모델 배포 절차](../operations/MATCH_MODEL_RELEASE.md)를 따른다.
