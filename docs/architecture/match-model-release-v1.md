# Expresso 한국어 추천 모델 v1

기존 E5 MLP에 요건별 경력 근거를 결합한 모델을 학습하고, 한국어 평가 공고 32건 전체에서 프로필 40명의 순위를 검증했다. NDCG@10은 기존 MLP 0.236, 새 로컬 모델 0.589, 같은 상위 10개를 Decisions로 재정렬했을 때 0.667이었다.

- 공고 추천과 특정 공고의 근거 기록 검색을 각각 실행할 수 있다. 기본 실행은 로컬 CPU를 사용하며 외부 API 사용은 호출별 선택이다.
- 검증 분할에서 가중치와 근거 표시 기준을 정했다. 평가 공고 32건은 최종 모델을 선택하는 데 쓰지 않았다. 여섯 가상 계정은 별도의 회귀 평가에 사용했다.
- 60점 이상 적합 공고는 새 평가 풀 1,280쌍에서 한 건이다. 이 데이터로 일반적인 적합 공고 회수율이나 채용 성공 가능성을 판단하기 어렵다.

## 무엇을 학습했는가

| 구성 | 입력과 동작 | 선택 근거 |
|---|---|---|

| 공고 재정렬 | 로컬 상위 K개에 대해 고정 요건과 요건별 상위 근거 원문 3건을 Decisions에 전달한다. 거절 항목은 후보 맨 뒤에 두고 동점은 기존 순서를 유지한다. | 한국어 최종 평가 K=10. 6개 더미 공고에서는 K=3. |
| 선택한 공고의 기록 검증 | 학습 모델·코사인·BM25의 순위에서 번갈아 최대 12개 기록을 고른다. 고정 요건과 기록 한 건의 관계를 Decisions로 채점해 상위 3건과 표시 기준 통과 ID를 반환한다. | 검증 표본에서 근거 존재 F1을 기준으로 API 표시 문턱 25/100 선택. 이 값은 API 점수의 문턱이며, 공고 적합 기준 60과 목적이 다르다. |

학습 코드는 파일럿 인코더 가중치를 동결한다. 모델 B는 교사가 연결한 기록을 학습하므로, 누락된 대체 근거가 음성 예시에 들어갈 수 있다. `evidenceRecordIds`는 모델이 제안한 근거다. 로컬 모델 A는 프로필 전체뿐 아니라 개별 기록을 읽지만, 개별 기록과 전체 공고 입력은 각각 E5의 512토큰 한도가 적용된다. ## 데이터와 검증 절차

- 수집 공고 855건의 스냅샷에서 기존 한국어 평가 공고와 겹치는 ID·정규화 원문·제목 등을 제외했다. 한국어 자격요건 절에서 최소 두 개의 항목을 확보한 공고 190건을 사용했다. 원문에서 필수 최대 4개, 담당업무 최대 2개, 우대 최대 2개를 선택하고 원문 행 번호를 고정했다. 공고 전체의 자격조건을 모두 포괄하는 자료로 간주하기는 어렵다.
- 학습·검증·평가 공고 풀은 124/34/32건, 프로필은 144/30/40명이다. 공고·프로필 ID는 세 분할 사이에서 분리했다. 프로필은 파일럿의 원래 분할을 유지했다. 과거 실험과 일부 프로필·생성 방식은 공유하며 새 평가의 모든 공고와 쌍은 기존 한국어 평가 공고에서 제외했다.
- 초기 후보는 프로필당 BM25 상위 3건과 나머지 중 고정 해시로 뽑은 3건이다. Terra가 이미 정한 요건마다 등급과 근거 ID를 부여하고 코드가 필수·업무·우대 비중 45/40/15를 적용했다. 학습 864쌍 중 회사 소개·잘린 문장이 요건에 섞인 두 공고의 3쌍을 제외했다. 중복 기간 가산이나 직군 태그를 이용한 양성 생성은 적용하지 않았다.
- 최종 평가 프로필 40명은 남은 26개 공고에도 같은 요건·루브릭을 적용해 **40 × 32 = 1,280쌍 전부** 채점했다. 화면에 상위 노출된 공고만 라벨이 있는 문제를 이 분할에서 해소했다. 요건 9,200건 중 대표 근거가 연결된 요건은 1,503개였다.
- 더미 6명의 207개 기록과 공고 6건은 학습과 가중치 선택에서 제외했다. 공고 순위 비교를 위해 기존 258개 요건별 판정에 루브릭 가중치를 적용한 점수를 참고값으로 썼다. 이 점수는 에이전트가 작성한 표에서 파생됐고 독립적인 사람의 공고 선호 순위는 확보하지 않았다.

## 공고 추천 결과

| 전체 공고에 라벨이 있는 평가 | 후보 풀 · 반환 수 | 기존 MLP | 새 로컬 모델 | 같은 후보를 로컬 근거 점수로 재정렬 | 같은 후보를 Decisions로 재정렬 |
|---|---|---:|---:|---:|---:|
| 한국어 40명 | 32건 · 상위 10 | 0.2362 | 0.5893 | 0.6116 | **0.6665** |
| 더미 6명 | 6건 · 상위 3 | 0.6714 | 0.8528 | 0.8934 | **0.8973** |

지표는 프로필별 선형 이득 NDCG의 평균이며 각각 NDCG@10·NDCG@3이다. 재정렬기는 로컬 상위 후보 안에서만 순서를 바꿨다. 한국어 평가에서 Decisions와 새 로컬 모델의 평균 차이는 **+0.0772**였다. 프로필 단위 paired bootstrap 20,000회·seed 42의 95% 구간은 **+0.0556~+0.0999**였다. 60점 이상 한 쌍은 상위 10개에 포함됐다. 더미 계정의 60점 이상은 5명·7쌍, 해당 5명 기준 평균 Recall@3은 0.80이었다.

기존 100명 실험의 미완료 API 비교도 별도로 끝냈다. 기존 평가 30명에서 라벨 후보만 정렬하면 Decisions 0.900, 기존 MLP 0.814였다. MLP가 전체 풀에서 고른 상위 300자리 중 라벨이 있던 자리는 54개였다. 그때의 불완전한 정답으로 측정한 파이프라인 수치를 새 완전 판정 풀의 수치와 직접 비교하지 않는다. [분할별 지표·신뢰구간과 이전 비교](../assets/match-release-2026-11-19/evaluation.json)

## 어떤 경력 기록이 근거인지 찾는 성능

일부 요건은 근거 1개, 일부는 여러 개를 정답으로 갖는다. Hit@3는 정답이 있는 요건 중 상위 3건에서 하나 이상을 회수한 비율이다. 근거 존재 F1은 근거가 없는 요건도 포함한다.

| 대상 | 평가 요건 / 근거 있음 | 로컬 Hit@3 | 후보 확장 + Decisions Hit@3 | 로컬 / Decisions 근거 존재 F1 |
|---|---:|---:|---:|---:|
| 한국어 전체 풀, 로컬 검색 | 9,200 / 1,503 | 88.7% | 해당 없음 | 0.447 / 해당 없음 |
| 한국어 평가 중 사전 해시 표본 | 256 / 44 | 90.9% | 86.4% | 0.504 / 0.725 |
| 더미 6명 전체 | 258 / 153 | 45.8% | 74.5% | 0.534 / 0.912 |

더미 계정에서 **직접 또는 강한 직접 근거만** 대상으로 하면 88개 중 로컬 40개(45.5%), 외부 검증 경로 66개(75.0%)를 회수했다. 검증용 후보 12개에 정답이 한 건 이상 들어간 비율은 더미의 전체 근거 요건에서 83.7%였다. 후보 생성에서 놓친 기록은 외부 검증으로 복구할 수 없다.

| 계정 | 기록 수 | 근거가 있는 요건 | 로컬 → 외부 검증 Hit@3 |
|---|---:|---:|---:|
| 문가령 | 25 | 31 | 61.3% → 71.0% |
| 배준호 | 50 | 33 | 24.2% → 66.7% |
| 한서윤 | 3 | 13 | 100% → 100% |
| 오태민 | 10 | 19 | 73.7% → 94.7% |
| 윤하린 | 19 | 24 | 41.7% → 91.7% |
| 정우진 | 100 | 33 | 18.2% → 51.5% |

한서윤은 기록이 세 건뿐이어서 Hit@3만으로 순서 품질을 구분할 수 없다. 배준호·정우진처럼 기록이 많은 계정에서는 근거 누락이 남았다. 같은 계정에서 기록 수를 줄이는 실험도 진행했다. 고정 해시 순서로 부분집합을 만들고, 남아 있는 정답 ID를 기준으로만 계산했다. 희망 직무나 계정 규모 자체를 인과 효과로 해석하지 않는다. 한국어 해시 표본에서는 외부 검증이 기록 순위의 일관된 개선을 보이지 않았으므로 두 외부 호출 경로 모두 명시적으로 선택할 수 있게 제공한다.

## 패키지와 실행

- CPU 패키지는 E5 인코더, 모델 A·B 채점 ONNX, 토크나이저, 근거 표시 정책, 두 추론 명령, 설치 확인용 예시 입력으로 구성한다. 가중치와 원문은 Git에 올리지 않고 Mac과 학습 PC의 실험 디렉터리에 보관한다. [CPU 실행 안내](../../scripts/ml-data/match_release/README.md)
- Mac 실험 디렉터리는 저장소의 `var/model-dev-v1/`이다. `expresso-match-cpu-v1.tar.gz`는 실행 패키지, `bundle/`은 PyTorch 복원용, `cpu/`는 ONNX 복원용, `example-input.json`은 실제 가상 계정과 공고를 연결한 로컬 예시다.
- 학습 PC 보관 위치는 `C:/code/expresso/.worktree/p5-data-collection/var/ml-data/experiments/match-release-4bc8ec9c8a85`다.
- CPU 실행 환경은 Python 3.12, ONNX Runtime 1.31.0, NumPy 2.3.2, tokenizers 0.21.4다. 모델 학습에는 PyTorch 2.7.0, transformers 4.55.4를 사용했다. CPU는 4스레드로 검사했다.
- Mac에서 여섯 계정의 공고 순서와 258개 요건의 상위 기록 ID가 PyTorch와 ONNX에서 모두 일치했다. 로컬 점수 최대 절대차는 0.00012점 미만이었다. Mac에서 측정한 공고 캐시를 재사용한 다섯 실제 요청의 중앙값은 약 0.55초였다. 사용자당 기록 수가 서로 달라 서비스 p95로 쓸 수 없다.
- Windows 학습 PC에서 동일한 25기록·6공고 입력으로 CPU 패키지 코드와 가중치를 다시 실행했다. Mac과 6개 공고 순서, 43개 요건의 상위 기록 ID가 일치했다. [교차 장비 일치도·파일 체크섬](../assets/match-release-2026-11-19/model-manifest.json)

## 재실험 순서

1. `fixed_data.py`로 파일럿 분할의 프로필과 수집 원문에서 고정 요건과 후보 목록을 작성한다. 입력 스냅샷의 SHA-256은 모델 명세에 있다.
2. `label_fixed.py`로 후보의 Terra 라벨을 만든다. `test_pool.py`는 남은 평가 후보를 채점해 전체 풀을 완성한다. 완료 응답 캐시는 입력 해시로 대조한다.
3. `train.py`에 파일럿 프로필·라벨·기록 임베딩, 기존 MLP 체크포인트, 지정 리비전 인코더와 새 라벨을 넘긴다. 학습 seed는 42다. 기록 학습은 요건별 연결 기록과 표본 추출한 비연결 기록을 사용한다. 검증 MRR로 B를 선택하고 검증 NDCG로 A를 선택한다.
4. `evaluation.py predict`, `api`, `report`로 공고 순위를 비교한다. `export_cpu.py`로 ONNX를 내보내고 `verify.py`로 원문·분할·CPU 일치도와 동일 계정 기록 수 실험을 검증한다. `record_search.py evaluate`로 요건별 외부 검증을 비교하고 `package_cpu.py`로 실행 패키지를 만든다. 각 명령은 `--help`로 경로 인수를 확인할 수 있다.

저장소 루트에서 학습이 끝난 모델을 실제 계정 예시로 복원하는 명령은 다음과 같다.

```sh
R=var/model-dev-v1
uv run --no-project --python 3.12 --with-requirements scripts/ml-data/match_release/requirements-cpu.txt python scripts/ml-data/match_release/cpu.py --bundle "$R/cpu" --input "$R/example-input.json" --output "$R/my-ranking.json" --top-k 6
uv run --no-project --python 3.12 --with-requirements scripts/ml-data/match_release/requirements-cpu.txt python scripts/ml-data/match_release/record_search.py query --bundle "$R/cpu" --input "$R/example-input.json" --job-id 9313f79c-febf-4311-bc0e-05d05c60a993 --output "$R/my-evidence.json"
```

배포 파일은 701,528,668바이트이며 SHA-256은 `7e57ade555763b514271e6396152b13535a5df468a35cdce5f92bdaf86a90fce`다. Windows 복사본에서 학습 및 평가 파일의 해시를 Mac 명세와 대조했다. 압축을 새 폴더에 풀어 최소 CPU 의존성으로 공고 추천과 개별 공고 근거 검색 명령을 실행했다.

## 제품 연결 및 검증

인증된 사용자는 공고 탐색의 **내 기록으로 공고 추천받기**에서 로컬 모델을 실행한다. 공고 상세의 **요건별 내 경력 근거 보기**에서 요건과 연결된 본인의 기록을 연다. 기본 입력은 정리됨·검증됨 상태의 기록이다. 모델 점수는 공고 순위용이며 기존 요건 충족률은 별도로 계산한다.

- 추천 API는 모집 중인 공개 공고를 32개씩 계산해 전체 상위 10개를 합친다. 원문의 한국어 요건을 평가하며, 저장된 분석이 있으면 그 요건을 사용한다. 분석이 없으면 학습 때 사용한 원문 추출기를 쓰고, 원문과 대조할 수 있는 구조화 항목도 활용한다. 평가 가능한 공고 수를 응답에 표시한다.
- 사용자가 Decisions 버튼을 눌렀을 때 커리어 기록 사용과 공고 분석 동의를 확인한다. 공고 목록에서는 상위 후보를 재정렬하고 공고 하나를 열었을 때는 요건별 근거 기록을 검증한다. 외부 호출이 실패하면 화면에 로컬 결과임을 표시한다.
- Worker가 MongoDB에 커밋된 공개 공고, 요건, 커리어 기록, 카테고리와 프로필 변경을 읽어 임베딩을 갱신한다. 공고 기반 제작을 시작하면 근거가 연결된 기록을 재료 후보에서 먼저 보여준다. 추론이 실패해도 기존 재료 순위로 제작할 수 있다.

### 실행

저장소 루트에서 CPU 배포 파일을 풀어 둔 경로를 `MODEL_DIR`에 지정한 뒤 아래 명령으로 로컬 추론 서비스를 실행한다. 기본 주소는 `127.0.0.1:4810`이다.

```sh
uv run --no-project --python 3.12 \
  --with-requirements services/match-inference/requirements.txt \
  python services/match-inference/server.py --bundle "$MODEL_DIR/cpu" \
  --threads 1 --vector-dir var/match-embeddings
```

API와 Worker 환경에 `MATCH_MODEL_URL=http://127.0.0.1:4810`을 설정하고 기존 제품 실행 명령으로 시작한다. Decisions를 사용하려면 추론 서비스 실행 환경에 `OPENAI_API_KEY`를 설정하고 위 명령에 `--decisions-cache var/match-decisions-cache --policy "$MODEL_DIR/evidence-policy.json"`을 추가한다. `GET /health` 응답에는 로컬 서비스와 외부 검증 설정 상태가 담긴다.

### 저장·복구

- SQLite에 벡터와 입력 해시, 공고·사용자별 참조, MongoDB 변경 스트림 재개 위치를 저장한다. 경력 기록과 통합 프로필은 계정별로 구분한다. 공개 공고에서 같은 문구를 사용하는 요건은 벡터를 공유한다. 원문은 MongoDB에서 읽는다.
- 처음 실행하면 기존 공개 공고와 정리됨·검증됨 기록을 준비한다. 이후에는 변경된 입력만 인코딩한다. 기록 제목이나 본문이 바뀌면 기록과 통합 프로필을 갱신한다. 삭제되거나 자격을 잃은 기록은 참조를 해제하고 마지막 참조가 사라진 벡터를 지운다.
- 재시작하면 남겨 둔 재개 위치부터 처리한다. 변경 스트림 이력이 만료되면 원천을 다시 대조하고 디스크에 없는 입력만 계산한다. 인코더·토크나이저 파일 또는 인코딩 규약 버전이 달라지면 새 저장소를 준비한다. 퇴역한 모델의 저장 파일은 해당 모델의 데이터 보존 정책에 따라 정리한다.
- 준비가 끝나기 전에 추천을 요청하면 최신 원문으로 필요한 벡터를 계산한다. 변경 처리와 SQLite 커밋이 끝난 항목은 첫 추천부터 재사용한다. 부팅 시 기존 벡터를 메모리 한도 16,384개까지 복원한다. 한도를 넘으면 공개 공고를 우선하고, 이후 필요한 벡터는 SQLite에서 읽는다. 부팅 시 복원 수·추가 디스크 조회 수·새 인코딩 건수는 내부 `POST /v1/vector-stats`에 빈 JSON 객체를 보내 확인한다.

오라클용 systemd 유닛은 `infra/systemd/expresso-match-inference.service`에 있다. 호스트에 설치할 때는 CPU 배포본을 `/home/ubuntu/expresso/var/match-release`에 풀고, 저장소 루트에서 `uv venv --python 3.13 var/match-venv`와 `uv pip install --python var/match-venv/bin/python -r services/match-inference/requirements.txt`로 환경을 준비한다. 유닛을 설치하고 활성화하면 systemd가 부팅 때 서비스를 시작한다. SQLite 상태 경로는 `/var/lib/expresso-match`이며 배포 디렉터리와 분리한다. 개발·시험·운영은 각각 전용 상태 경로를 사용한다.

### 6계정 제품 검증

2026-11-19에 더미 계정과 실제 수집 공고를 분리한 MongoDB에 복사해 제품 API와 ONNX로 검증했다. 모집 중인 공개 공고 346개 중 한국어 본문이 있는 공고는 237개였고, 평가 가능한 요건을 얻은 202개를 선별했다. 109개에는 한국어 본문이 없었고, 한국어 공고 35개에서는 사용할 요건을 얻지 못했다.

| 계정 | 추천에 사용한 기록 | 반환 공고 |
|---|---:|---:|

| 한서윤 | 2 | 10 |
| 오태민 | 9 | 10 |
| 윤하린 | 19 | 10 |

각 계정의 1위 공고에서 요건별 기록 ID가 그 계정의 유효한 기록에 속하는지 확인했다. Chrome에서 문가령 계정으로 공고 탐색 → 추천 → 요건별 근거 → 기록 상세를 열었다. 실제 Decisions 응답으로 상위 10건을 재정렬했고, 1위 Data Analyst 공고의 요건 6개 모두에 기준을 넘은 기록이 있었다. 동일 공고로 분석 Worker의 완료 경로와 제작 재료 API까지 확인했다.

이 시험은 제품 경로를 검증한다. 순위 품질은 위의 분리한 평가 세트에서 측정했다. 독립적인 사람의 선호 순위와 실제 지원·합격 결과를 이용한 검증은 남아 있다.
