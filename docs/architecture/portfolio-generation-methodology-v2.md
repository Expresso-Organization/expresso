# 포트폴리오 생성 방법론 v2

- 상태: 설계 논의 초안
- 작성일: 2026-08-22
- 적용 대상: Expresso의 직무 맞춤형 웹 포트폴리오 생성
- 관계: v1의 통짜 생성 경로(모델이 지면 전체의 HTML/CSS를 한 번에 저작)를
  대체한다.

## 1. 목표

1. 토큰 효율적인 포트폴리오 생성
2. 시각적으로 아름다운 고퀄리티 디자인
3. 등장 애니메이션과 인터랙티브 요소

## 2. 핵심 원칙

- **AI는 백지에서 그리지 않는다.** 라이브러리에서 찾고, 눈과 텍스트로 보고,
  고르면 시스템이 조합한다. AI는 조합된 결과를 눈으로 확인해 필요한 곳만
  수술적으로 고친다. 애니메이션과 인터랙션도 직접 짜지 않고 찾아서 적용한다.
- **사람은 프롬프트와 정책만 작성한다.** 라이브러리 항목의 생성·선별·축적은
  시스템의 검색과 AI가 수행한다. 사람이 항목을 하나하나 만들거나 고르지 않는다.
- **자연스러운 조합은 조합 알고리즘이 아니라 라이브러리 입장 규약의 문제다.**
  조합 결과의 통일감은 대부분 항목이 라이브러리에 들어올 때 결정된다. 조합기는
  얇고 결정적으로 유지한다.

## 3. 생성 흐름

1. AI가 라이브러리에서 디자인 요소를 검색한다.
2. 검색 결과를 스크린샷과 description으로 확인하고 사용할 항목을 결정한다.
3. 시스템이 결정된 항목을 자동으로 조합한다.
4. AI가 조합 결과를 눈으로 확인하고, 수정이 필요한 곳만 수술적으로 미세
   수정한다.
5. 이후 사용자가 요구하는 편집은 AI가 직접 수정한다.

모션·인터랙션도 1~2단계의 검색·선택을 똑같이 탄다. 별도의 단계가 아니라 항목
종류(§4.1) 중 하나다. 1~2단계의 결정은 페이지 전역 결정부터 순서대로
진행한다(§6.1).

## 4. 라이브러리 구성

### 4.1 항목의 종류

AI가 검색해서 고르는 디자인 결정은 전부 항목이 된다.

| 종류 | 내용 |
|---|---|
| 구조 컴포넌트 | 내용이 들어갈 슬롯을 가진 섹션·요소 단위의 HTML/CSS 구조 |
| 테마 | 팔레트와 타이포그래피 조합. 페이지 전체에 주입되는 CSS 변수 값 |
| 모션 프리셋 | 등장 애니메이션과 인터랙션 |

한 지면은 구조 × 테마 × 모션 × 내용의 조합으로 만들어진다.

### 4.2 항목의 꼴

| 요소 | 역할 |
|---|---|
| raw HTML/CSS | 조합기가 소비하는 실체. 내용이 들어갈 슬롯을 가진다. 검색 신호로 쓰지 않는다 |
| description | 검색 임베딩의 원천. 서술 템플릿을 따른다 |
| 스크린샷 | AI의 눈 확인용. 등록할 때 미리 렌더하며 질의 시점에 렌더하지 않는다 |
| 임베딩 | description 기반 벡터. 초기에는 두지 않고 규모가 커지면 추가한다(§5.2) |
| 메타데이터 | 종류·용도·밀도 태그, 필요한 표면 종류(§6.3), 슬롯 제약 — 항목 수 범위 · 텍스트 길이 범위 · 이미지 필수 여부(§5) |

description은 자유 문장으로 두지 않고 서술 템플릿을 따른다 — 무엇을 보여주는가
· 어떤 인상을 주는가 · 어떤 내용이 들어가는가. 검색 품질은 인덱스만큼 질의
어휘가 정하므로, AI가 질의할 때 쓰는 어휘 체계와 description의 어휘 체계를 같게
유지한다.

### 4.3 입장 규약

라이브러리에 들어오는 모든 항목이 지키는 두 규약. 조합의 자연스러움은 조합
단계가 아니라 이 규약이 만든다.

1. **스타일 변수화** — 색·타이포그래피·간격을 하드코딩하지 않고 CSS 변수로
   받는다. 조합 시점에 테마 하나를 주입하는 것만으로 서로 다른 출처의 항목들이
   통일감을 갖는다.
2. **구조 규약** — 컨테이너 최대 폭, 섹션 상하 여백 단위, 그리드 기준을 모든
   항목이 공유한다. 항목마다 다른 골격을 갖고 오면 경계마다 이음새가 보인다.
3. **배경 비소유** — 페이지 레벨 배경을 칠하지 않는다. 항목은 투명하게
   만들어지고, 필요한 표면 종류만 메타데이터로 선언한다. 배경은 조합기가
   칠한다(§6.3).

규약 준수 여부는 등록 시점에 검사한다. 구체 검사 항목은 미결정(§8)이다.

### 4.4 조달

세 채널에서 가져온다. **B와 C를 주력으로 하고, 부족한 것을 A로 채운다.**

| 채널 | 출발물 | 특징 |
|---|---|---|
| B. 오픈소스 이식 | 동작하는 원본 코드 | 사람 디자이너가 검증한 품질에서 출발한다. 라이선스 확인(MIT/Apache 계열만, 재배포 불가 유료 컬렉션 제외)과 정적 HTML/CSS·입장 규약으로의 재작성이 필요하다 — 실체는 "원본 확보 + AI 이식" |
| C. 시각 레퍼런스 기반 생성 | 큐레이션 갤러리의 스크린샷 | 잘 만든 웹 디자인을 수준·인상의 기준점으로 삼아 AI가 새 항목을 생성한다. 특정 사이트의 복제가 되지 않도록 구조는 새로 짠다 |
| A. 백지 생성 | 프롬프트만 | 라이선스 부담이 없고 종류 제한이 없다. 참조물 없이는 평범한 결과로 수렴하므로 보충용 |

채널은 셋이지만 생산 라인은 하나다. 어느 채널이든 마지막은 같다 — 규약에 맞는
HTML/CSS 산출 → 클래스 네임스페이스 변환 → 스크린샷 렌더 → description 작성 →
임베딩 → 등록. 네임스페이스 변환은 서로 다른 출처의 항목이 한 문서에서 클래스
이름으로 충돌하는 것(예: 오픈소스 이식품 둘이 모두 `.card`를 정의)을 등록
시점에 없애기 위한 것이다.

자산 종류별 기본 배정:

| 자산 | 채널 | 이유 |
|---|---|---|
| 모션 프리셋 | B 우선 | 오픈소스 생태가 성숙하고 MIT가 흔하다. 미학보다 동작 메커니즘의 정확성이 중요한 영역 |
| 구조 컴포넌트 | C 주력 + B 보조 | 미적 품질이 승부처라 시각 레퍼런스가 필요하다 |
| 테마 | C | 생성 자체는 쉽지만 취향의 기준점이 없으면 무난한 조합만 나온다 |

### 4.5 성장

처음부터 라이브러리를 채우려 하지 않는다. 종류별 소수의 변형으로 시작하고,
검색이 빈손으로 돌아온 지점을 다음 생산 주문으로 삼는다. 무엇을 만들어 둘지
미리 맞추는 대신 수요가 목록을 만든다.

## 5. 검색

### 5.1 질의와 호출 구조

질의는 자유 문장 하나가 아니라 세 부분의 합성이다 — **하드 필터**(항목 종류,
내용의 꼴), **인상 서술**(랭킹용), **맥락**(테마, 앞뒤에 오는 것).

호출 구조는 라인업 결정(§6.1)과 묶어 둘로 고정한다.

```text
계획 호출 1회 — 지면 전체의 섹션별 질의를 일괄 생성
  → 결정적 검색(§5.2)
  → 선택 호출 1회 — 모든 섹션의 후보를 한눈에 보고 라인업 전체를 결정
```

섹션 수와 무관하게 구조 선택에 드는 AI 호출은 2회다. 섹션마다 검색과 선택을
반복하지 않는다.

### 5.2 좁히기

세 단계로 좁힌다.

1. **메타데이터 필터** — 종류·용도·밀도 태그와 **내용의 꼴**로 후보를 좁힌다.
   슬롯 제약(항목 수 범위, 텍스트 길이 범위, 이미지 필수 여부)을 실제 내용과
   대조해, 내용과 맞지 않는 컴포넌트는 후보에 올라오지 않게 한다. 내용
   불일치(빈 그리드 칸, 오버플로, 늘어난 이미지)는 조합 단계에서 고치는 것보다
   검색 단계에서 거르는 것이 근본적이다.
2. **description 읽기** — AI가 필터 통과분의 description을 전부 읽고 눈 확인에
   올릴 후보를 압축한다. description은 텍스트라 수십 개를 읽어도 싸다.
3. **눈 확인** — 최종 소수 후보만 스크린샷으로 AI가 확인하고 결정한다.
   후보들을 라벨 붙여 한 이미지로 합성한 **컨택트 시트**로 보여 준다 — 이미지
   한 장 비용으로 후보 전체를 나란히 비교한다. 선택 시점에는 데스크톱 렌더만
   보고, 라인업 맥락은 이미지가 아니라 텍스트 요약으로 준다.

임베딩은 초기에는 두지 않는다. 필터 통과분을 전부 읽는 비용이 커지는
규모(수백)가 되면 2단계를 description 임베딩 랭킹으로 바꾼다. 서술 템플릿
규율(§4.2)을 첫날부터 지키면 임베딩을 나중에 얹을 때 description을 다시 쓸
일이 없다.

### 5.3 원칙

- 눈 확인은 항상 좁혀진 소수에만 쓴다. 이미지 입력은 비싸므로 라이브러리
  전체를 눈으로 훑지 않는다.
- raw HTML은 검색 신호로 쓰지 않는다. 코드 토큰은 랭킹에 잡음이 많고, 후보
  판단에는 스크린샷이 더 싸고 정확하다.
- 질의와 description은 같은 어휘 체계를 쓴다(§4.2).

## 6. 조합

### 6.1 결정 순서

선택은 페이지 전역 결정부터 진행한다.

```text
내용 파악 → 테마 → 구조 라인업 → 모션 문법 → 조합
```

- 테마를 먼저 정해야 구조 후보를 고를 때 그 테마와 어울리는지를 판단할 수
  있다.
- 구조 선택은 슬롯별 독립 선택이 아니라 **지면 단위의 라인업 결정**이다.
  리듬은 시퀀스의 속성이므로, AI는 후보 스크린샷을 놓고 앞뒤에 무엇이 오는지를
  보면서 한 벌을 고른다. 가운데 정렬 연속, 동일 밀도 연속처럼 어느 경계에도
  결함이 없는데 전체가 단조로워지는 문제를 여기서 막는다.
- 내용의 꼴은 검색 필터가 먼저 거른다(§5).

### 6.2 조합기의 일

조합기는 결정적 코드다. 하는 일은 다섯이다 — 항목 배열, 배경·수직 리듬 배정,
테마 변수 주입, 슬롯에 내용 주입, 모션 부착.

### 6.3 배경 소유권

컴포넌트는 페이지 레벨 배경을 소유하지 않는다(§4.3). 조합기가 항목들이 선언한
표면 요구를 보고 배경 교차 패턴과 섹션 간 수직 리듬을 배정한다. 인접 항목의
배경 충돌과 여백 중복 같은 경계 문제를 규칙으로 없앤다.

### 6.4 모션 문법

기본 모션(등장 애니메이션)은 페이지 전역 문법으로 하나를 골라 전 섹션에 일관
적용한다. 필요한 경우 섹션 단위 예외를 허용한다. 특정 섹션의 인터랙션은 국소
선택으로 남는다.

### 6.5 눈 확인과 수술적 수정

입장 규약(§4.3)과 위 규칙들이 통일감의 대부분을 만들고, 못 잡은 잔여 이음새는
AI가 조합 결과의 전체 스크린샷을 눈으로 확인해 수술적으로 고친다.

사전 렌더 스크린샷(중립 테마)과 실제 지면(선택된 테마)의 인상 차이는
받아들이고, 이 최종 눈 확인에서 잡는다. 테마 불일치가 실제로 잦아지면 최종
후보 소수를 선택된 테마로 재렌더해 보여 주는 옵션을 도입한다.

## 7. 편집

사용자가 요구하는 편집은 AI가 지면의 HTML을 직접 고친다 — 자유 패치. 편집을
제한된 연산 집합으로 한정하지 않는다. 사용자의 편집 요청은 열린 집합이라,
제한된 어휘로는 원하는 편집을 다 반영할 수 없기 때문이다.

편집된 지면의 검사 시점과 편집 이후 원본 관리는 미결정(§8)이다.

## 8. 미결정 사항

- 슬롯에 들어갈 내용(카피·이미지)의 출처와 작성 주체
- 구조 규약의 구체 값 — 컨테이너 폭, 여백 단위, 그리드 기준
- 표면 종류의 구체 분류와 배경 교차 패턴의 배정 규칙
- 등록 시점 검사의 구체 항목
- 임베딩 추가 시점의 모델과 저장 방식
- 눈 확인에 올리는 후보 수의 기본값
- 인상 어휘의 유한 태그 통제 여부와 태그 목록의 소유
- 눈 확인에서 후보가 전원 탈락했을 때의 처리 — 차선 채택 후 생산 주문
  기록인지, 그 자리에서 생산인지
- 라이브러리의 범위 — 전역 공유인지, 다른 단위인지
- 스크린샷 렌더 인프라
- 편집된 지면의 검사 시점과 원본 관리
- 채널 C에서 참조원으로 삼을 갤러리 목록과 참조 정책
