# 프론트엔드 아키텍처

## 출발점

Expresso 웹은 Next.js 16 App Router 단일 애플리케이션입니다. 앱 화면과 랜딩,
공개 포트폴리오 렌더러가 한 코드베이스에 있고, 렌더링 방식만 다릅니다.

```text
브라우저
    │
    ▼
services/web/src/app
    │
    ├── (auth)      셸 없는 화면 — 로그인 · 회원가입
    ├── (app)       앱 셸 화면 — 홈 · 내 커리어 · 공고 · 분석
    │
    ▼
services/web/src/lib/api
    │
    └── HTTP /v1 → services/backend
```

## 왜 Next.js인가

구현 명세서 §12는 공개 포트폴리오에 LCP 1.5초 미만을 요구합니다. 공개 포트폴리오는
배포마다 내용이 고정된 스냅샷이므로 정적 생성이 자연스럽고, `{slug}.xpresso.me`
서브도메인 라우팅도 같은 애플리케이션에서 처리할 수 있습니다. 앱 화면은 서버
컴포넌트로 첫 페이로드를 줄여 TTI 2.5초 목표에 맞춥니다.

## 경계

- `app/(auth)`: 앱 셸이 없는 화면. 세션이 없어도 열린다
- `app/(app)`: 앱 셸 화면. `requireSession()`이 세션과 카테고리를 함께 가져온다
- `components/shell`: 셸 3종(앱 · 위저드 · 에디터)과 사이드바
- `components/ui`: 구현 명세서 §5 컴포넌트. 도메인을 모른다
- `lib/api`: 계약 기반 HTTP 클라이언트. 모든 응답을 Zod로 검증한다
- `styles/tokens.css`: 디자인 토큰의 유일한 출처

UI 컴포넌트는 도메인 타입을 알지 않습니다. 화면이 도메인 데이터를 UI 속성으로
바꿔서 넘깁니다.

## 계약

`packages/contracts`의 Zod 스키마를 백엔드와 프론트엔드가 함께 씁니다. 응답은
`lib/api/client.ts`에서 파싱하므로, 백엔드가 계약을 어기면 화면이 잘못 그려지는
대신 그 자리에서 실패합니다. 타입은 스키마에서 파생하고 손으로 적지 않습니다.

## 세션

세션 토큰은 `httpOnly` 쿠키 하나(`ex_session`)에만 둡니다. 클라이언트
자바스크립트가 읽을 수 없으므로 XSS로 토큰이 새어 나가지 않습니다. 로그인·가입·
로그아웃은 서버 액션이며, 토큰은 브라우저로 내려가지 않습니다.

## 토큰과 스타일

CSS Modules와 `--ex-*` CSS 변수를 씁니다. 유틸리티 프레임워크를 쓰지 않는 이유는
명세가 "표에 없는 색·크기를 새로 만들지 않는다"를 규칙으로 두기 때문입니다. 변수
목록이 곧 허용 목록이 되므로 이탈이 코드 리뷰가 아니라 파일 하나에서 드러납니다.

## 구현 순서

구현 명세서 §14.1의 마일스톤을 따릅니다.

| M6 | 분석 07–07c · 요금제 | 미착수 |
