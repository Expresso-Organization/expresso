# MongoDB 기반 백엔드 마이그레이션 설계

작성일: 2026-08-28

상태: 대화에서 승인한 설계의 문서화. 구현과 운영 전환은 아직 진행하지 않았습니다.

구현 순서와 검증은 [구현 계획](mongodb-migration-plan.md)에, 테이블별 저장 위치는 [컬렉션 대응표](mongodb-collection-map.md)에 기록합니다.

## 목적과 작업 구분

Expresso의 영속 저장소를 MySQL에서 MongoDB로 전면 이전합니다. 기존 API와 제품 기능을 유지하면서, 후속 커리어 기록 편집기가 문서 중심의 저장 구조를 사용할 수 있도록 준비합니다.

작업은 다음 두 개로 나눕니다. 이 문서는 첫 번째 작업의 설계입니다.

| 작업 | 결과 | 완료 경계 |
| --- | --- | --- |
| MongoDB 기반 백엔드 마이그레이션 | 모든 백엔드 도메인의 MongoDB 전환, 공고 자산 이관, 운영 절차 교체 | 현재 웹과 API가 MongoDB만으로 동작합니다. |
| 커리어 기록 편집기 구현 | 제목·프로퍼티·블록 본문, 카테고리별 뷰, 관계·수식·롤업, 내부 AI와의 편집 협업 | 별도 설계와 구현으로 진행합니다. |

현재 MySQL에도 카테고리 정의와 기록의 프로퍼티를 JSON으로 저장하는 구조가 있습니다. 카테고리마다 테이블을 추가해야 하는 구조는 아닙니다. 이번 결정은 RDB에서 해당 기능이 불가능해서가 아니라, 앞으로 사용할 문서 모델에 저장소와 접근 방식을 맞추기 위한 선택입니다.

MongoDB의 저장 형식은 BSON입니다. API와 AI에는 필요한 필드를 JSON으로 변환해 전달합니다. 저장소 변경만으로 AI 컨텍스트의 품질이나 조회 성능이 좋아진다고 가정하지 않습니다.

## 확정 사항

| 항목 | 결정 |
| --- | --- |
| 이전 범위 | 커리어 기록만이 아니라 백엔드 전체를 이전합니다. |
| 접근 방식 | 공식 MongoDB Node.js 드라이버를 사용합니다. Mongoose와 SQL 호환 계층은 도입하지 않습니다. |
| 계약 | `packages/contracts`의 Zod 계약, UUID, 응답 형식을 유지합니다. |
| 스키마 소유권 | 컬렉션·인덱스·검증 규칙·마이그레이션은 `packages/database`가 소유합니다. |
| 실행 환경 | 기존 Oracle Cloud 서버에서 인증을 설정한 단일 노드 replica set으로 시작합니다. |
| 다른 인프라 | Redis/BullMQ와 파일·객체 저장소를 유지합니다. |
| 데이터 보존 | 수집한 공고와 공고에 붙은 공통 분석 결과를 보존합니다. 사용자 데이터는 초기화합니다. |
| 중단 시간 | 제한을 두지 않습니다. 쓰기를 중단한 상태에서 일괄 이관합니다. |
| 큐 전환 | Expresso 작업 큐에 새 prefix를 적용합니다. 이전 작업을 새 저장소에서 실행하지 않습니다. |
| 기존 편집 기능 | 첫 번째 작업에서는 현재 `bodyMd` 계약을 유지합니다. |

## 구조와 책임

Fastify API와 BullMQ Worker는 계속 별도 프로세스로 실행합니다. 두 프로세스는 같은 도메인 코드와 MongoDB 연결 계층을 사용합니다. 모듈을 별도 서비스로 분리하지 않습니다.

| 위치 | 이전 후 책임 |
| --- | --- |
| `packages/contracts` | 요청·응답의 Zod 스키마와 파생 타입을 제공합니다. 저장소 전용 타입을 API로 노출하지 않습니다. |
| `packages/database` | 저장 문서의 타입, 컬렉션 정의, 인덱스, 검증 규칙, 버전별 마이그레이션을 관리합니다. |
| `services/backend/src/platform` | MongoDB 연결·종료·상태 검사와 공통 트랜잭션·outbox 기반을 제공합니다. |
| `services/backend/src/modules/*` | 각 도메인의 조회·변경과 업무 규칙을 구현합니다. |
| API·Worker 조립 코드 | 같은 설정으로 저장소를 연결하고 각 모듈에 전달합니다. |

모듈은 다른 모듈의 내부 파일을 직접 가져오지 않습니다. 필요한 기능은 모듈의 진입점으로 노출합니다. SQL 호출을 흉내 내는 범용 어댑터를 만들지 않고, 도메인별 조회와 변경을 MongoDB에 맞게 작성합니다.

세션 토큰은 기존과 같이 `httpOnly` 쿠키 `ex_session`에만 둡니다. 인증 방식이나 AI 호출의 기본값 `off`는 이번 작업에서 바꾸지 않습니다.

## 저장 모델

### 문서와 참조의 경계

사용자나 카테고리마다 컬렉션을 만들지 않습니다. 같은 종류의 데이터를 컬렉션에 모으고 소유자와 카테고리 식별자로 구분합니다. 카테고리 정의, 기록, 저장된 뷰는 서로 다른 수명과 조회 경로를 갖는 문서로 관리합니다.

함께 읽고 수정하며 크기가 제한된 값은 문서 안에 포함합니다. 독립적으로 수정하거나 여러 곳에서 참조하는 데이터는 별도 문서로 둡니다. 이력·이벤트·작업처럼 계속 늘어나는 데이터를 부모 문서의 배열에 누적하지 않습니다. 이는 MongoDB의 [데이터 모델링 지침](https://www.mongodb.com/docs/manual/data-modeling/best-practices/)에 따른 구분입니다.

기존 UUID는 문자열 식별자로 유지합니다. 내부 `_id`에 UUID 문자열을 사용하고, API 경계에서는 기존 `id` 필드로 반환합니다. ObjectId나 BSON 전용 값을 응답에 그대로 노출하지 않습니다.

날짜·시간대·소수 정밀도·누락 필드와 `null`의 차이를 필드별로 정리합니다. SQL의 대소문자 비교와 nullable unique 제약도 MongoDB에서 자동으로 같아진다고 가정하지 않습니다. 저장 형식이 달라져도 응답과 업무 규칙은 유지합니다.

### 도메인별 이전 대상

아래 표는 이전 범위입니다. 최종 컬렉션 이름과 포함·참조 관계는 구현 계획에서 기존 테이블별로 대응시킵니다. 테이블을 무조건 같은 수의 컬렉션으로 복제하지 않습니다.

| 영역 | 주요 데이터와 경계 |
| --- | --- |
| 계정·권한 | 사용자, OAuth 연결, 세션, 동의, 플랜·사용량, 계정 삭제 절차를 이전합니다. |
| 커리어 | 카테고리 정의, 기록, 뷰, 기록 간 연결, 프로필, 스킬·근거를 이전합니다. 현재 본문은 `bodyMd`로 제공합니다. |
| 공고·분석 | 출처, 회사, 공고, 요구사항·출처 구간을 보존합니다. 사용자별 분석·매칭·관심·검색 데이터는 새 저장소에서 다시 생성합니다. |
| 인터뷰·생성 | 인터뷰, 답변, brew, 입력 자료, recipe, 생성 작업·사용량 차감을 이전합니다. |
| 포트폴리오·배포 | 섹션, 블록, 레이아웃, 편집 제안, 개정 이력, 스냅샷, 배포·내보내기 기능을 이전합니다. |
| 미디어·운영 | 미디어 메타데이터, 알림, 방문·전환 집계, 대시보드, 예약 작업, outbox를 이전합니다. |

기능을 이전하는 것과 과거 데이터를 보존하는 것은 다릅니다. 계정이나 포트폴리오의 기존 행을 이관하지 않아도, 해당 기능은 MongoDB에서 동작해야 합니다.

### 검증 규칙과 인덱스

API 입력은 Zod 계약으로 검증합니다. 저장 문서의 필수 필드와 기본 타입은 MongoDB 검증 규칙으로 확인합니다. 소유권, 참조 대상의 상태, 카테고리별 프로퍼티 규칙은 도메인 코드에서 검증합니다.

인덱스는 실제 조회와 업무 제약을 기준으로 정의합니다. 소유자별 목록·정렬, 고유 식별자, 멱등성 키, 큐 작업 조회, 만료·삭제 대상 조회를 포함합니다. nullable 필드의 고유성에는 기존 의미에 맞는 조건부 인덱스를 사용합니다.

컬렉션·인덱스·검증 규칙은 `pnpm db:migrate`에서 적용합니다. API와 Worker가 시작될 때 자동 생성하거나 수정하지 않습니다.

## 정합성과 동시성

MySQL의 외래 키·트리거·잠금이 담당하던 규칙을 목록으로 만들고, 각 규칙의 새 구현 위치와 테스트를 대응시킵니다. 스키마 파일만 옮기고 트리거의 동작을 빠뜨리지 않습니다.

| 기존 보장 | MongoDB에서 유지할 방식 |
| --- | --- |
| 사용자 간 데이터 격리 | 조회·수정 조건에 소유자를 포함하고, 참조 연결 시 양쪽 소유권을 검증합니다. |
| 카테고리·프로퍼티 규칙 | 정의와 값을 함께 검증합니다. 사용 중인 프로퍼티 제거와 잘못된 타입 저장을 막습니다. |
| 기록 편집 충돌 | `expectedVersion`을 포함한 조건부 변경을 사용합니다. 충돌 시 기존 계약의 오류를 반환합니다. |
| 인용된 기록의 삭제 제한 | 인용 추가와 기록 삭제가 경쟁해도 제한을 우회하지 못하도록 공통 문서의 버전 변경 또는 동등한 쓰기 충돌 장치를 둡니다. |
| 공고 원문·출처 구간 | 원문의 불변성과 인용 구간의 일치를 검증합니다. 원문을 다시 생성하거나 재분석해 대체하지 않습니다. |
| 공개 스냅샷 | 발행된 내용의 불변성과 포트폴리오·배포 간 참조 일치를 유지합니다. |
| 생성 결과·사용량 | 결과 저장, 사용량 기록, 작업 상태 등 함께 확정할 변경을 트랜잭션으로 묶습니다. |
| 중복 요청·작업 재시도 | 고유 인덱스와 조건부 상태 전이로 중복 생성·중복 차감을 막습니다. |
| 삭제·만료 | 기존 삭제 제한과 연관 데이터 정리를 유지합니다. TTL 삭제만으로 연쇄 정리를 대신하지 않습니다. |
| 개수·빈도 제한 | 기존 대시보드 개수 제한과 이벤트 빈도 제한을 원자적 변경 또는 동시성 제어로 유지합니다. |

여러 문서의 상태가 함께 바뀌어야 하면 트랜잭션을 사용합니다. 단일 문서 변경은 원자적 조건부 갱신을 우선합니다. 트랜잭션 안에서 참조를 읽기만 하는 것으로 경쟁 상황이 모두 해결되지는 않습니다. 삭제·인용·한도 검사처럼 같은 제약을 공유하는 변경은 서로 충돌할 수 있도록 설계하고 병렬 요청으로 검증합니다.

트랜잭션 재시도 중 AI 호출, 파일 쓰기, 큐 발행 같은 외부 부작용을 반복하지 않습니다. 외부 작업은 트랜잭션 밖에서 수행하고 상태 전이와 멱등성 키로 연결합니다.

### Outbox와 작업 큐

Outbox는 도메인 변경과 함께 저장하는 발행 대기 이벤트입니다. DB 저장과 큐 발행 사이에서 이벤트가 유실되지 않도록 유지합니다.

도메인 변경과 outbox 추가를 같은 트랜잭션으로 확정합니다. 발행기는 원자적 조건부 갱신으로 이벤트를 점유하고, 점유 만료 시 다른 발행기가 재시도할 수 있게 합니다. 발행 후 상태 저장에 실패하면 중복 전달이 생길 수 있으므로 소비자도 멱등하게 처리합니다. 정확히 한 번의 전달을 보장한다고 표현하지 않습니다.

## 이관 데이터

### 보존 대상

| 현재 MySQL 데이터 | 보존 내용 |
| --- | --- |
| `job_source` | 수집 출처, 식별자, 수집에 필요한 설정·상태를 보존합니다. |
| `company` | 회사 식별자와 공통 메타데이터를 보존합니다. |
| `job_posting` | 공고 원문, 수집 메타데이터, 정규화·추출 결과, 분석 시점과 관련 필드를 보존합니다. |
| `job_posting_requirement` | 요구사항, 분류, 출처 구간, 추출기 버전과 추출 시점을 보존합니다. |

여기서 보존하는 분석 결과는 공고에 붙은 공통 결과입니다. 사용자별 적합도나 커리어 기록을 입력으로 만든 결과와 구분합니다. 이미 분석된 공고를 AI에 다시 보내서 복원하지 않습니다.

식별자와 참조 관계를 유지합니다. 회사 로고 등 보존 데이터가 참조하는 파일도 확인합니다. 사용자 데이터 초기화를 이유로 공용 파일 저장소 전체를 삭제하지 않습니다.

### 초기화 대상

계정·세션, 사용자 커리어 기록, 사용자별 `job_analysis`·`job_analysis_history`·`match_score`·`requirement_coverage`, 인터뷰·생성 작업 이력, 생성된 포트폴리오·레이아웃·HTML·CSS·배포 데이터를 이관하지 않습니다. 기존 사용자는 새 환경에서 다시 가입해야 합니다.

플랜·템플릿 등 기능에 필요한 공통 초기 데이터는 마이그레이션과 seed로 준비합니다. 사용자 데이터와 분리해 반복 실행해도 중복되지 않도록 합니다.

### 이관 도구와 검증

기존 `scripts/operations/copy-job-postings.mjs`는 PostgreSQL에서 MySQL로 복사하는 도구입니다. 보존 대상 파악에 참고하되 그대로 재사용하지 않습니다.

새 이관 도구는 원본을 읽기 전용으로 접근합니다. 필드별 대응을 명시하고 기존 식별자로 재실행할 수 있게 합니다. 모르는 필드나 변환 실패를 조용히 버리지 않습니다. 부분 성공을 완료로 처리하지 않고 실패 항목과 재시작 지점을 기록합니다.

검증 보고서에는 다음 결과를 남깁니다.

- 출처·회사·공고·요구사항별 건수와 식별자 집합을 비교합니다.
- 원문과 분석 필드는 표현 차이를 정규화한 뒤 값 또는 해시를 비교합니다.
- 공고·회사·출처·요구사항 사이의 참조 누락을 검사합니다.
- 원문에서 요구사항의 출처 구간이 여전히 일치하는지 확인합니다.
- 날짜, 빈 배열, `null`, 다국어 원문, 긴 본문의 변환을 확인합니다.
- 같은 입력을 다시 이관해도 중복이나 내용 변화가 없는지 확인합니다.

## 실행 환경과 마이그레이션

### MongoDB 운영 구성

기존 Oracle Cloud 서버에 인증을 설정한 단일 노드 replica set을 구성합니다. MongoDB의 다중 문서 트랜잭션은 standalone에서 지원되지 않으므로 replica set으로 실행합니다. [트랜잭션 운영 조건](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/)과 [replica set 전환 절차](https://www.mongodb.com/docs/manual/tutorial/convert-standalone-to-replica-set/)를 기준으로 설정합니다.

단일 노드는 트랜잭션을 사용할 수 있는 시작 구성이며, 서버 장애 시 자동으로 전환할 다른 노드가 없습니다. 데이터 복제에 의한 고가용성을 제공하지 않는다는 제한을 수용합니다. 서버와 분리된 위치의 백업과 복원 검증이 필요합니다.

DB 포트는 외부에 공개하지 않습니다. 호스트에는 loopback으로만 노출하고, 컨테이너 간 연결은 내부 네트워크로 제한합니다. 런타임 계정과 스키마 변경 계정을 분리하고 replica set 인증용 비밀값을 저장소에 넣지 않습니다. 연결 문자열의 호스트 이름은 API·Worker·마이그레이션 실행 위치 모두에서 접근 가능해야 합니다.

Replica set 초기화와 인증 설정은 인프라 준비 절차가 담당합니다. `pnpm db:migrate`는 준비된 DB에 애플리케이션 스키마를 적용합니다. 트랜잭션의 읽기·쓰기 보장과 내구성 설정을 명시하고, 개발·CI·운영에서 같은 동작을 검증합니다.

### 스키마 변경 절차

마이그레이션 실행 이력에 버전·이름·체크섬·적용 시점을 기록합니다. 이미 적용한 마이그레이션의 내용을 바꾸면 중단합니다. 동시에 두 실행자가 스키마를 바꾸지 못하도록 점유와 만료 처리를 둡니다. 점유권을 잃은 실행자는 계속 진행하지 않습니다.

컬렉션 생성, 검증 규칙 변경, 인덱스 생성, seed를 재실행 가능한 단계로 나눕니다. 모든 관리 명령을 하나의 트랜잭션으로 되돌릴 수 있다고 가정하지 않습니다. 중간 실패 시 완료 단계와 실패 원인을 남기고, 중복 데이터로 고유 인덱스를 만들 수 없다면 원인을 해결하기 전까지 배포를 중단합니다.

MongoDB 서버·드라이버 버전과 이미지 태그는 구현 시 호환성을 확인해 고정합니다. 마이그레이션 실행 계정 외에는 인덱스나 검증 규칙을 수정하지 않습니다.

## 전환과 복구

### 운영 전환 순서

1. 운영과 같은 구성에서 이관·검증·복원 절차를 리허설합니다.
2. API, Worker, 수집기와 예약 실행 등 모든 쓰기 경로를 중단합니다. 실행 중 작업을 종료하거나 중단 상태로 확정합니다.
3. MySQL 데이터, 필요한 파일, Redis의 기존 작업 상태와 기존 배포 설정을 백업합니다. 백업을 복원할 수 있는지 확인합니다.
4. 새 MongoDB를 준비하고 스키마 마이그레이션과 공통 seed를 실행합니다.
5. 보존 대상 데이터를 이관하고 검증 보고서를 확인합니다. 불일치가 있으면 전환을 중단합니다.
6. API·Worker·발행기·예약 작업의 DB 설정과 BullMQ prefix를 함께 변경합니다. 이전 큐의 소비자와 예약 발행기가 남아 있지 않은지 확인합니다.
7. 검증용 계정으로 공고 조회, 신규 가입, 기록 생성, 생성 작업, 배포를 점검합니다. 실제 사용자 쓰기는 막아 둡니다. 기존 배포 URL은 과거 사용자 데이터 초기화에 따라 더 이상 제공하지 않습니다.
8. 실제 사용자 쓰기를 허용하고 수집·예약 작업을 재개합니다. 수집기가 기존 공고를 중복 생성하지 않는지 확인합니다.

Redis 전체를 비우지 않습니다. 이전 큐는 복구를 위해 남겨 두되 새 소비자가 읽지 않게 합니다. 새 큐에서 참조하는 작업·계정은 모두 MongoDB에 있어야 합니다. 만료 여부와 관계없이 이전 환경의 세션은 새 환경에서 인증되지 않아야 합니다.

### 복구 경계

MongoDB에서 검증 데이터 외의 새 쓰기를 받기 전에는 기존 애플리케이션, MySQL, 이전 큐 설정을 함께 복원할 수 있습니다. 이때 새 MongoDB와 새 큐를 사용하는 프로세스는 먼저 중단합니다.

새 쓰기를 받은 뒤에는 MySQL로 설정만 되돌리면 새 계정·기록·생성 결과가 사라집니다. 이 상태의 자동 롤백은 제공하지 않습니다. 쓰기를 중단하고 MongoDB의 새 데이터를 보존한 뒤, MongoDB 복원이나 전진 수정으로 복구합니다. MySQL 복귀가 필요하면 새 데이터를 옮기는 별도 절차와 데이터 손실 여부를 먼저 결정해야 합니다.

이전 MySQL 데이터와 볼륨은 전환·복원 검증이 끝날 때까지 보존합니다. 폐기 여부는 별도로 확인합니다. 새 환경의 백업에는 MongoDB뿐 아니라 필요한 파일과 큐의 복구 절차도 포함합니다.

## 검증과 완료 기준

문서 작성 완료와 마이그레이션 완료를 구분합니다. 아래 항목은 이후 구현의 완료 기준입니다.

### 기능과 정합성

- 모든 SQL 접근 지점을 도메인별로 대응시킵니다. API·Worker의 런타임에 MySQL 연결과 SQL 실행이 남지 않아야 합니다.
- 기존 API의 성공·오류 계약, UUID, 페이지네이션, 정렬, 검색과 필터 집계가 유지되어야 합니다. MongoDB의 기본 비교 규칙으로 달라진 결과를 허용하지 않습니다.
- 소유권, 프로퍼티 검증, 출처 구간, 스냅샷 불변성, 삭제 제한, 사용량 차감과 계정 삭제를 실제 DB로 검증합니다.
- 같은 기록의 동시 수정, 인용 추가와 삭제의 경쟁, 작업 중복 처리, 트랜잭션 재시도, outbox 재발행과 점유 만료를 테스트합니다.
- 기존 웹이 새 편집기 없이 MongoDB 백엔드에서 동작해야 합니다. 대표 사용자 흐름을 직접 점검합니다.

### 자동 검사와 운영 검증

계약과 데이터베이스 패키지를 먼저 빌드합니다. 테스트가 두 패키지의 `dist`를 참조하는 현재 순서를 유지합니다.

```bash
pnpm --filter @expresso/contracts build
pnpm --filter @expresso/database build
pnpm db:migrate
pnpm typecheck
pnpm test
pnpm test:infra
pnpm --filter @expresso/backend test:load
pnpm build
```

이 명령들은 MongoDB용 환경과 스크립트로 전환한 뒤 실행할 검증 순서입니다. 현재 저장소에서는 여전히 MySQL을 사용합니다. 통합 테스트와 성능 테스트는 실제 MongoDB replica set과 Redis를 사용합니다. 가짜 저장소를 쓰는 단위 테스트만으로 완료하지 않습니다.

성능 기준은 [성능 예산](../operations/PERFORMANCE_BUDGET.md)을 유지합니다. 공고 검색·필터 집계, 기록 목록, 생성 결과 저장, 큐 등록을 같은 데이터 규모와 조건에서 비교하고 인덱스 사용을 확인합니다. 작은 데이터에서의 통과를 운영 규모의 보장으로 해석하지 않습니다.

CI, 개발용 Compose, 서버용 Compose, 환경변수 예시, 배포 스크립트, README와 에이전트 지침을 함께 갱신합니다. [배포](../operations/DEPLOYMENT.md), [백업·복원](../operations/BACKUP_AND_RESTORE.md), [복구 리허설](../operations/RECOVERY_REHEARSAL.md)도 MongoDB 기준으로 바꿉니다. 연결 실패 시 readiness 검사와 배포 중단 동작을 검증합니다.

이관 검증 보고서와 복원 리허설 결과를 남겨야 완료입니다. 실데이터 전환이나 복원 검증을 수행하지 못했다면 코드 이전과 운영 전환의 상태를 나누어 보고합니다.

## 후속 편집기와의 경계

후속 작업은 문서 하나가 카테고리 하나에 속하는 모델을 사용합니다. 제목·프로퍼티·본문을 공통 형식으로 두고 카테고리와 뷰를 달리합니다. 기본 카테고리는 사용자가 수정할 수 있는 시작 템플릿입니다. 관계형 프로퍼티·수식·롤업과 내부 AI 에이전트의 실시간 편집을 별도 작업에서 구현합니다.

편집기는 MIT Tiptap 기반으로 독립 구현합니다. [SynapseNote](https://github.com/Nedian0Brien/SynapseNote)의 사용자 작성 데이터베이스 로직은 출처와 의존성을 확인해 선별 이식합니다. GPL 편집기 코드를 가져오는 것으로 해석하지 않습니다.

협업 상태는 Yjs의 영속 바이너리를 기준으로 삼고 같은 버전의 블록 JSON을 조회·검색·AI용으로 제공합니다. 두 표현을 독립적으로 수정하지 않습니다. AI와 사용자 변경은 같은 경로를 거치며, 오래된 문맥에 대한 AI 변경은 다시 검증합니다. 자동 저장, AI 변경 표시와 되돌리기도 포함합니다. 이 저장·동기화 구조는 두 번째 작업에서 구현합니다.

사람 사이의 다중 사용자 협업은 제품 범위 밖입니다. 외부 에이전트용 MCP/API 연동도 별개 기능입니다. 카테고리 삭제·복원 정책은 아직 확정하지 않았으며, 이번 마이그레이션에서 기존 기록 삭제 정책을 임의로 바꾸지 않습니다.
