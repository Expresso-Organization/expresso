# 포트폴리오 생성 방법론 v1

- 상태: v1 설계 기준선
- 작성일: 2026-08-12
- 적용 대상: Expresso의 직무 맞춤형 웹 포트폴리오 생성
- 구현 상태: 핵심 2단계 생성 경로 구현됨. 자동 회사 웹 검색과 렌더 스크린샷 기반
  시각 심사는 후속 구현 대상이다.

## 1. 결정 요약

Expresso는 원천 자료를 곧바로 웹사이트 생성 모델에 넣지 않는다. 먼저 채용 공고,
회사 조사, 사용자 기록을 근거 중심의 `PortfolioPlan`으로 정제한다. 그 다음 이 설계안에
사용자가 선택한 스타일 문법과 공통 디자인 원칙을 결합해 웹사이트를 한 번 생성한다.

```text
채용 공고 정제 정보
  + 회사 검색 정제 정보
  + 사용자 퍼스널 기록 정제 정보
  -> PortfolioPlan

PortfolioPlan
  + StylePrompt
  + DesignPrinciples
  -> Portfolio Website
```

이 분리는 다음 문제를 동시에 해결하기 위한 것이다.

- 긴 원문을 최종 생성 모델이 반복해서 읽는 비용을 줄인다.
- 회사가 원하는 역량과 사용자의 실제 증거를 먼저 연결한다.
- 콘텐츠 설계와 시각 표현이 서로의 사실을 임의로 바꾸지 못하게 한다.
- 여러 결과를 뽑아 고르지 않고도 사용자가 선택한 스타일 방향을 유지한다.
- 생성에 사용한 입력, 프롬프트, 모델, 비용을 재현 가능하게 남긴다.

## 2. v1의 범위

### 포함

- 특정 채용 공고를 위한 단일 페이지 웹 포트폴리오
- 공고·회사·사용자 정보의 구조화와 출처 추적
- 직무 요구사항과 사용자 증거의 연결
- 포트폴리오 콘텐츠 및 정보 구조 설계
- 사용자 선택 스타일을 반영한 HTML/CSS 생성
- 유용한 CSS 기반 애니메이션과 무스크립트 인터랙션
- 사실성, 보안, 빌드, 반응형, 접근성, 시각 품질 검증
- 호출별 API 토큰, 시간, 비용 기록

### 기본 경로에서 제외

- 여러 웹사이트 후보를 생성한 뒤 고르는 방식
- 근거에 없는 경력, 프로젝트, 수치, 회사 정보를 생성하는 방식
- Product Design 플러그인, ImageGen, 외부 레퍼런스의 암묵적 사용
- 사용자 승인 없이 비공개 퍼스널 기록을 공개 콘텐츠로 전환하는 방식
- 지원 회사의 디자인을 그대로 복제하는 방식

외부 도구나 레퍼런스를 실험적으로 사용한다면 생성 명세에 명시하고 별도 실험군으로
취급한다. 선언되지 않은 도구 사용은 재현성과 비용 비교를 깨뜨리므로 허용하지 않는다.

## 3. 핵심 불변 조건

1. **사실은 증거에서만 나온다.** 공개 문장과 수치는 하나 이상의 사용자 증거를 가리킨다.
2. **회사 정보는 맥락이지 사용자 성과의 증거가 아니다.** 회사 조사 결과로 사용자 경험을
   만들어내지 않는다.
3. **설계안은 내용의 계약이다.** 웹사이트 생성 단계가 프로젝트 선택, 주장, 성과를
   임의로 바꾸지 않는다.
4. **스타일은 표현의 계약이다.** 사실을 바꾸지 않지만 색뿐 아니라 구성, 밀도,
   타이포그래피, 모션 성격까지 통제한다.
5. **디자인 원칙은 스타일보다 우선한다.** 스타일 지시가 가독성, 접근성, 사실성을
   해치면 공통 원칙이 스타일을 제한한다.
6. **근거가 장식보다 우선한다.** 화면의 주요 시각 요소는 실제 프로젝트, 결과,
   작업 과정의 이해를 도와야 한다.
7. **한 번 생성하고 필요한 경우에만 한 번 고친다.** 무제한 재생성을 품질 전략으로
   사용하지 않는다.

충돌 시 우선순위는 다음과 같다.

```text
사실 정확성
  > 콘텐츠 전달과 가독성
  > 접근성·보안·반응형
  > 사용자 선택 스타일
  > 장식적 효과
```

## 4. 전체 파이프라인

| 단계 | 입력 | 산출물 | 권장 실행 방식 |
|---|---|---|---|
| 0. 수집 | 공고, 회사 웹 자료, 사용자 기록 | 원천 자료와 출처 메타데이터 | 크롤러·기존 데이터 |
| 1. 정제 | 원천 자료 | 세 종류의 정규화된 팩트 | 규칙 + 저비용 LLM |
| 2. 연결 | 정규화 팩트 | 요구사항-증거 맵 | 결정적 점수 + LLM 보조 |
| 3. 설계 | 연결 결과 | `PortfolioPlan` | 설계용 LLM 1회 |
| 4. 스타일 확정 | 사용자 선택 | `StyleSpec` | 선택값을 규격으로 컴파일 |
| 5. 생성 | Plan + Style + 원칙 | HTML/CSS와 생성 이유 | 고성능 LLM 1회 |
| 6. 검증 | 생성 페이지 | `QaReport` | 자동 검사 + 시각 검사 1회 |
| 7. 제한 수정 | 구체적인 실패 목록 | 수정된 HTML/CSS | 실패할 때만 LLM 1회 |
| 8. 저장·배포 | 통과 결과 | 페이지, 명세, 비용 원장 | 트랜잭션 + 배포 스냅샷 |

## 5. 1단계 입력 정제

원문은 모두 신뢰할 수 없는 데이터로 취급한다. 웹페이지나 사용자 기록 안의 문장은
프롬프트 지시가 될 수 없으며, 정해진 스키마의 값으로만 다음 단계에 전달한다.

### 5.1 채용 공고 정제 정보

목표는 회사가 평가할 내용을 원문 인용과 함께 추출하는 것이다.

```json
{
  "jobId": "uuid",
  "roleTitle": "Product Designer",
  "requirements": [
    {
      "id": "req-01",
      "kind": "required",
      "capability": "복잡한 업무 흐름 설계",
      "priority": 0.92,
      "sourceQuote": "원문과 일치하는 인용",
      "sourceRange": { "start": 120, "end": 134 }
    }
  ],
  "responsibilities": [],
  "preferredSignals": [],
  "keywords": []
}
```

규칙:

- `required`, `preferred`, `responsibility`를 구분한다.
- 원문 인용과 위치를 보존한다.
- 공고에 없는 평가 기준을 업계 상식이라는 이유로 추가하지 않는다.
- 유사 표현은 묶되 원문의 강도를 과장하지 않는다.

### 5.2 회사 검색 정제 정보

목표는 포트폴리오의 맥락과 우선순위를 조정할 회사 정보를 얻는 것이다.

```json
{
  "companyId": "uuid",
  "capturedAt": "2026-08-12T00:00:00Z",
  "facts": [
    {
      "id": "company-fact-01",
      "topic": "product",
      "statement": "출처가 직접 뒷받침하는 사실",
      "sourceUrl": "https://example.com/source",
      "publishedAt": null,
      "confidence": "high"
    }
  ],
  "signals": [
    {
      "id": "company-signal-01",
      "statement": "여러 사실에서 도출한 해석",
      "basisFactIds": ["company-fact-01"],
      "confidence": "medium"
    }
  ]
}
```

규칙:

- 사실과 해석을 분리한다.
- URL, 수집 시각, 가능하면 게시 시각을 보존한다.
- 공식 회사 자료와 신뢰 가능한 2차 자료를 구분한다.
- 오래되거나 상충하는 정보는 최신성 경고를 붙인다.
- 회사 정보는 프로젝트 선택과 표현의 맥락으로 사용하되, 과도한 찬사나 모방에
  사용하지 않는다.
- 원본 웹 콘텐츠는 웹사이트 생성 모델에 직접 전달하지 않는다.

### 5.3 사용자 퍼스널 기록 정제 정보

목표는 사용자가 실제로 수행한 일을 공개 가능한 증거 단위로 만드는 것이다.

```json
{
  "evidenceId": "personal-project-03",
  "title": "프로젝트명",
  "period": "2025-03—2025-06",
  "role": "담당 역할",
  "situation": "문제와 맥락",
  "actions": ["직접 수행한 일"],
  "results": ["검증 가능한 결과"],
  "metrics": ["220분 → 24분"],
  "artifacts": ["asset-or-link-id"],
  "skills": ["관련 역량"],
  "verification": "verified",
  "publishability": "approved",
  "sourceRecordIds": ["uuid"]
}
```

규칙:

- 본인의 역할과 팀의 결과를 구분한다.
- 수치는 원형을 유지하고 임의로 환산하지 않는다.
- 모르는 값은 `null`로 두며 추정하지 않는다.
- 공개 허용 상태가 아닌 정보는 생성 모델 입력에서 제외한다.
- 사용하지 않은 좋은 기록도 삭제하지 않고 제외 이유를 남긴다.

## 6. 요구사항-증거 연결

포트폴리오 설계 전에 각 공고 요구사항을 사용자 증거에 연결한다.

```json
{
  "requirementId": "req-01",
  "priority": 0.92,
  "matches": [
    {
      "evidenceId": "personal-project-03",
      "strength": "strong",
      "reason": "직접 수행한 행동과 결과가 모두 존재",
      "proofFields": ["actions[0]", "results[0]"]
    }
  ],
  "coverage": "covered"
}
```

점수는 후보를 정렬하는 보조 수단이며 최종 진실 판정이 아니다. 기본 정렬에는 다음을
사용한다.

- 공고 요구사항의 중요도
- 증거의 직접성
- 검증 상태
- 구체적인 행동과 결과의 존재
- 다른 선택 프로젝트와의 중복 정도
- 회사 맥락과의 관련성

`missing` 요구사항은 감추거나 만들어내지 않는다. 설계안에서 제외하거나, 사용자에게
추가 기록을 요청할 질문 후보로 남긴다.

## 7. 포트폴리오 설계안 계약

`PortfolioPlan`은 1단계의 유일한 공식 산출물이다. 완성된 웹 카피나 시각 디자인이
아니라, 무엇을 왜 어떤 순서로 전달할지 정의하는 계획이다.

```json
{
  "version": 1,
  "target": {
    "company": "지원 회사",
    "role": "지원 직무",
    "primaryReaders": ["채용 담당자", "실무 리드"],
    "decisionGoal": "인터뷰 대상으로 판단하게 한다"
  },
  "positioning": {
    "headlineIntent": "첫 화면에서 전달할 정체성",
    "valueProposition": "회사에 제공할 수 있는 가치",
    "differentiators": ["증거가 있는 차별점"]
  },
  "requirementCoverage": [],
  "narrative": {
    "arc": "문제 정의에서 실행과 검증으로 이어지는 이야기",
    "sectionOrder": ["hero", "selected-work", "capabilities", "about", "contact"]
  },
  "sections": [
    {
      "id": "selected-work",
      "purpose": "핵심 요구 역량을 프로젝트 증거로 확인시킨다",
      "takeaway": "독자가 읽고 남겨야 할 한 문장",
      "evidenceIds": ["personal-project-03"],
      "contentPattern": "case-study",
      "interactionOpportunity": "세부 과정 펼치기",
      "targetLength": 900
    }
  ],
  "claims": [
    {
      "id": "claim-01",
      "intent": "사용자의 기여를 설명",
      "evidenceIds": ["personal-project-03"],
      "allowedNumbers": ["220분", "24분"]
    }
  ],
  "exclusions": [],
  "unusedEvidence": [],
  "rationale": "이 공고에서 이 구성과 증거를 선택한 이유"
}
```

설계 단계가 반드시 결정해야 하는 것:

- 지원자를 어떤 한 문장으로 이해시킬지
- 어떤 요구사항을 앞에 둘지
- 어떤 프로젝트를 선택하고 무엇을 제외할지
- 프로젝트마다 문제, 역할, 행동, 결과 중 무엇을 강조할지
- 독자의 읽기 순서와 섹션별 핵심 takeaway
- 콘텐츠 자체가 요구하는 표현 방식과 인터랙션 기회
- 근거 부족, 비공개, 중복 때문에 사용하지 않을 내용

설계 단계가 결정하지 않는 것:

- 최종 색상, 폰트, 그림자, 모서리 반경
- 특정 섹션의 픽셀 단위 레이아웃
- 최종 애니메이션 곡선과 지속 시간
- 완성 문장의 미세한 문체

## 8. 스타일 계약

사용자의 스타일 선택은 자유 문장 그대로 전달하지 않고 `StyleSpec`으로 컴파일한다.
“모던하고 세련되게”처럼 해석 범위가 넓은 값만으로는 충분하지 않다.

```json
{
  "name": "Editorial Tech",
  "visualCharacter": ["정교함", "지적임", "절제된 실험성"],
  "composition": "asymmetric-editorial",
  "typography": "large-display-readable-body",
  "palette": {
    "background": "#F4F0E8",
    "text": "#171717",
    "accent": "#D05A38"
  },
  "density": "comfortable",
  "geometry": "open-planes-and-rules",
  "motion": {
    "character": "calm-responsive",
    "allowed": ["text-reveal", "project-transition", "subtle-parallax"],
    "avoid": ["continuous-floating-decoration", "animate-everything"]
  },
  "interaction": "evidence-exploration",
  "imagery": "project-artifacts-first",
  "antiPatterns": [
    "generic-saas-landing",
    "three-identical-cards",
    "decorative-dashboard-without-evidence",
    "color-only-variation"
  ]
}
```

스타일 간 다양성은 팔레트가 아니라 다음 축의 조합으로 만든다.

- 읽는 흐름: 단일 서사, 비대칭 편집, 밀도 높은 격자 등
- 주인공: 타이포그래피, 프로젝트 이미지, 수치, 과정 다이어그램 등
- 정보 밀도와 여백 리듬
- 프로젝트를 보여주는 형식
- 모션의 성격과 인터랙션 방식
- 표면 문법: 색, 선, 면, 질감, 모서리

## 9. 공통 디자인 원칙

`DesignPrinciples`는 스타일과 분리해 버전 관리한다. 모든 생성에 같은 안정적인 접두
프롬프트로 사용한다.

1. 첫 화면에서 지원자의 역할, 강점, 대표 증거를 빠르게 이해할 수 있어야 한다.
2. 장식보다 정보 위계를 우선한다.
3. 프로젝트마다 문제, 본인의 기여, 결과가 구분되어야 한다.
4. 동일한 카드 패턴을 모든 콘텐츠에 반복하지 않는다.
5. 한 섹션에는 명확한 주인공과 하나의 핵심 takeaway가 있어야 한다.
6. 애니메이션은 등장, 관계, 상태 변화를 설명할 때만 사용한다.
7. 인터랙션은 탐색이나 이해를 개선해야 하며 기능 없는 장식이 되어서는 안 된다.
8. 모바일에서도 핵심 증거와 연락 행동을 제거하지 않는다.
9. 키보드 접근, 명도 대비, 포커스 표시, 모션 감소 설정을 지원한다.
10. 설계안에 없는 사실, 프로젝트, 회사명, 성과, 수치를 만들지 않는다.
11. 사용할 수 있는 실제 프로젝트 이미지가 있으면 장식 이미지보다 우선한다.
12. 모든 시각적 선택은 포트폴리오의 핵심 메시지를 강화해야 한다.

## 10. 웹사이트 생성 프롬프트 조립

생성 프롬프트는 아래 순서를 고정한다.

```text
1. System role와 보안·사실성 정책
2. DesignPrinciples 버전
3. StyleSpec
4. PortfolioPlan
5. 공개 가능한 증거와 미디어 목록
6. HTML/CSS 출력 계약과 허용 목록
7. 자체 점검 체크리스트
```

`PortfolioPlan`에 이미 들어 있는 내용을 원문 전체로 다시 반복하지 않는다. 다만 생성된
문장의 사실성을 대조할 수 있도록 공개 가능한 최소 증거 텍스트와 허용 수치 목록은 함께
전달한다.

생성 모델의 책임:

- 설계안의 읽기 순서와 takeaway를 실제 카피와 지면으로 구현한다.
- 스타일 문법을 구성, 타이포그래피, 밀도, 모션에 일관되게 반영한다.
- 콘텐츠에 맞는 시각 장치와 무스크립트 인터랙션을 선택한다.
- 반응형 HTML/CSS와 한 문장의 디자인 rationale을 반환한다.

생성 모델이 해서는 안 되는 것:

- 원천 자료를 다시 해석해 설계 결정을 뒤집는 일
- 더 멋져 보인다는 이유로 성과를 과장하거나 수치를 환산하는 일
- 스타일에 없는 상투적인 SaaS 구성으로 회귀하는 일
- 허용되지 않은 스크립트, 외부 이미지, 폼을 추가하는 일

## 11. 검증과 제한 수정

### 11.1 하드 게이트

다음 조건을 하나라도 만족하지 못하면 배포할 수 없다.

- 모든 공개 주장과 두 자리 이상 수치가 허용된 증거에 연결된다.
- 비공개 또는 미승인 기록이 출력에 없다.
- 금지된 태그, 이벤트 속성, URL, 외부 자산이 없다.
- 필수 섹션과 핵심 CTA가 존재한다.
- HTML/CSS 소독과 출력 스키마 검증을 통과한다.
- 390px와 1280px 화면에서 가로 오버플로가 없다.
- 키보드로 핵심 탐색과 인터랙션을 사용할 수 있다.
- `prefers-reduced-motion`에서 핵심 내용을 잃지 않는다.

사실성 오류는 자동 완화해 공개하지 않는다. 수정에 실패하면 초안 상태로 보존하고
사용자에게 해당 문장과 근거 부족을 보여 준다.

### 11.2 시각 품질 루브릭

하드 게이트 통과 후 다음 항목을 각각 5점으로 평가한다.

| 항목 | 질문 |
|---|---|
| 콘텐츠 명료성 | 10초 안에 역할, 강점, 대표 증거가 읽히는가 |
| 시각 위계 | 무엇을 먼저 보고 다음에 볼지가 분명한가 |
| 구성 완성도 | 섹션 간 리듬과 밀도가 의도적으로 느껴지는가 |
| 스타일 충실도 | 선택한 스타일이 색뿐 아니라 구조와 타이포에 나타나는가 |
| 증거 표현 | 프로젝트 결과와 과정이 장식보다 강하게 보이는가 |
| 모션·인터랙션 | 이해와 탐색에 도움이 되고 과하지 않은가 |
| 반응형·접근성 | 작은 화면과 키보드, 모션 감소에서 품질을 유지하는가 |

v1에서는 총점보다 항목별 실패를 사용한다. 2점 이하 항목이 있으면 그 결함만 담은 수정
프롬프트를 한 번 호출한다. “더 예쁘게” 같은 전면 재생성 지시는 사용하지 않는다.

### 11.3 다양성 평가

스타일 간 차이를 다음 신호로 비교한다.

- 첫 화면의 구성 유형
- 섹션별 폭과 배치 패턴
- 타이포그래피 크기 대비
- 카드 반복 비율
- 프로젝트별 표현 형식의 차이
- 모션과 인터랙션 패턴
- 색을 제거해도 서로 다른 구조로 인식되는지

색상만 달라지고 같은 히어로와 같은 카드 배열을 반복하면 다양성 실패로 판정한다.

## 12. 비용 전략과 측정

### 12.1 기본 생성 예산

- 정제: 저비용 모델, 소스별 한 번
- 연결: 가능한 부분은 결정적 코드로 처리
- 설계안: 설계용 모델 한 번
- 웹사이트: 고성능 생성 모델 한 번
- 자동 검증: 코드 기반
- 시각 검수: 스크린샷 입력 한 번
- 수정: 실패한 경우에만 최대 한 번

정제 결과와 `PortfolioPlan`은 캐시 가능한 버전 산출물이다. 스타일만 바꾸면 원천 자료를
다시 정제하지 않고 같은 설계안을 재사용한다. 사용자 기록이나 공고가 바뀌었을 때만
영향받는 단계를 무효화한다.

### 12.2 비용 기록

실제 API가 반환한 usage만 확정 비용으로 사용한다. 값이 제공되지 않으면 추정치를 확정
비용처럼 기록하지 않고 `unavailable`로 남긴다.

```json
{
  "provider": "provider-name",
  "model": "model-name",
  "pricingSnapshotAt": "2026-08-12T00:00:00Z",
  "calls": [
    {
      "stage": "page-generation",
      "inputTokens": 0,
      "cacheReadTokens": 0,
      "outputTokens": 0,
      "durationMs": 0,
      "costUsd": 0
    }
  ],
  "totalCostUsd": 0,
  "repairCount": 0
}
```

비용 비교에는 최소한 다음을 함께 표시한다.

- 전체 비용과 단계별 비용
- 첫 결과까지 걸린 시간
- 수정 호출 횟수
- 하드 게이트 통과 여부
- 시각 품질 루브릭
- 사용한 모델, 프롬프트 버전, 도구와 외부 레퍼런스

싼 결과와 좋은 결과를 하나의 임의 점수로 합치지 않는다. 비용과 품질을 함께 놓고
파레토 우위 여부로 비교한다.

## 13. 재현성 산출물

각 생성은 다음 산출물을 보존한다.

| 산출물 | 내용 |
|---|---|
| `source-manifest.json` | 원천 출처, 수집 시각, 해시, 공개 허용 상태 |
| `portfolio-plan.json` | 확정된 `PortfolioPlan` |
| `style-spec.json` | 사용자 선택을 컴파일한 스타일 문법 |
| `generation-manifest.json` | 모델, 프롬프트 버전·해시, 도구, 토큰, 시간, 비용 |
| `qa-report.json` | 하드 게이트와 시각 루브릭 결과 |
| `page.html` / `page.css` | 소독을 통과한 생성 결과 |

`generation-manifest.json`에는 사용한 플러그인, 스킬, 웹 검색, 이미지 생성, 참고 URL을
명시적으로 기록한다. 비어 있으면 사용하지 않았음을 의미한다.

## 14. 현재 Expresso와의 대응

| v1 개념 | 현재 대응 | 남은 차이 |
|---|---|---|
| 채용 공고 정제 | `job_analysis`, 요구사항과 원문 span | v1 필드와 우선순위 명시 필요 |
| 사용자 기록 정제 | career record, interview cleanup | 공개 허용 상태의 생성 입력 계약 강화 필요 |
| 요구사항-증거 연결 | coverage, material ranking | 회사 맥락과 중복도 반영 필요 |
| `PortfolioPlan` | `Recipe` / `AiRecipePlanner` + v1 plan snapshot | 구현됨. 세밀한 claim trace 확장 가능 |
| 회사 검색 정제 | `company_research_item`과 owner-scoped API | fact/signal 저장 구현. 자동 검색 수집기 필요 |
| 스타일 계약 | 확장된 `PageStyleGrammar` + 생성 전 override | 구성, 모션, 이미지, anti-pattern 구현됨 |
| 디자인 원칙 | `DESIGN_PRINCIPLES_VERSION` | 별도 버전 계약 구현됨 |
| 웹사이트 생성 | `AiPageGenerator` + generation Worker 후처리 | Plan + Style + Principles 직접 입력 구현됨 |
| 사실·보안 검증 | 숫자 대조, HTML/CSS sanitize, QA 상태 | 공개 하드 블록 구현. 비수치 주장 trace 고도화 필요 |
| 시각 검증 | 정적 반응형·모션·스타일 검사 | 실제 렌더 스크린샷 기반 QA 필요 |
| 비용 기록 | planning/page generation manifest | 단계별 usage·API 비용 기록 구현됨 |

기존 `Recipe`는 폐기 대상이 아니라 `PortfolioPlan`으로 진화할 출발점이다. 기존
`AiPageGenerator`도 유지하되 원천 자료의 해석 책임을 줄이고, 확정된 설계안을 표현하는
역할로 좁힌다.

## 15. v1 완료 조건

다음을 모두 만족하면 방법론 v1이 제품에 구현된 것으로 본다.

- 세 입력 소스가 출처를 포함한 정규화 계약으로 저장된다.
- 회사 조사 정보가 사실과 해석, 최신성을 구분한다.
- `PortfolioPlan`이 요구사항, 증거, 주장, 섹션을 역추적할 수 있다.
- 사용자가 생성 전에 `StyleSpec`을 선택하거나 승인한다.
- 생성 모델은 Plan + Style + Principles 계약만으로 웹페이지를 만든다.
- 선언되지 않은 도구나 레퍼런스가 생성 과정에 개입하지 않는다.
- 사실성, 보안, 모바일, 접근성 하드 게이트가 자동화된다.
- 시각 검수와 제한 수정이 최대 한 번으로 동작한다.
- API 토큰, 비용, 시간, 모델, 프롬프트 버전이 호출별로 남는다.
- 서로 다른 스타일 결과가 색뿐 아니라 구조적으로 구분된다.

## 16. 후속 설계 순서

1. `PortfolioPlan`과 입력 정제 데이터의 JSON Schema 확정
2. 현재 `Recipe`에서 `PortfolioPlan`으로의 호환·마이그레이션 설계
3. 회사 검색 수집, 출처 평가, 최신성 정책 설계
4. `PageStyleGrammar` 확장과 사용자 선택 UI 정의
5. 버전이 분리된 `DesignPrinciples` 및 생성 프롬프트 확정
6. 렌더 기반 QA와 한 번의 제한 수정 계약 정의
7. 단계별 usage·비용 원장과 비교 실험 프로토콜 구현
