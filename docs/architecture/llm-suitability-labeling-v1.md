# LLM 공고 적합도 라벨링 v1

## 목적

합성 프로필과 채용 공고의 적합도를 Claude Code Sonnet이 동일한 기준으로 평가하여
`0~100` 정수 라벨을 만듭니다. 이 점수는 합격 확률이 아닙니다. 현재 프로필에 기록된
경력 근거가 공고의 자격 요건과 주요 업무를 얼마나 뒷받침하는지를 나타냅니다.

기존 `structured-weak-label-v1`은 직무 분류, 연차 차이, 기술 문자열 일치를 코드로
합산한 개발용 약한 라벨입니다. 새 학습에서는 이 값을 교사 라벨로 사용하지 않습니다.

## 입력 데이터

- 프로필: 합성 프로필 v4.5.2 품질 게이트를 통과한 1,000개
- 공고 원천: 로컬 JTH `jobs.csv` 6,011건
- 후보로 실제 선택된 고유 공고: 2,886건
- 후보군: 프로필당 10건, 총 10,000쌍
- 후보 구성: 동일 직무 5건, 인접 직무 3건, 무작위 직무 2건
- 분할: 프로필 family와 공고 ID를 기준으로 `train`, `valid`, `test`를 분리합니다.

후보 선정에만 프로필의 희망 직무를 사용합니다. Sonnet이 적합도를 평가할 때는 희망
직무를 근거로 제공하지 않습니다. 평가 입력에는 경력 연차와 사용자가 작성한 기록의
제목, 기본 프로퍼티, 본문만 넣습니다.

JTH 공고는 이미 직무, 경력, 기술, 도구, 학력, 언어 등 구조화된 필드를 포함합니다.
Sonnet은 이 필드에서 필수 자격, 주요 업무, 우대 사항을 해석합니다. 빈 값이나 공고에
없는 조건은 만들지 않습니다.

## 평가 원칙

1. 프로필에 실제로 기록된 내용만 근거로 사용합니다.
2. 직무명이 같다는 이유만으로 충족으로 판정하지 않습니다.
3. 제목이나 프로퍼티만 있고 본문 근거가 없으면 `transferable`을 넘지 않습니다.
4. 유사 기술은 자동으로 같은 기술로 간주하지 않습니다.
5. 연차, 산업, 학력, 자격은 공고에 명시된 경우에만 평가합니다.
6. 기록이 짧거나 적다는 사실 자체는 감점 사유가 아닙니다. 확인할 수 없는 요구사항만
   `not_evidenced`로 판정합니다.
7. 명시적 불충족도 해당 요구사항 점수를 낮출 뿐, 최종 점수 상한이나 탈락 규칙을
   적용하지 않습니다.
8. 합성 여부, 생성 모델, provenance, profile family, split은 평가 입력에서 제외합니다.

## 요구사항별 근거 판정

Sonnet은 공고의 요구사항을 최대 8개로 정리하고 각각 다음 5단계 중 하나로 판정합니다.

| 판정 | 기준점 | 의미 |
| --- | ---: | --- |
| `strong` | 100 | 구체적인 행동, 범위, 결과가 있는 강한 직접 근거 |
| `adequate` | 75 | 해당 요구를 수행했다고 볼 수 있는 직접 근거 |
| `partial` | 50 | 일부만 충족하거나 깊이와 범위가 부족한 직접 근거 |
| `transferable` | 25 | 인접 경험은 있으나 해당 요구의 직접 경험은 아님 |
| `not_evidenced` | 0 | 현재 프로필에서 확인할 수 없음 또는 명시적으로 부족함 |

하나의 기록이 여러 요구사항을 뒷받침할 수 있습니다. 다만 같은 내용을 요구사항 안에서
반복 가산하지 않습니다. 근거가 있는 판정에는 실제 `recordId`만 연결합니다.

## 종합 점수

평가 축은 세 개입니다.

| 평가 축 | 기본 비중 | 내용 |
| --- | ---: | --- |
| `must` | 45% | 기술, 경력, 학력, 자격 등 명시된 필수 자격 |
| `responsibility` | 40% | 실제 수행할 주요 업무와 프로필 기록의 직접 일치 |
| `preferred` | 15% | 우대 사항과 추가적인 강점 |

근무지, 고용 형태, 근무 방식 등 `condition`은 현재 프로필에 대응하는 희망 조건 필드가
없으므로 점수에서 제외합니다. 특정 평가 축이 공고에 없으면 그 비중을 나머지 축에
비례해 재분배합니다.

Sonnet은 요구사항의 종류와 근거 수준까지만 판단합니다. 각 축의 점수는 코드가 그 축에
속한 요구사항 판정의 평균으로 계산하고, `matchScore`도 적용 가능한 축 점수의 가중 평균을
반올림해 계산합니다. 이 계산식은 LLM의 판단을 대신하는 규칙 라벨이 아니라, Sonnet이
내린 요구사항별 판정을 한 점수로 일관되게 합치는 공개된 루브릭입니다. 산술을 코드로
분리해 LLM의 계산 오류 때문에 같은 사례를 다시 호출하지 않습니다.

점수 해석은 다음과 같습니다.

| 구간 | 의미 |
| --- | --- |
| 0~19 | 공고의 핵심 업무와 자격을 뒷받침하는 기록이 거의 없음 |
| 20~39 | 인접하거나 전이 가능한 경험은 있으나 직접 근거가 부족함 |
| 40~59 | 일부 핵심 요구에는 직접 근거가 있지만 중요한 공백이 큼 |
| 60~79 | 주요 업무와 필수 자격의 다수를 직접 뒷받침함 |
| 80~94 | 대부분의 핵심 요구에 구체적이고 강한 근거가 있음 |
| 95~100 | 적용 가능한 거의 모든 요구에 강한 직접 근거가 있음 |

## 출력 계약

사용자와 학습 모델이 사용하는 외부 라벨은 `matchScore` 하나입니다. 다음 내부 필드는
라벨의 추적, 오류 분석, 재생성에 사용합니다.

```json
{
  "profileId": "profile-001",
  "jobId": "job-001",
  "matchScore": 72,
  "dimensionScores": {
    "must": {"applicable": true, "score": 68},
    "responsibility": {"applicable": true, "score": 81},
    "preferred": {"applicable": true, "score": 54}
  },
  "requirementAssessments": [
    {
      "requirement": "백엔드 API 설계 경험",
      "kind": "responsibility",
      "coverage": "adequate",
      "evidenceRecordIds": ["record-17"]
    }
  ],
  "reason": "주요 업무 경험은 직접 확인되지만 일부 필수 기술의 근거가 부족합니다.",
  "confidence": 86,
  "rubricVersion": "job-profile-fit-v1",
  "labelSource": "claude-code-sonnet-5"
}
```

`confidence`는 적합도가 아니라 주어진 텍스트만으로 판정할 수 있었던 정도입니다. 학습
목표에는 기본적으로 사용하지 않고 낮은 신뢰도 사례의 점검과 재라벨링에만 사용합니다.

## Claude Code 실행 계약

- 실행 파일: Windows 네이티브 Claude Code
- 모델 인자: `--model sonnet`
- 현재 확인된 canonical model: `claude-sonnet-5`
- 사용자 설정 차단: `--safe-mode --disable-slash-commands`
- 도구 차단: `--tools ""`
- 기본 에이전트 컨텍스트 축소: 짧은 평가 전용 `--system-prompt`
- 사고 예산: `--effort low`
- 세션 저장 차단: `--no-session-persistence`
- 출력: `--output-format json --json-schema <schema>`
- 재시도: 계약 오류와 일시적 API 오류만 최대 3회
- 세션 한도: HTTP 429와 재설정 안내를 받으면 즉시 중단하고 재설정 뒤 재개
- 재개: 완료된 프로필 배치는 다시 호출하지 않음

원본 응답에는 모델명, 사용량, 소요 시간, 비용 추정값을 보존합니다. 최종 라벨 파일은
프로필과 공고 ID, split, 루브릭 버전, 모델 버전을 함께 기록합니다. 프롬프트, 출력
스키마, 모델, effort를 묶은 요청 해시가 같은 완료 응답만 재사용합니다.

## 품질 게이트

- 프로필 1,000개, 후보쌍 10,000개, 누락 0건
- `(profileId, jobId)` 중복 0건
- 프로필, 공고, 라벨의 split 불일치 0건
- `matchScore` 범위 오류 0건
- 존재하지 않는 `recordId` 참조 0건
- 요구사항 판정과 축 점수의 허용 오차 초과 0건
- 적용 가능한 축 점수와 최종 점수의 반올림 오차 초과 0건
- 모델 또는 루브릭 버전 혼합 0건
- 점수 구간별 건수와 후보 bucket별 분포를 manifest에 기록

## Pairwise 학습 확장

첫 모델은 0~100 회귀 라벨로 학습합니다. 이후 동일 프로필의 공고 두 개를 비교하는
pairwise 학습을 추가할 수 있습니다.

1. 기존 점수 차이가 15점 이상인 공고쌍은 높은 점수 쪽을 선호 라벨로 자동 파생합니다.
2. 점수 차이가 작은 쌍은 임의로 순서를 만들지 않습니다.
3. 첫 모델이 순서를 자주 뒤집는 hard pair만 Sonnet에 직접 비교시킵니다.
4. cross-encoder는 점수 회귀 손실과 pairwise ranking loss를 함께 사용합니다.
5. 제품에는 보정된 단일 `matchScore`만 출력합니다.

자동 파생한 pairwise 라벨은 동일한 scalar 라벨을 재표현한 것이므로 독립적인 정답으로
간주하지 않습니다. Sonnet이 직접 비교한 hard pair와 사람이 검수한 pair를 별도 slice로
평가합니다.
