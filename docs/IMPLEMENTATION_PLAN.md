## 1. 목표

개발 포털의 기능 명세 D1–D12와 42개 테이블 데이터 모델을 실행 가능한 백엔드로 구현한다. 사용자가 커리어 기록을 축적하고, 공고를 분석해 근거가 연결된 포트폴리오를 생성·편집·배포하며, 익명화된 방문 데이터를 다음 행동으로 연결하는 전체 흐름을 API와 비동기 Worker로 제공하는 것이 목표다.

첫 구현 게이트는 기능을 넓게 펼치는 것이 아니라 다음 종단 슬라이스다.

```text
가입/인증 → 기본 카테고리 7종 생성 → 기록 작성/자동 저장
→ 기록 근거 조회 → 사용자 간 데이터 격리 검증
```

## 2. 완료 정의

백엔드 구현은 다음 조건을 모두 만족할 때 완료로 본다.

1. D1–D12에서 백엔드가 책임지는 API, 비동기 작업, 저장 규칙이 버전이 명시된 계약으로 제공된다.
2. 인증된 사용자는 자신의 데이터에만 접근할 수 있고 교차 사용자 접근 테스트가 전 도메인에서 통과한다.
3. AI 산출물의 모든 주장에 원문 범위, 기록 ID 또는 질문 ID 근거가 있으며 근거 없는 주장과 사용자가 제공하지 않은 수치가 저장·공개되지 않는다.
4. 사용자가 수정한 콘텐츠는 잠금되고, 자동 저장·낙관적 동시성·변경 이력·복원이 검증된다.
5. 30초 이상 걸릴 수 있는 분석·생성·내보내기·집계는 재시도 가능한 Worker 작업이며 API 재호출로 중복 실행되지 않는다.
6. 실제 PostgreSQL과 Redis를 사용하는 통합 테스트, 핵심 사용자 흐름 E2E, 계약·보안·성능 테스트가 CI에서 통과한다.
7. 스키마 마이그레이션, 백업/복구, 배포, 관측, 롤백 절차가 재현 가능한 명령과 증거로 남는다.

- Node.js 24 이상, pnpm 11, TypeScript ESM, Fastify, PostgreSQL, Redis/BullMQ를 현재 호환성 기준으로 유지한다.
- 서비스 시작 과정에서 자동 마이그레이션하지 않고 배포 단계에서 `pnpm db:migrate`를 실행한다.

- 현재 작업 트리의 개발 포털 변경과 기존 백엔드/데이터베이스 변경은 사용자 소유 변경으로 보존한다.

## 6. 아키텍처와 계약

### 실행 단위

```text
클라이언트
  │ HTTPS + versioned contract
  ▼
backend-api (Fastify)
  ├─ auth/request context ── application service ── PostgreSQL transaction
  ├─ idempotency/outbox ────────────────────────── Redis/BullMQ
  └─ signed asset access ───────────────────────── object storage
                                                   │
                                                   ▼
backend-worker
  ├─ job analysis / AI interview / generation
  ├─ export / aggregation / notification
  └─ progress, result, failure evidence 기록
```

### 코드 경계

- `packages/contracts`: HTTP DTO, 이벤트/작업 payload, 오류 봉투, 페이지네이션, 멱등 키와 계약 테스트의 단일 소유자.
- `packages/database`: 추가 전용 SQL 마이그레이션, 체크섬 실행기, 데이터 불변성 테스트.
- `services/backend/src/api`: Fastify 조립, 인증 컨텍스트, 전역 오류/요청 로깅. 도메인 작업과 중앙 조립을 한 단계씩 함께 검증한다.
- `services/backend/src/modules/<domain>`: route → application service → repository 순서의 공개 진입점. 다른 도메인의 내부 파일을 import하지 않는다.
- `services/backend/src/platform`: PostgreSQL, Redis, 큐, 객체 저장소, 메일, AI provider 어댑터.
- `services/backend/src/worker`: processor 조립. 도메인 작업자는 processor 파일을 추가하고 중앙 등록은 통합 게이트에서 한다.

### 공통 계약

- API prefix는 `/v1`; 성공 응답은 리소스 DTO, 실패는 `{ error: { code, message, requestId, details? } }` 형태다.
- 모든 사용자 소유 쿼리는 인증 컨텍스트의 `userId`를 명시적으로 받고, 저장소 API가 이를 생략하지 못하게 한다.
- 변경 요청은 `Idempotency-Key` 또는 리소스 버전(`If-Match`)을 사용한다. 충돌은 `409`, 오래된 버전은 `412`로 구분한다.
- 외부 이벤트와 장기 작업은 payload version, trace ID, idempotency key를 갖는다. 최대 재시도 후 DLQ와 운영 알림으로 이동한다.
- AI provider는 구조화 출력 스키마를 통과한 결과만 반환한다. 별도 evidence validator가 근거 일치, 수치 출처, 잠금 위반을 검사한 뒤 저장을 허용한다.
- 공개 배포는 편집 테이블을 직접 읽지 않고 불변 deployment snapshot만 읽는다.
- 분석 이벤트는 수집 API에서 최소화·유효성 검사를 거친 뒤 원시 이벤트와 일 집계를 분리한다.

## 8. 검증 전략과 예산

- 단위 테스트: 도메인 불변식, 상태 전이, 점수/집계, entitlement, evidence validator를 외부 시스템 없이 검증한다.
- 계약 테스트: `packages/contracts`의 JSON Schema/OpenAPI와 Fastify route가 동일한 요청·응답·오류를 제공하는지 검사한다.
- 데이터베이스 테스트: 빈 DB에 전체 마이그레이션, 두 번째 실행 무변경, 이전 체크섬 변조 거부, 외래키/소유권/트리거를 실제 PostgreSQL에서 검사한다.
- 통합 테스트: 격리된 PostgreSQL/Redis에서 API→DB→queue→worker→DB 흐름과 멱등 재시도를 검사한다.
- E2E: 각 마일스톤의 한 사용자 흐름과 교차 사용자 공격 흐름을 HTTP 경계에서 실행한다.
- 보안: 인증 누락, IDOR, 입력 크기, 파일 형식, 서명 URL, 공개/비공개 전환, 비밀 로그 노출을 자동 점검한다.
- 성능 목표: 일반 읽기/쓰기 API p95 300ms 이하, 수집 API p95 150ms 이하, 큐 등록 p95 200ms 이하를 로컬 기준 부하에서 만족한다. 장기 작업은 30초 전에 job ID를 반환한다.
- 신뢰성 목표: 동일 멱등 키 100회 재전송 시 도메인 효과와 quota 차감은 각각 1회, Worker 강제 재시작 후 완료/재시도 상태 유실 0건.
- 품질 게이트: `pnpm typecheck`, `pnpm test`, `pnpm build`, 마이그레이션 테스트, 계약/E2E, 보안/성능 스모크가 모두 통과해야 통합한다.

## 9. 직렬 실행과 통합 원칙

- 서브에이전트를 사용하지 않고 coordinator가 현재 checkout에서 DAG 순서대로 한 작업씩 직접 구현한다.
- 공유 계약(`packages/contracts/**`)을 먼저 동결한 뒤 각 도메인은 이를 읽기 전용 기준으로 사용한다.
- 한 작업 안에서 도메인 구현, 중앙 API/Worker wiring, 마이그레이션, focused test를 함께 끝낸다.
- 각 작업은 focused test → 영향 범위 회귀 → 전체 typecheck/test/build → 증거 감사 순으로 검증하고 통과한 뒤에만 다음 작업으로 이동한다.
- 자체 리뷰에서는 diff를 완료 기준별로 다시 읽고 P0/P1 결함을 수정한다. 새 범위는 현재 작업에 섞지 않고 체크리스트와 DAG를 먼저 갱신한다.
- 미커밋된 기존 사용자 변경은 그대로 보존하며, 파일이 겹칠 때는 현재 내용을 먼저 읽고 최소 패치만 적용한다.

## 10. 주요 위험과 완화

## 11. 배포와 롤백

1. 개발/CI는 격리된 PostgreSQL·Redis에서 마이그레이션과 계약 테스트를 먼저 실행한다.
2. 스테이징은 마이그레이션 → API → Worker 순서로 배포하고 readiness, queue lag, 오류율을 확인한다.
3. 프로덕션은 이전 버전과 호환되는 expand/contract 마이그레이션만 사용한다. 파괴적 변경은 최소 한 릴리스 뒤에 수행한다.
4. API/Worker는 이전 이미지로 되돌릴 수 있어야 하며, 실패한 Worker 작업은 DLQ에서 멱등하게 재처리한다.
5. 공개 포트폴리오는 직전 deployment snapshot으로 즉시 되돌린다.
6. 데이터 롤백이 필요한 변경은 배포 전에 복원 테스트를 마친 백업과 명시적 복구 스크립트를 요구한다.
7. 단계 배포 중 오류율, p95 지연, queue lag, 생성 실패율, quota 불일치가 예산을 넘으면 자동 확대를 중단하고 이전 릴리스로 복귀한다.
