# 2. 요구사항 정의

## 2.1. 서비스 구성 및 개요

Expresso는 **AI서비스**와 **AI학습서버**를 분리해 운영한다. 양식이 요구하는 분리이자,
두 서버의 수명 주기가 실제로 다르기 때문이다. AI서비스는 사용자 요청마다 응답해야 하고,
AI학습서버는 데이터가 쌓였을 때 배치로 학습한다.

> `[그림 2.1] 서비스 시나리오 구성도 — 아래 구성을 PPT로 그려 캡처한다.`

```text
[클라이언트]                [AI서비스]                      [AI학습서버]
 웹 (Next.js)  ──REST──▶  API 서버 (Fastify)   ──학습요청──▶  학습·검증·배포
 모바일 웹                   │                                   │
 공개 사이트                  ├─ 큐(BullMQ/Redis) ─▶ Worker      ├─ 데이터세트 생성
                            │                        │          ├─ 모델 학습
                            ├─ PostgreSQL            │          ├─ 성능 검증(ROC)
                            ├─ 객체 저장소            │          └─ 모델 배포
                            │                        │              │
                            └─ LLM 프로바이더 ◀───────┘              │
                               (Claude / Codex)                     │
        [모델 A 랭커] [모델 B 분류기] ◀──── 배포된 모델 ──────┘

[데이터 수집]
 채용 사이트 크롤링 ─▶ job_source 실행 ─▶ job_posting 정규화 ─▶ 학습 데이터 원천
 사용자 경력 기록   ─▶ record        ─────────────────────────▶ 학습 데이터 원천
```

### 각 구성요소가 하는 일

| 구성요소 | 역할 | 현재 구현 |
| --- | --- | --- |
| 웹 클라이언트 | 기록 작성 · 공고 탐색 · 생성 요청 · 편집 · 배포 · 분석 | Next.js 16, 화면 25개 |
| API 서버 | REST 125개 · 인증 · 권한 · 검증 · 낙관적 잠금 | Fastify 5 |
| Worker | 공고 분석 · 생성 · 내보내기 · 분석 집계 · 알림 · 정리 | BullMQ, 프로세서 8종 |
| PostgreSQL | 도메인 데이터 75개 테이블 | PostgreSQL 18.4 |
| Redis | 작업 큐 · 캐시 | Redis 8.2 |
| LLM 프로바이더 | 공고 해석 · 레시피 · 문장 생성 | Claude Code / Codex / fixture |
| **AI학습서버** | 모델 A·B 교사 라벨링 · 학습 · 검증 · 배포 | **미구현 — 본 프로젝트 과제** |

### AI서비스와 AI학습서버의 분리 근거

| 축 | AI서비스 | AI학습서버 |
| --- | --- | --- |
| 호출 시점 | 사용자 요청마다 | 배치(주기 또는 수동) |
| 응답 시간 요구 | 초 단위 | 분~시간 단위 |
| 상태 | 무상태 | 데이터세트·모델 아티팩트 보유 |
| 실패 영향 | 해당 요청만 | 다음 배포까지 기존 모델 유지 |
| 확장 방식 | 수평 확장 | 단일 노드 |

두 서버는 REST로만 통신한다(7.4). 학습서버가 죽어도 서비스는 **직전에 배포된 모델**로
계속 답한다. 모델이 하나도 없으면 규칙 기반 판정으로 되돌아간다.

## 2.2. 데이터분석의 요구사항

AI학습이 필요로 하는 데이터가 어떤 내용과 특성을 가져야 하는지 정의한다.

학습 대상은 **퍼스널 데이터(사용자 기록)와 채용 공고를 잇는 두 방향**이다.

| 모델 | 방향 | 입력 | 출력 |
| --- | --- | --- | --- |
| A | 기록 → 공고 | (프로필, 공고) | 적합도 0–100 + 축별 충족 |
| B | 공고 → 기록 | (요구사항, 기록) | covered / partial / missing |

두 방향 모두 현재는 문자열 부분일치로 구현되어 있고, 그 구현이 성능 baseline이 된다.

### 데이터가 갖춰야 할 내용

| 요구 | 내용 | 근거 |
| --- | --- | --- |
| 공고 원문 | 제목 · 본문 · 회사 · 고용형태 · 경력 요건 | `job_posting` |
| 요구사항 | 공고에서 추출한 역량 항목의 라벨과 인용문 | `job_posting_requirement` |
| 요구사항 축 | `technology` / `impact` / `role` / `conditions`. 널 허용 | `job_posting_requirement.axis` |
| 요구사항 종류 | `must` / `nice` / `tone` | `job_posting_requirement.kind` |
| 기록 본문 | 사용자 경력 기록의 제목과 본문 | `record` |
| 기록 카테고리 | 경험 · 프로젝트 · 학력 등 7종 + 사용자 정의 | `category` |
| 프로필 요약 | 총 경력 · 주 직군 · 스킬 목록 | `career_profile` · `skill` |
| 라벨 | 모델별 판정값 | 3.1의 교사 |

### 데이터가 갖춰야 할 특성

1. **라벨이 규칙의 출력이어서는 안 된다.** 현행 `match_score` · `requirement_coverage`에
   쌓인 값은 문자열 매칭 결과다. 그것을 학습하면 규칙을 복제할 뿐이다.
2. **사용자가 없으므로 라벨을 사람이 대량으로 만들 수 없다.** LLM을 교사로 쓰고,
   그 교사가 사람과 얼마나 맞는지를 표본으로 따로 잰다(9.2).
3. **직군이 편중되지 않아야 한다.** 백엔드만으로 학습하면 디자인 직군에서 무너진다.
4. **클래스 분포가 지나치게 치우치지 않아야 한다.** 무작위 쌍은 대부분 부적합이다.
5. **개인정보가 학습에 들어가지 않아야 한다.** 이름 · 연락처 · 소속 기업명은 특징 추출
   전에 마스킹한다.
6. **한국어와 영어가 섞인다.** 기술 용어는 영어, 서술은 한국어다. 토크나이저와 임베딩이
   둘 다 다뤄야 한다.

### 현재 확보 가능한 원천

| 원천 | 위치 | 상태 |
| --- | --- | --- |
| 채용 공고 | `job_posting` | 수집 파이프라인 구현됨(`job_source`) |
| 추출된 요구사항 | `job_posting_requirement` | 공고 분석 시 생성 |
| 사용자 기록 | `record` | 실사용 데이터 없음 — 동의받은 이력서와 공개 자료로 구축 |
| 규칙 판정 | `match_score` · `requirement_coverage` | **baseline으로만 사용** |
| LLM 응답 픽스처 | `services/backend/fixtures/ai/` | 공고 분석 결과 일부 |

## 2.4. AI서비스 유스케이스 모델

> `[그림 2.2] 사용자용 유스케이스 다이어그램 — 아래 액터와 유스케이스를 UML 툴로 그려
> 캡처한다. AI학습서버 · 데이터수집 · AI서버가 반드시 표시되어야 한다.`

### 액터

| 액터 | 설명 |
| --- | --- |
| 구직자 | 기록을 쌓고 포트폴리오를 생성·배포하는 주 사용자 |
| 방문자 | 배포된 공개 포트폴리오를 열람하는 익명 사용자 |
| 운영자 | 공고 수집 소스와 스케줄 작업을 관리하는 사용자 |
| API 서버 | 요청을 처리하는 시스템 액터 |
| 데이터수집기 | 채용 사이트에서 공고를 수집하는 시스템 액터 |
| AI서버 | LLM 프로바이더를 호출해 분석·생성하는 시스템 액터 |
| AI학습서버 | 모델 A(공고 추천 랭커)와 모델 B(요건 충족 분류기)를 학습·배포하는 시스템 액터 |

### 사용자 유스케이스

```text
구직자 ──▶ 회원가입 ──include──▶ 약관 동의
       ──▶ 로그인 (Google 연동 «extend»)
       ──▶ 경력 기록 작성 ──extend──▶ AI 인터뷰로 작성
       ──▶ 공고 검색 ──include──▶ 자연어 조건 해석 [AI서버]
                    ──include──▶ 공고 적합도 순위 [AI학습서버 · 모델 A]
       ──▶ 공고 분석 ──include──▶ 요구사항 추출 [AI서버]
                    ──include──▶ 요건 충족 판정 [AI학습서버 · 모델 B]
       ──▶ 재료 선정 ──include──▶ 기록 추천 [AI학습서버 · 모델 B]
       ──▶ 레시피 작성 ──extend──▶ 문장으로 수정 지시 [AI서버]
       ──▶ 포트폴리오 생성 ──include──▶ 근거 검증
       ──▶ 포트폴리오 편집 ──extend──▶ 말로 고치기 [AI서버]
       ──▶ 배포 ──include──▶ 주소 발급
       ──▶ 방문 분석 열람 ──extend──▶ 해설 생성 [AI서버]

방문자 ──▶ 공개 포트폴리오 열람 ──include──▶ 방문 이벤트 기록

데이터수집기 ──▶ 공고 정기 수집 ──▶ 정규화 ──▶ 중복 제거
```

> `[그림 2.3] 운영자용 유스케이스 다이어그램 — 아래 유스케이스를 UML 툴로 그려 캡처한다.`

```text
운영자 ──▶ 공고 소스 등록
      ──▶ 수집 실행 트리거
      ──▶ 수집 결과 확인
      ──▶ 스케줄 작업 관리
      ──▶ 시스템 상태 확인
      ──▶ 학습 데이터세트 생성 [AI학습서버]
      ──▶ 모델 학습 실행 [AI학습서버]
      ──▶ 모델 성능 확인 [AI학습서버]
      ──▶ 모델 배포·롤백 [AI학습서버]
```

## 2.6. 요구기능 정의 (웹관리자용)

**현재 형상에는 전용 관리자 앱과 권한 분리가 없다.** 인증 컨텍스트
(`services/backend/src/api/plugins/auth-context.ts`)에 역할(role) 개념이 없고, 아래
운영 기능은 일반 인증 사용자면 호출할 수 있다. 관리자 화면(5.5)도 없다.

이 절은 **현재 API로 실재하는 운영 기능**과 **AI학습서버 운영을 위해 새로 필요한 기능**을
나누어 적는다. 권한 분리는 구현 대상이다.
