# 8. 데이터 설계

## 8.1. 데이터 모델

Expresso의 영속 저장소는 MongoDB 8.0 단일 노드 replica set의 `expresso` 데이터베이스다.
애플리케이션은 `packages/database/src/collections.ts`의 컬렉션 접근자와
`packages/database/src/documents/`의 문서 타입을 사용한다. 컬렉션 validator와 인덱스는
`packages/database/src/collection-specs.ts`가 관리한다. 현재 접근자에는 컬렉션 82개가
선언돼 있다. 이 수는 코드의 접근자 수이며 운영 데이터베이스의 실재 컬렉션 수를 뜻하지 않는다.

문서 식별자는 UUID 문자열 `_id`이고, 컬렉션 사이의 참조는 `userId`, `recordId`,
`jobPostingId` 같은 필드에 저장한다. 사용자 소유 문서는 `userId`로 조회 범위를 제한한다.
속성처럼 부모와 함께 읽고 쓰는 값은 문서 안에 두고, 이력·업데이트·이벤트처럼 독립적으로
증가하거나 보존해야 하는 값은 별도 컬렉션에 둔다. 교차 컬렉션의 원자적 변경에는
MongoDB 트랜잭션을 사용한다.

### 핵심 참조

```text
users._id ──▶ career_records.userId ──▶ career_document_snapshots.recordId
         └──▶ job_analyses.userId ──▶ brews.jobAnalysisId
         └──▶ portfolios.userId ──▶ deployments.portfolioId
job_postings._id ──▶ job_posting_requirements.jobPostingId
job_posting_requirements._id ──▶ requirement_coverages.requirementId
career_records._id ──▶ brew_sources.recordId
```

공개 포트폴리오의 문장 근거는 `generation_sentence_evidence`가
`recipe_evidence_paths`를 거쳐 `career_records`의 원천 기록을 가리키도록 보존한다.
생성 검증은 이 참조와 근거 수치를 확인한다. 현재 `requirement_coverages`의
`covered/partial/missing` 값은 규칙 기반 계산 결과다. AI 모델을 통한 순위 산출과
메타데이터 기록은 4장의 개발 목표다.

## 8.2. 논리적 설계(컬렉션 명세서)

커리어 본문은 스냅샷과 순서가 있는 업데이트로 관리한다. 저장된 뷰는 `career_views.configuration`에 둔다. 관계·수식·롤업 결과는 커리어 기록과 관계 컬렉션에 연결한다. AI 편집 제안의 상태와 기준 버전은 `career_ai_proposals`에 남긴다.

## 8.3. 로그파일 설계

로그는 **JSON 한 줄에 한 사건**으로 남긴다(`pino`). 사람이 읽는 형식이 아니라 기계가
거르는 형식이다. 장애가 났을 때 필요한 것은 예쁜 문장이 아니라 `requestId`로 한 요청의
전 구간을 모으는 능력이다.

### 파일명

| 프로세스 | 파일명 | 회전 |
| --- | --- | --- |
| API 서버 | `expresso-api.log` | 일 단위 · 14일 보관 |
| Worker | `expresso-worker.log` | 일 단위 · 14일 보관 |
| AI학습서버 | `expresso-training.log` | 일 단위 · 30일 보관 |

학습 로그를 더 오래 두는 이유는, 모델 성능 문제가 배포 후 몇 주 뒤에 드러나기 때문이다.

### 레벨

| 레벨 | 형식 | 설명 | 비고 |
| --- | --- | --- | --- |
| 10 | trace | 개발 중 상세 추적 | 운영에서 사용하지 않음 |
| 20 | debug | 분기·중간 상태 | 운영에서 사용하지 않음 |
| 30 | info | 요청 처리 · 작업 시작/완료 등 정상 흐름 | 운영 기본값 |
| 40 | warn | 재시도 가능한 실패 · 폴백 발동 | |
| 50 | error | 요청 실패 · 작업 실패 | |
| 60 | fatal | 프로세스를 계속할 수 없는 오류 | |

운영 기본 레벨은 `info`이고, `LOG_LEVEL` 환경변수로 바꾼다.

### 공통 필드

| 필드 | 설명 |
| --- | --- |
| `level` | 위 레벨 번호 |
| `time` | 밀리초 단위 epoch |
| `requestId` | 요청 식별자. 응답 헤더 `x-request-id`와 같다 |
| `req.method` | HTTP 메서드 |
| `req.url` | 경로. **쿼리스트링은 잘라낸다** |
| `req.host` | 호스트 |
| `msg` | 사건 이름 |

### 남기지 않는 것

`services/backend/src/platform/observability.ts`가 아래 경로를 `[REDACTED]`로 치환한다.

```text
req.headers.authorization      request.headers.authorization
req.headers.cookie             request.headers.cookie
req.headers['x-api-key']       body.password
body.token                     body.accessToken
body.refreshToken              databaseUrl
redisUrl
```

쿼리스트링을 통째로 잘라내는 이유는, 검색어에 개인정보가 들어가기 때문이다. 무엇을
가려야 할지 하나씩 정하는 것보다 통째로 버리는 쪽이 안전하다.

오류 객체도 그대로 남기지 않는다. `safeErrorSummary()`가 `name` · `code` · `statusCode`만
추린다. LLM 프로바이더가 돌려준 거절 사유처럼 사용자 입력이 섞인 문장은 이 필터를 지난다.

| 필드 | 설명 |
| --- | --- |
| `contract` | 호출 계약 이름 (`job_analysis`, `recipe_draft`, …) |
| `provider` | `claude-code` / `codex` / `fixture` / `off` |
| `model` | 실제 모델 이름 |
| `tokensIn` · `tokensOut` | 토큰 수 |
| `durationMs` | 소요 시간 |
| `costUsd` | 추정 비용 |

## 8.4. 오류코드 및 오류파일 설계

### 서비스 오류코드

API가 답하는 오류 코드는 `packages/contracts/src/common.ts`의 `ErrorCodeSchema`에
정의된 10종이다. HTTP 상태와 1:1로 대응한다.

| 코드 번호 | 코드 | 설명 | 비고 |
| --- | --- | --- | --- |
| 200 | — | 정상 처리(성공) | |
| 400 | `VALIDATION_ERROR` | 요청 스키마 검증 실패 | |
| 401 | `AUTH_REQUIRED` | 인증이 필요하거나 세션이 만료됨 | |
| 403 | `FORBIDDEN` | 인증은 되었으나 권한이 없음 | |
| 404 | `NOT_FOUND` | 리소스가 없음 | |
| 409 | `CONFLICT` | 현재 상태와 충돌하는 요청 | |
| 412 | `PRECONDITION_FAILED` | `If-Match` 버전이 낡음 | 낙관적 잠금 |
| 422 | `UNPROCESSABLE` | 요청은 읽었으나 그대로는 처리할 수 없음 | 근거 검증 실패 등 |
| 429 | `RATE_LIMITED` | 사용량 한도 초과 | |
| 503 | `DEPENDENCY_UNAVAILABLE` | DB · Redis · LLM 등 의존 서비스 장애 | |
| 500 | `INTERNAL_ERROR` | 그 밖의 서버 오류 | |

401과 403을 나누는 이유는 클라이언트의 다음 행동이 다르기 때문이다. 401은 다시 로그인,
403은 다시 로그인해도 소용없다.

### 도메인 오류

같은 `UNPROCESSABLE`이라도 원인이 다르다. `details`에 도메인 코드를 넣는다.

| 도메인 코드 | HTTP | 설명 |
| --- | --- | --- |
| `GEN_UNGROUNDED_NUMBER` | 422 | 생성 문장에 근거 없는 수치가 있다 |
| `GEN_EVIDENCE_OUT_OF_RECIPE` | 422 | 레시피 밖의 근거를 인용했다 |
| `GEN_EXCLUSION_VIOLATED` | 422 | 레시피의 제외 조건을 어겼다 |
| `GEN_LOCKED_BLOCK_CHANGED` | 422 | 잠긴 블록을 바꾸려 했다 |
| `GEN_METRIC_WITHOUT_RECORD` | 422 | 수치 블록이 경력 기록을 인용하지 않았다 |
| `QUOTA_EXCEEDED` | 429 | 생성 횟수 한도 초과 |
| `PLAN_REQUIRED` | 403 | 상위 플랜에서만 쓸 수 있는 기능 |
| `SLUG_TAKEN` | 409 | 이미 쓰이는 공개 주소 |
| `AI_PROVIDER_UNAVAILABLE` | 503 | LLM 프로바이더 응답 없음 |

### 오류파일

오류만 따로 모은 파일을 남긴다. 운영 중 `error` 이상만 골라 보기 위해서다.

| 항목 | 값 |
| --- | --- |
| 파일명 | `expresso-error.log` |
| 대상 레벨 | 50(error) 이상 |
| 형식 | 8.3과 같은 JSON 한 줄 |
| 회전 | 일 단위 · 90일 보관 |

일반 로그(14일)보다 오래 두는 이유는, 드물게 나는 오류의 재발 주기가 2주보다 길기
때문이다.
