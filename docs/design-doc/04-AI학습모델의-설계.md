# 4. AI학습모델의 설계

## 4.1. 모델 파이프라인의 구성

> `[그림 4.1] AI학습 파이프라인 — 아래 흐름을 PPT로 그려 캡처한다.`

```text
[원천]                [교사 라벨링]         [전처리]        [학습]         [배포]

job_posting      ┐                                       ┌─ 모델 A ─┐
job_posting_     ├──▶ Claude 교사 A ──▶ match-v1 ────────┤  랭커     ├──▶ 아티팩트 A
  requirement    │    (프로필×공고)       마스킹·특징      └──────────┘        │
record           ┤                                                             │
  (퍼스널 데이터) │                                        ┌─ 모델 B ─┐        │
                 └──▶ Claude 교사 B ──▶ record-v1 ────────┤  랭커     ├──▶ 아티팩트 B
사람 검수 300쌍 ─────────┘  (공고×기록)                    └──────────┘        │
      │                                                          │             │
      └──── 교사 신뢰도 측정 ────────────────────────── 검증 · 승인 ────────────┘
                                                                 │
                                    ┌────────────────────────────┴──────────────┐
                                    ▼                                           ▼
                        [AI서비스] 공고 목록 정렬                  [AI서비스] 기록 목록 정렬
                          화면 00 · 06 · 00b                            화면 01b
                              │                                           │
                        모델 없음 → match-score.ts               모델 없음 → 규칙 기반 정렬
```

### 단계별 책임

| 단계 | 입력 | 출력 | 실행 위치 |
| --- | --- | --- | --- |
| 교사 라벨링 | 실물 공고 · 프로필 | 라벨 각 20,000쌍 | AI학습서버 (Batch API) |
| 사람 검수 | 표본 각 300쌍 | 교사 신뢰도 κ | 팀 |
| 마스킹 · 특징추출 | 원문 쌍 | 22 / 34차원 벡터 | AI학습서버 |
| 학습 | train 분할 | 모델 후보 | AI학습서버 |
| 검증 | valid · test | 성능 지표 | AI학습서버 |
| 승인 | 성능 지표 | 배포 여부 | AI학습서버 |
| 서빙 A | 프로필 × 공고 | 적합도 + 축별 내역 | AI서비스 |
| 서빙 B | 공고 × 기록 | 적합도 + 순위 | AI서비스 |

**특징추출 코드는 학습과 서빙이 같은 것을 씁니다.** 두 곳에 따로 구현하면 특징 값이
달라지고, 그 차이는 성능 저하로만 드러나 원인을 찾기 어렵습니다.

**임베딩 캐시가 모델 A의 서빙을 가능하게 합니다.** 공고 임베딩은 수집 시 한 번,
프로필 임베딩은 기록이 바뀔 때만 다시 계산합니다. 목록 렌더 시점에는 캐시된 벡터로
특징만 조립합니다.

## 4.2. AI학습 알고리즘 선정

### 두 문제의 성격

| | 모델 A | 모델 B |
| --- | --- | --- |
| 입력 | 22차원 실수 벡터 | 34차원 실수 벡터 |
| 출력 | 적합도 0–100 (순위가 목적) | 적합도 0–100 (순위가 목적) |
| 목적 | 같은 사용자의 공고들을 **줄 세우기** | 한 공고에 대해 내 기록을 **줄 세우기** |
| 지연 예산 | 밀리초 | 밀리초 |

### 후보 비교

| 방식 | 모델 A | 모델 B |
| --- | --- | --- |
| 규칙 기반 (현행) | baseline — 문자열 포함 | baseline — 토큰 겹침 순 정렬 |
| 로지스틱 회귀 | 보조 baseline | 보조 baseline |
| 그래디언트 부스팅 | **채택** (LambdaMART 랭킹 목적함수) | **채택** (LambdaMART 랭킹 목적함수) |
| 딥러닝 (MLP·Transformer) | 표본 20,000행에 과적합 | 같음 |
| 교차 인코더 (BERT류) | 쌍마다 추론 — 목록 지연 예산 초과 | 가능하나 학습 비용 큼 |

### 선정

**둘 다 그래디언트 부스팅(LightGBM) 랭커입니다. 무엇을 줄 세우는지만 다릅니다.**

| | 모델 A | 모델 B |
| --- | --- | --- |
| objective | `lambdarank` | `lambdarank` |
| 그룹 단위 | 프로필 1명의 공고 묶음 | 공고 1건의 기록 묶음 |
| 평가 지표 | NDCG@10 | NDCG@10 |

**공통 근거**

| 근거 | 설명 |
| --- | --- |
| 표본 규모 | 수천~수만 행의 표 형식 데이터에서 가장 안정적입니다 |
| 특징 성격 | 연속·이산·원핫이 섞이고 스케일이 다릅니다. 트리는 스케일에 둔감합니다 |
| 결측 처리 | 결측을 분기 조건으로 다룹니다. 기간·수치가 없는 기록이 많습니다 |
| 서빙 속도 | 단일 트리 추론이 밀리초입니다. 모델 A의 목록 지연 예산을 만족합니다 |
| 설명 가능성 | 특징 중요도와 SHAP으로 축별 사유를 낼 수 있습니다 |
| 학습 비용 | 단일 CPU로 수 분. GPU가 필요 없습니다 |

**모델 A에 랭킹 목적함수를 쓰는 이유**는, 절대 점수가 아니라 **순서**가 제품이 쓰는
값이기 때문입니다. 목록은 정렬되고, Home은 상위 몇 건만 보여줍니다. 모든 공고의 점수를
5점씩 낮게 매겨도 순서가 맞으면 제품은 정상입니다.

**교차 인코더를 뺀 이유**는 지연입니다. 공고 200건에 쌍마다 인코더를 돌리면 목록 하나에
수 초가 걸립니다. 임베딩을 미리 캐시하고 GBM으로 조립하는 편이 같은 신호를 훨씬 싸게
씁니다.

### 왜 모델을 둘로 두는가

모델 B가 기록마다 적합도를 내므로, 그 값을 모으면 공고 하나의 일치도를 만들 수
있습니다. 그런데도 모델 A를 따로 두는 것은 **기록 하나하나에는 없는 신호**를
쓰기 때문입니다.

| 특징 | 무엇을 보는가 |
| --- | --- |
| `years_gap` | 공고 요구 연차와 내 총 경력의 차 |
| `record_count` | 내 기록이 몇 건인가 |
| `posting_req_count` | 공고 요건이 몇 개인가 |
| `category_profile` | 내 주 직군 |

기록별 적합도의 평균만으로는 요건 스무 개 중 셋을 채운 공고와 요건 셋을 모두
채운 공고가 같아 보입니다. 모델 A는 나와 공고 전체를 함께 봅니다.

### 요건 충족 판정은 학습 모델이 하지 않습니다

요건마다 `covered` · `partial` · `missing`을 가리는 것은 **외부 LLM**이 맡습니다
(공고 분석 단계). 학습 모델 둘은 순서만 냅니다.

판정과 순서를 한 모델에 맡기지 않는 이유는 근거 때문입니다. 판정에는 원문의
어느 대목을 보고 그렇게 정했는지가 따라와야 하고, 그건 원문을 읽는 쪽이 낼 수
있습니다. 트리 모델은 특징 기여도만 냅니다.

### 설명 가능성이 필요한 이유

두 모델의 출력이 모두 사용자에게 그대로 보입니다. 판정 자체가 화면이 되고,
그 옆에 근거가 함께 붙습니다.

- 모델 A → 화면 06 목록 정렬(T2.3.1). 근거는 축별 충족 내역(T2.3.3)
- 모델 B → 화면 01b 재료 자동 선택(T4.1.1). 근거는 "이 기록을 왜 뺐는가"(T4.1.3 제외 사유 제시)

근거를 댈 수 없는 판정은 제품에서 쓸 수 없습니다. 정확도만 높은 모델보다 정확도가 조금
낮아도 근거를 낼 수 있는 모델을 택합니다.

### 임베딩은 학습하지 않습니다

의미 유사도 특징을 만드는 문장 임베딩은 사전학습 다국어 모델을 그대로 씁니다. 20,000행으로
임베딩을 파인튜닝하면 무너집니다. 두 모델이 같은 임베딩을 공유하므로 캐시도 공유합니다.

## 4.3. AI학습 파라미터 설정

### 모델 A — LightGBM 랭커

| 파라미터 | 값 | 선정 근거 |
| --- | --- | --- |
| `objective` | `lambdarank` | 순서가 제품이 쓰는 값 |
| `metric` | `ndcg` | `ndcg_eval_at = [5, 10]` |
| `label_gain` | `[0, 1, 3]` | 낮음·중간·높음. 높음의 이득을 크게 |
| `num_leaves` | 31 | 20,000행에서 기본값 이상은 과적합 |
| `max_depth` | 6 | 22차원 입력에 상호작용 6단계 |
| `learning_rate` | 0.05 | 낮추고 트리 수로 보완 |
| `n_estimators` | 500 | early stopping이 실제 개수를 정함 |
| `early_stopping_rounds` | 50 | 검증 NDCG가 50회 개선 없으면 중단 |
| `min_child_samples` | 30 | 잎 하나가 30행 미만이면 잡음을 학습 |
| `subsample` · `colsample_bytree` | 0.8 | 과적합 억제 |
| `random_state` | 42 | 재현성 |

### 모델 B — LightGBM 랭커

| 파라미터 | 값 | 선정 근거 |
| --- | --- | --- |
| `objective` | `lambdarank` | 순서가 제품이 쓰는 값 |
| `metric` | `ndcg` | `ndcg_eval_at = [5, 10]` — 재료 고르기가 상위 여덟 건을 씀 |
| `label_gain` | `[0, 1, 3]` | 낮음·중간·높음. 높음의 이득을 크게 |

| `max_depth` | 6 | 34차원 입력 |
| `learning_rate` | 0.05 | |
| `n_estimators` | 500 | early stopping |
| `min_child_samples` | 30 | |
| `random_state` | 42 | 재현성 |

그룹은 **공고 1건에 딸린 기록 묶음**입니다. 모델 A의 그룹이 프로필 1명의 공고
묶음인 것과 짝입니다.

### 탐색 범위 (공통)

| 파라미터 | 범위 | 방법 |
| --- | --- | --- |
| `num_leaves` | 15 – 63 | 격자 |
| `max_depth` | 4 – 8 | 격자 |
| `learning_rate` | 0.01 – 0.1 | 로그 균등 |
| `min_child_samples` | 10 – 50 | 격자 |

5-겹 교차검증으로 탐색하되, **겹은 프로필 단위로 나눕니다**(3.3과 같은 이유).

### 교사 파라미터

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 교사 모델 | Claude (계약별 기본 티어) | 판정 품질과 비용의 균형 |
| 호출 방식 | Batch API | 50% 할인. 지연이 문제되지 않는 오프라인 작업 |
| 프롬프트 버전 | 데이터세트 메타에 기록 | 프롬프트가 바뀌면 라벨의 성격이 바뀜 |
| 온도 | 기본값 | 교사 판정의 재현성보다 분포의 자연스러움 우선 |

## 4.4. AI학습 모델의 생성

### 학습 절차 (두 모델 공통)

```text
1. 데이터세트 로드      match-v1 / record-v1 의 train 분할
2. 교차검증 탐색        5-겹(프로필 단위), 탐색 범위는 4.3
3. 최적 파라미터 확정    valid 지표 최적
4. 전체 train 재학습     확정 파라미터로 train 전체 학습
5. test 평가            한 번만. 여러 번 보면 test가 valid가 된다
6. 교사·사람 비교        사람 검수 300쌍으로 세 축 비교(9.2)
7. baseline 비교        현행 규칙과 같은 test 분할로 비교
8. 승인 판정            9.2 기준 충족 시 배포 대상
9. 아티팩트 저장         모델 · 특징 명세 · 지표 · 메타데이터
```

5단계를 한 번만 하는 것이 중요합니다. test를 보고 파라미터를 고치면 test 성능이
부풀려집니다.

### 산출물

| 파일 | 내용 |
| --- | --- |
| `model.txt` | LightGBM 모델 |
| `feature_spec.json` | 특징 순서 · 이름 · 스케일링 파라미터 |
| `metrics.json` | test 성능 · ROC 좌표 · baseline · 교사 비교 |
| `metadata.json` | 데이터세트 버전 · 교사 모델 · 프롬프트 버전 · 학습 시각 · 코드 커밋 |

`feature_spec.json`이 모델과 함께 배포되어야 합니다. 서빙 시 특징 순서가 어긋나면 모델은
오류 없이 **조용히 틀린 답**을 냅니다.

### 모델 버전

| 항목 | 규칙 |
| --- | --- |
| 버전 형식 | `match-{데이터세트}-{일련번호}` · `record-{데이터세트}-{일련번호}` |
| 예 | `match-v1-003` · `record-v1-002` |
| 배포 단위 | 모델별로 한 번에 하나의 버전만 활성 |
| 독립성 | A와 B는 따로 배포·롤백됩니다 |
| 보관 | 각 최근 5개 버전 |

### 서비스에서의 사용

> `[그림 4.2] 두 모델의 서비스 적용 — 아래를 PPT로 그려 캡처한다.`

```text
[모델 A — 공고 목록을 열 때]
  공고 목록 요청
     ├─▶ 캐시된 공고 임베딩 + 프로필 임베딩
     ├─▶ 특징 조립 (a1–a14)
     ├─▶ 모델 있음 ─▶ 랭커 ─▶ 적합도 + 축별 내역 ─▶ match_score 저장
     └─▶ 모델 없음 ─▶ calculateExplainableMatch() 폴백
                              ▼
                    화면 06 목록 정렬 (T2.3.1)
                    화면 00 추천 공고 (T11.1.1)

[모델 B — 재료 고르기를 열 때]
  기록 목록 요청
     ├─▶ 공고 × 사용자 기록 쌍 생성
     ├─▶ 특징 추출 (b1–b18, feature_spec.json 순서)
     ├─▶ 모델 있음 ─▶ 랭커 ─▶ 적합도 + topFeatures
     └─▶ 모델 없음 ─▶ 규칙 기반 정렬 폴백
                              ▼
                    화면 01b 재료 자동 선택 (T4.1.1)
                    화면 01b 제외 사유 제시 (T4.1.3)

  요건별 충족(화면 01 · T3.2.2)은 공고 분석 단계에서 외부 LLM이 판정해
  requirement_coverage 에 저장한 값을 그대로 씁니다.
```

### 신뢰도 임계값

**모델 B** — 순위가 목적이라 모델 A와 같은 방식으로 다룹니다.

| 상황 | 처리 |
| --- | --- |
| 상위와 하위의 적합도 차가 5점 미만 | 자동 선택을 멈추고 사용자에게 고르게 함 |
| 기록이 8건 미만 | 모델을 쓰지 않고 전부 선택 — 줄 세울 것이 없음 |

**모델 A** — 순위가 목적이라 임계값의 의미가 다릅니다.

| 상황 | 처리 |
| --- | --- |
| 요구사항을 하나도 못 읽은 공고 | 점수를 내지 않고 `null` (현행 규칙과 동일) |
| 상위와 하위의 점수 차가 5점 미만 | "비슷한 공고" 로 묶어 표시 |
| 프로필 기록이 3건 미만 | 모델을 쓰지 않고 최신순 정렬 — 학습 분포 밖 |

세 번째가 중요합니다. 기록이 거의 없는 신규 사용자는 학습 데이터에 없던 입력입니다.
