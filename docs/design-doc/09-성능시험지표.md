# 9. 성능시험지표

## 9.1. AI서비스 성능평가지표

### 지표 1 — 근거 없는 수치 차단율

| 평가항목 | 단위 | 개발목표치 | 평가방법 |
| --- | --- | --- | --- |
| 근거 없는 수치 차단율 | % | 100 | 팀 자체시험 |

| 항목 | 내용 |
| --- | --- |
| **시험내용** | 포트폴리오 생성 결과에 사용자 기록에 없는 수치가 섞여 나가는지 측정한다. 이 서비스는 채용 문서를 만들기 때문에, 지어낸 수치가 단 한 건이라도 공개되면 사용자에게 실질적 피해가 간다. 따라서 목표치는 100%다. 근거에 없는 수치를 심어 둔 입력을 생성기에 넣고, 검증 단계가 모두 거부하는지 확인한다. |
| **시험환경** | 1. 근거 수치가 명시된 경력 기록 세트<br>2. 수치를 지어내도록 유도하는 프롬프트 입력 50건<br>3. `validateGenerationOutput()`이 포함된 생성 경로<br>4. 결과를 확인할 로그 |
| **시험절차** | 1. 기록에 수치가 3개 있는 레시피를 준비한다.<br>2. 기록에 없는 수치를 포함하도록 유도하는 입력 50건을 만든다.<br>3. 각 입력으로 생성을 실행한다.<br>4. 생성 결과에 기록에 없는 수치가 있는지 검사한다.<br>5. 50건 모두 `GEN_UNGROUNDED_NUMBER`로 거부되면 통과다. 1건이라도 통과하면 실패다. |

### 지표 2 — 퍼스널 데이터–공고 연결 품질

| 평가항목 | 단위 | 개발목표치 | 평가방법 |
| --- | --- | --- | --- |
| 공고 추천 순위 품질 (모델 A · NDCG@10) | — | ≥ 0.80 | 팀 자체시험 |
| 요건 충족 판정 정확도 (모델 B · 매크로 F1) | % | ≥ 70 | 팀 자체시험 |

| 항목 | 내용 |
| --- | --- |
| **시험내용** | 사용자 기록과 채용 공고를 잇는 두 방향을 각각 측정한다. 모델 A는 "이 사람에게 맞는 공고"의 순위가 사람의 판단과 얼마나 맞는지, 모델 B는 "이 공고에 쓸 기록"의 충족 판정이 얼마나 맞는지를 본다. 두 모델 모두 현행 문자열 매칭 구현이 baseline이다. 상세 지표와 승인 기준은 9.2에 있다. |
| **시험환경** | 1. `match-v1` · `coverage-v1` 데이터세트의 test 분할<br>2. 학습된 랭커와 분류기<br>3. 규칙 기반 구현 두 개 (`match-score.ts` · `coverage.ts`)<br>4. 사람이 검수한 각 300쌍<br>5. 평가 스크립트 |
| **시험절차** | 1. test 분할을 로드한다(학습·검증에 쓰이지 않은 것).<br>2. 규칙 기반으로 전량 판정하고 지표를 구한다(baseline).<br>3. 학습 모델로 전량 판정하고 같은 지표를 구한다.<br>4. 사람 검수 300쌍에서 학생·교사·규칙을 함께 비교한다.<br>5. 모델 A NDCG@10 ≥ 0.80, 모델 B 매크로 F1 ≥ 70%이고 둘 다 baseline보다 높으면 통과다. |

### 지표 3 — 포트폴리오 생성 성공률

| 평가항목 | 단위 | 개발목표치 | 평가방법 |
| --- | --- | --- | --- |
| 포트폴리오 생성 성공률 | % | ≥ 90 | 팀 자체시험 |

| 항목 | 내용 |
| --- | --- |
| **시험내용** | 생성 요청이 사용 가능한 포트폴리오로 끝나는 비율을 측정한다. 실패에는 LLM 오류, 근거 검증 실패, 빌드 실패, 타임아웃이 모두 포함된다. 근거 검증 실패는 지표 1의 관점에서는 성공이지만 사용자 관점에서는 실패이므로, 두 지표를 함께 봐야 한다. |
| **시험환경** | 1. 서로 다른 직군의 공고 20건<br>2. 기록이 10건 이상인 사용자 계정 5개<br>3. 실제 LLM 프로바이더(픽스처 아님)<br>4. 생성 작업 로그 |
| **시험절차** | 1. 공고 20건 × 계정 5개 = 100건의 생성을 실행한다.<br>2. 각 생성의 최종 상태를 기록한다.<br>3. 실패 건은 사유별로 분류한다.<br>4. 90건 이상이 `done`이면 통과다. |

## 9.2. AI학습 성능(ROC)

두 모델을 각각 측정합니다. **재는 것이 서로 다르므로 지표도 다릅니다.**

### 모델 A — 공고 추천 랭커

순위가 목적이므로 순위 지표를 주로 보되, 양식이 요구하는 ROC를 위해 **"적합(높음) 대
나머지"** 이진 분류로도 잽니다.

| 지표 | 재는 것 |
| --- | --- |
| NDCG@10 | 상위 10건의 순서가 교사 판단과 얼마나 맞는가 |
| MAP | 전체 순위 품질 |
| AUC (높음 vs 나머지) | 이진 판정으로서의 분별력 |

> `[그림 9.1] 모델 A의 ROC 곡선 — 높음 vs 나머지. 규칙 baseline의 동작점을 점으로 함께 찍는다.`

### 모델 B — 요구사항 충족 분류기

3분류이므로 **OvR(One-vs-Rest) ROC**를 클래스마다 그립니다.

| 곡선 | 양성 | 음성 |
| --- | --- | --- |
| covered vs rest | covered | partial + missing |
| partial vs rest | partial | covered + missing |
| missing vs rest | missing | covered + partial |

> `[그림 9.2] 모델 B의 ROC 곡선 3개 — 한 그래프에 그리고 각 AUC를 범례에 적는다.`
>
> `[그림 9.3] 모델 B의 혼동 행렬 3×3 — 어떤 오분류가 많은지 보인다.`

### 세 축으로 잽니다 — 증류의 함정을 피하려고

**라벨의 출처가 Claude이므로, 학생이 교사를 잘 흉내 낸다는 것과 판정이 옳다는 것은 다른
말입니다.** 교사가 체계적으로 틀리면 학생이 그대로 배우고 AUC는 높게 나옵니다. 그래서
숫자를 셋 나란히 놓습니다.

| 축 | 비교 대상 | 표본 | 답하는 질문 |
| --- | --- | --- | --- |
| 1 | 학생 ↔ 교사 | test 분할 3,000쌍 | 증류가 성공했는가 |
| 2 | 교사 ↔ 사람 | 사람 검수 300쌍 | 교사를 믿어도 되는가 |
| 3 | **학생 ↔ 사람** | 같은 300쌍 | **실제로 쓸 만한가** |
| 4 | 규칙 ↔ 사람 | 같은 300쌍 | 지금보다 나아졌는가 |

**3번이 실제로 답해야 할 질문이고, 4번이 그 비교 대상입니다.** 1번만 높고 3번이 낮으면
교사가 틀린 것이고, 그때는 학습이 아니라 교사 프롬프트를 고쳐야 합니다.

### 배포 승인 기준

**모델 A**

| 지표 | 기준 | 근거 |
| --- | --- | --- |
| NDCG@10 (학생 ↔ 교사) | ≥ 0.80 | 증류 성공의 하한 |
| AUC (높음 vs 나머지) | ≥ 0.85 | 이진 분별력 |
| 학생 ↔ 사람 일치도 | 규칙 대비 상대 개선 ≥ 20% | 제품이 나아졌다는 증거 |
| 서빙 지연 (공고 200건) | ≤ 50ms | 목록 렌더 예산 |

**모델 B**

| 지표 | 기준 | 근거 |
| --- | --- | --- |
| 매크로 AUC (학생 ↔ 교사) | ≥ 0.85 | 3분류 실용 하한 |
| covered vs rest AUC | ≥ 0.88 | 가장 중요한 클래스 |
| 매크로 F1 (학생 ↔ 사람) | ≥ 0.70 | 사람 기준 실용성 |
| **covered → missing 오분류율** | ≤ 2% | 아래 설명 |
| baseline 대비 매크로 F1 | 상대 개선 ≥ 15% | 복잡한 모델을 쓸 이유 |

**공통 게이트**

| 지표 | 기준 |
| --- | --- |
| 교사 ↔ 사람 일치도 (κ) | ≥ 0.6 |

κ가 0.6 미만이면 **모델을 배포하지 않고 교사 프롬프트부터 고칩니다.** 교사가 사람과
어긋난 상태에서 학생을 아무리 잘 학습시켜도 제품은 나아지지 않습니다.

### covered → missing 오분류에 별도 기준을 두는 이유

3분류 오류가 모두 같은 무게를 갖지 않습니다.

| 오분류 | 사용자에게 일어나는 일 | 심각도 |
| --- | --- | --- |
| covered → partial | 근거 있는 기록이 "부분 충족"으로 표시됩니다 | 낮음 |
| partial → covered | 약한 근거가 강조됩니다 | 중간 |
| **covered → missing** | **실제로 갖춘 역량이 "없음"으로 표시됩니다** | **높음** |
| missing → covered | 없는 역량을 있다고 보여줍니다 | 높음 |

`covered → missing`은 사용자가 실제로 가진 강점을 포트폴리오에서 빼게 만듭니다. 그리고
사용자는 그것이 빠졌다는 사실조차 모릅니다.

### 측정 절차

```text
1. test 분할 로드         3.3의 15%. 학습·탐색에 쓰이지 않은 것
2. 학생 예측              모델 A: 점수 / 모델 B: 클래스별 확률
3. ROC 산출               A: 높음 vs 나머지 / B: OvR 3곡선
4. AUC 산출               클래스별 + 매크로
5. 순위 지표 산출          모델 A: NDCG@10 · MAP
6. 혼동 행렬              모델 B: 3×3
7. 사람 검수분 비교        학생·교사·규칙을 같은 300쌍에서 비교
8. baseline 산출          규칙은 확률이 없으므로 동작점 1개만 찍는다
9. 승인 판정              위 기준 전부 충족 여부
```

8단계에 주의합니다. 규칙 기반 판정은 확률을 내지 않으므로 ROC 곡선을 그릴 수 없습니다.
곡선 대신 (FPR, TPR) 점 하나로 찍고, 모델의 곡선이 그 점 위를 지나는지 봅니다.
