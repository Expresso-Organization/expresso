# 9. 성능시험지표

## 9.1. AI서비스 성능평가지표

### 지표 1 — 포트폴리오 제작 흐름

제안서의 사용자 편의 목표에 따라, 커리어 기록 재사용과 공고별 포트폴리오 제작을 평가한다.

| 평가항목 | 단위 | 현재 상태 | 평가방법 |
| --- | --- | --- | --- |
| 공고 선택부터 포트폴리오 배포까지의 완료율 | % | 기준선 측정 전 | 사용자 시나리오 시험 |
| 공고별 포트폴리오 제작 소요 시간 | 분 | 기준선 측정 전 | 시작·완료 시각 기록 |
| AI 대화 답변의 커리어 기록 재사용 | 건 | 기준선 측정 전 | 저장·선택 이력 확인 |

같은 사용자 기록으로 여러 공고의 포트폴리오를 만들게 하고, 자료 재수집과 경험 선택·수정에 걸린 시간을 기록한다. 현재 측정값과 목표치는 사용자 시나리오 시험 후 확정한다.

### 지표 2 — 공고·기록 추천 품질

| 평가항목 | 단위 | 현재 상태 | 평가방법 |
| --- | --- | --- | --- |
| 공고 추천 순위 품질 | NDCG@10 | 학습 모델 측정 전 | 규칙 기반·Bi-Encoder+MLP·Cross-Encoder 비교 |
| 공고 후보 선별 성능 | Recall@K | 학습 모델 측정 전 | 선별 후보에서 적합 공고 유지율 |
| 적합도 점수 오차 | MAE | 학습 모델 측정 전 | 루브릭 점수 대비 절대 오차 |
| 공고쌍 순서 일치율 | % | 학습 모델 측정 전 | 같은 프로필의 공고쌍 비교 |
| 기록 추천 순위 품질 | NDCG@10 | 학습 모델 측정 전 | 공고별 기록 순위와 사람 평가 비교 |

공고 추천은 3장에서 계획한 평가 700쌍을 사용한다. 기록 추천 데이터셋과 평가 규모는 라벨 구축 후 확정한다. 지표 정의와 모델 비교 절차는 9.2에 기술한다.

### 지표 3 — 포트폴리오 생성 성공률

| 평가항목 | 단위 | 개발목표치 | 평가방법 |
| --- | --- | --- | --- |
| 포트폴리오 생성 성공률 | % | ≥ 90 | 팀 자체시험 |

| 항목 | 내용 |
| --- | --- |
| **시험내용** | 생성 요청이 사용 가능한 포트폴리오로 끝나는 비율을 측정한다. 실패에는 LLM 오류, 근거 검증 실패, 빌드 실패, 타임아웃이 모두 포함된다. 근거 검증 실패는 생성 품질 점검에 기록하고, 사용자 관점의 생성 실패에도 포함한다. |
| **시험환경** | 1. 서로 다른 직군의 공고 20건<br>2. 기록이 10건 이상인 사용자 계정 5개<br>3. 실제 LLM 프로바이더(픽스처 아님)<br>4. 생성 작업 로그 |
| **시험절차** | 1. 공고 20건 × 계정 5개 = 100건의 생성을 실행한다.<br>2. 각 생성의 최종 상태를 기록한다.<br>3. 실패 건은 사유별로 분류한다.<br>4. 90건 이상이 `done`이면 통과다. |

### 지표 4 — 응답 시간

| 평가항목 | 단위 | 개발목표치 | 평가방법 |
| --- | --- | --- | --- |
| 대표 read 경로 p95 | ms | ≤ 300 | 자동화 시험 |
| 대표 write 경로 p95 | ms | ≤ 300 | 자동화 시험 |
| 이벤트 수집 p95 | ms | ≤ 150 | 자동화 시험 |
| 큐 등록 p95 | ms | ≤ 200 | 자동화 시험 |

| 항목 | 내용 |
| --- | --- |
| **시험내용** | 동기 경로가 예산 안에서 응답하는지 측정한다. 비동기로 넘긴 작업(생성·분석·내보내기)은 이 예산의 대상이 아니다. 시험은 매 실행마다 p95를 다시 계산하고, 예산을 넘으면 실패로 처리한다. |
| **시험환경** | 로컬 Docker MongoDB 8.0 단일 노드 replica set + Redis, 독립된 성능 시험 데이터베이스 |
| **시험절차** | 1. `GET /v1/home` 100회<br>2. `POST /v1/career/records` 40회<br>3. 익명 이벤트 수집 60회<br>4. 집계 큐 등록 40회<br>5. 각 경로의 p95를 예산과 비교한다. |

2026-09-28 현재 코드의 MongoDB 로컬 시험에서 p95는 읽기 4.56ms(100회), 기록 쓰기
8.01ms(40회), 방문 이벤트 4.88ms(60회), 큐 등록 5.30ms(40회)였다. 읽기 100건의
동시 요청은 109.20ms가 걸렸다. 공고 1,000건 목록은 77.85ms, 9MiB 스냅샷 10조각의
쓰기·읽기는 114.99ms·54.11ms였다. 독립된 임시 MongoDB 테스트 데이터베이스에서
`pnpm --filter @expresso/editor build` 후
`EXPRESSO_LOAD_TEST=1 node scripts/test-infra.mjs test/load/performance-budget.test.ts --disableConsoleIntercept`를
실행했고 3개 시험이 통과했다. 이 값은 운영 트래픽의 보장값이 아니다.

## 9.2. AI학습 성능 및 모델 비교

이 절은 제안서의 성능 평가 지표를 따른다. 현재 학습 아티팩트가 없어 모델 성능의 실측값은 없다. 9.1의 MongoDB 로컬 시험값은 서비스 API의 측정값이며 학습 모델의 추론 성능으로 사용하지 않는다.

| 비교 대상 | 역할 | 상태 |
| --- | --- | --- |
| 현재 규칙 기반 추천 | 제품 기준선 | 구현됨, 동일 평가셋의 순위 지표 미측정 |
| Bi-Encoder+MLP | 전체 공고 후보 선별 | 학습·평가 전 |
| Cross-Encoder | 선별 후보 재정렬 | 학습·평가 전 |
| 기록 추천 모델 | 지원 공고에 쓸 기록 정렬 | 학습 구조·평가셋 확정 전 |

| 지표 | 평가 질문 | 적용 단계 |
| --- | --- | --- |
| NDCG@10 | 적합한 공고가 상위에 배치되는가 | 선별·재정렬·최종 추천 |
| Recall@K | 선별 단계에서 관련 공고를 충분히 남기는가 | Bi-Encoder+MLP |
| MAE | 예측 점수가 교사 루브릭 점수와 얼마나 다른가 | 두 적합도 모델 |
| 공고쌍 순서 일치율 | 같은 프로필의 더 적합한 공고에 높은 점수를 주는가 | 두 적합도 모델 |
| p95 지연·처리량 | 추천 요청의 처리 시간과 단위 시간당 처리량은 얼마인가 | 온라인 추론 |
| 임베딩 생성 시간·메모리·저장 용량 | 인코더 교체의 비용은 얼마인가 | 임베딩 모델 비교 |

Recall@K는 후보 풀의 크기가 K보다 크고 관련성 기준이 정해진 평가셋에서 측정한다. 공고쌍은 같은 프로필에서 루브릭 점수 차이가 5점 이상인 경우로 구성한다. 교사 점수만 정답으로 취급하면 교사 오류를 놓치므로, 사람 평가 표본에서 교사·학습 모델·현재 규칙을 함께 비교한다.

평가 700쌍은 학습과 설정 결정에 사용하지 않는다. `multilingual-e5-base`, `KURE-v1`, `BGE-M3`, `Qwen3-Embedding-0.6B`는 같은 데이터 분할과 지표로 비교한다. Bi-Encoder+MLP 단독, Cross-Encoder 재정렬, 현재 규칙 기반 추천의 품질과 처리 비용을 함께 기록한다. 기록 추천은 별도 평가셋을 만들고 같은 순위 평가 절차를 적용한다.

| 결과 항목 | 규칙 기반 | Bi-Encoder+MLP | Cross-Encoder | 기록 추천 |
| --- | --- | --- | --- | --- |
| NDCG@10 | 측정 전 | 측정 전 | 측정 전 | 측정 전 |
| Recall@K | 해당 없음 | 측정 전 | 해당 없음 | 설계 후 측정 |
| MAE | 해당 없음 | 측정 전 | 측정 전 | 설계 후 측정 |
| 공고쌍 순서 일치율 | 측정 전 | 측정 전 | 측정 전 | 해당 없음 |
| p95 지연·처리량 | 측정 전 | 측정 전 | 측정 전 | 측정 전 |

제안서는 지표를 제시하지만 배포 합격 수치는 정하지 않았다. 수치 기준은 규칙 기반의 동일 평가셋 결과와 사용자 시나리오 시험을 확인한 뒤 정한다.
