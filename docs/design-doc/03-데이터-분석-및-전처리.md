# 3. 데이터 분석 및 전처리

## 학습 과제 — 퍼스널 데이터와 채용 공고를 잇는 두 방향

Expresso의 모든 생성은 **사용자 기록과 채용 공고를 연결하는 일**에서 시작합니다. 그
연결을 두 방향으로 학습합니다.

```text
                    ┌──────────────── 모델 A ────────────────┐
                    │  기록 → 공고                            │
사용자 기록 ────────┤  "이 사람에게 맞는 공고는 무엇인가"      ├──▶ 공고 추천 · 목록 정렬
  (퍼스널 데이터)   │  프로필 1건 × 공고 N건 → 순위            │
                    └────────────────────────────────────────┘

                    ┌──────────────── 모델 B ────────────────┐
                    │  공고 → 기록                            │
채용 공고 ──────────┤  "이 공고에 쓸 기록은 무엇인가"          ├──▶ 요건 충족 판정 · 재료 추천
                    │  요구사항 1건 × 기록 M건 → 충족 판정     │
                    └────────────────────────────────────────┘
```

두 모델 모두 **지금 문자열 부분일치로 대체되어 있습니다.** 그 두 함수가 그대로 성능
baseline이 됩니다.

| 모델 | 현행 구현 | 판정 방법 |
| --- | --- | --- |
| A | `jobs/match-score.ts` `calculateExplainableMatch()` | `source.includes(normalized(item))` |
| B | `job-analysis/coverage.ts` `calculateRequirementCoverage()` | 요구사항 토큰이 기록에 전부 있는가 |

### 왜 하나가 아니라 둘인가

두 방향은 같은 관련도를 보지만 **서빙 제약이 다릅니다.** B를 집계해서 A를 만들 수
없습니다.

| | 모델 A | 모델 B |
| --- | --- | --- |
| 호출 시점 | 공고 목록을 열 때마다 | brew 하나당 한 번 |
| 한 번에 평가할 쌍 | 공고 200건 × 1 = **200회** | 요구사항 8개 × 기록 50개 = **400회** |
| B로 A를 만들면 | 200 × 400 = **8만 회** | — |
| 지연 요구 | 밀리초 (목록 렌더) | 초 (비동기 작업 안) |
| 무효화 | 기록 1건 수정 시 전 공고 점수 | 해당 brew만 |
| 입력 단위 | 프로필 요약 × 공고 요약 (거친 판정) | 요구사항 × 기록 (세밀한 판정) |

목록 한 화면에 8만 회 평가는 사전 계산으로도 감당되지 않습니다. 기록 한 줄만 고쳐도
전부 낡기 때문입니다. **A는 거칠고 빠르게, B는 세밀하고 느리게** — 이것이 두 모델을
나누는 이유입니다.

### 제품에서 쓰이는 자리

| 모델 | 화면 | 태스크 |
| --- | --- | --- |
| A | 00 Home · 추천 공고 | T11.1.1 추천 공고 제시 |
| A | 06 공고 탐색 · 목록 정렬 | T2.3.1 점수 계산 |
| A | 00b 공고 AI 검색 결과 | T2.3.3 축별 충족 내역 |
| B | 01 공고 분석 · 요건별 충족 | T3.2.2 기록 커버리지 판정 |
| B | 01b 재료 고르기 · 자동 선택 | T4.1.1 매칭 순 정렬과 자동 선택 |
| B | 01b 재료 고르기 · 제외 사유 | T4.1.3 제외 사유 제시 |

### 지금 규칙이 실패하는 방식

```text
[모델 B 자리] coverage.ts
  요구사항 "React 기반 프론트엔드 개발 경험"
  → 토큰 react · 기반 · 프론트엔드 · 개발 · 경험
  → 기록에 이 다섯이 전부 있어야 covered

  React로 프론트엔드를 만든 기록도 "기반"이라는 낱말이 없으면 partial로 떨어집니다.

[모델 A 자리] match-score.ts
  요건 문자열이 기록 본문에 그대로 들어 있는지만 봅니다.
  "TypeScript"를 요구하는 공고에 "TS"로만 적은 기록은 0점입니다.
```

두 함수 모두 **표기가 다르면 못 봅니다.** 의미가 같아도 글자가 다르면 놓칩니다.

## 3.1. 데이터 수집출처 및 수집방법

### 원천 1 — 채용 공고 (크롤링)

수집은 `job_source`에 등록된 소스를 주기적으로 실행해 이뤄집니다. 이미 구현되어
있습니다(`services/backend/src/modules/jobs/ingest/`).

| 항목 | 내용 |
| --- | --- |
| 수집 대상 | 국내 개발·디자인 직군 채용 공고 |
| 수집 방식 | 소스별 어댑터가 목록 조회 후 상세 파싱 |
| 저장 위치 | `job_posting` · `company` |
| 중복 제거 | 원본 URL, 정규화된 제목·회사 조합 |
| 목표 규모 | 공고 3,000건 이상 |

> `[그림 3.1] 공고 수집 출처 — 수집 대상 사이트의 목록/상세 화면과 제공 정보를 캡처한다.`

### 원천 2 — 공고에서 추출한 요구사항

공고 본문을 그대로 쓰지 않습니다. LLM이 역량 항목 단위로 쪼갠 결과
(`job_posting_requirement`)를 씁니다. 추출은 구현되어 있습니다.

| 필드 | 설명 |
| --- | --- |
| `label` | 역량 항목 (예: "React 기반 프론트엔드 개발 경험") |
| `axis` | `technology` / `impact` / `role` / `conditions`. 널 허용 |
| `kind` | `must` / `nice` / `tone` |
| `source_span` | 공고 원문에서 인용한 구간 |

### 원천 3 — 사용자 기록 (퍼스널 데이터)

실사용자가 없으므로 두 경로로 확보합니다.

1. **동의받은 실제 이력서** — 팀원과 지인의 이력서·포트폴리오를 기록 형식으로 옮깁니다.
2. **공개 이력서·기술 블로그의 프로젝트 서술** — 정규화하고 원문 링크를 남깁니다.
   재배포하지 않습니다.

| 항목 | 목표 |
| --- | --- |
| 프로필 수 | 60명 이상 |
| 프로필당 기록 수 | 10건 이상 |
| 직군 분포 | 백엔드 · 프론트엔드 · 데이터 · 디자인 각 15명 이상 |

직군을 고르게 모으는 것이 규모보다 중요합니다. 백엔드만으로 학습하면 디자인 직군에서
무너집니다.

### 원천 4 — 라벨 (LLM 교사)

**사람이 수만 쌍을 라벨링할 수 없습니다.** Claude를 교사로 써서 라벨을 만들고, 소형
모델이 그것을 재현하도록 학습합니다.

```text
공고(실물) × 프로필(실물)
      │
      ├──▶ [교사 A] Claude — 이 사람에게 이 공고가 적합한가       → 모델 A 라벨
      └──▶ [교사 B] Claude — 이 기록이 이 요구사항을 충족하는가   → 모델 B 라벨
```

이것이 이 프로젝트의 **증류(distillation)** 구조입니다. 학습의 목표는 정확도 향상이
아니라 **비용과 지연의 개선**입니다 — 목록 화면에서 공고마다 Claude를 부를 수 없기
때문입니다.

| 항목 | 모델 A | 모델 B |
| --- | --- | --- |
| 교사 입력 | 프로필 요약 + 공고 요약 | 요구사항 1건 + 기록 1건 |
| 교사 출력 | 적합도 0–100 + 축별 충족 + 한 줄 사유 | covered / partial / missing + 사유 |
| 목표 쌍 수 | 20,000 | 20,000 |
| 예상 비용 | Batch API로 $45 – $90 | Batch API로 $45 – $90 |

### 교사를 믿어도 되는지 따로 잽니다

교사가 체계적으로 틀리면 학생이 그대로 배우고, 성능 지표는 높게 나옵니다. 이 함정을
막기 위해 **시험세트의 일부를 사람이 직접 라벨링**합니다.

| 라벨 출처 | 규모 | 쓰임 |
| --- | --- | --- |
| Claude 교사 | 각 20,000쌍 | 학습 · 검증 · 시험 |
| 팀원 합의 | 각 300쌍 | 교사와 사람의 일치도(κ) 측정 |

팀원 2인이 독립 라벨링하고 불일치는 3인이 합의합니다. κ가 0.6 미만이면 판정 기준을 다시
정의합니다.

### 판정 기준

**모델 A — 공고 적합도**

| 구간 | 기준 |
| --- | --- |
| 높음 (70–100) | 필수 요건 대부분을 기록으로 증명할 수 있습니다. 지금 지원할 만합니다. |
| 중간 (40–69) | 핵심 요건 일부가 비어 있으나 인접 경험으로 메울 여지가 있습니다. |
| 낮음 (0–39) | 직무가 다르거나 필수 요건이 대부분 비어 있습니다. |

**모델 B — 요구사항 충족**

| 라벨 | 기준 |
| --- | --- |
| `covered` | 기록이 요구사항의 핵심 역량을 직접 증명합니다. 채용 담당자에게 근거로 제시할 수 있습니다. |
| `partial` | 인접 역량이거나, 증명은 되지만 깊이·기간이 요구 수준에 못 미칩니다. |
| `missing` | 관련이 없습니다. |

## 3.2. 데이터 특징추출 및 특징분포

두 모델은 **같은 전처리와 같은 임베딩을 공유**합니다. 특징 묶음만 다릅니다.

### 공통 전처리

| 순서 | 처리 | 설명 |
| --- | --- | --- |
| 1 | 정규화 | NFKC · 소문자화 · 공백 정리 |
| 2 | 마스킹 | 사람 이름 · 이메일 · 전화번호 · 소속 기업명을 자리표시자로 치환 |
| 3 | 기술 사전 매핑 | `React.js` · `ReactJS` · `리액트` → `react`. 스킬 집계 로직의 사전을 재사용 |
| 4 | 문장 임베딩 | 다국어 모델. 프로필 · 공고 · 기록 · 요구사항 단위로 캐시 |
| 5 | 결측 처리 | 기간 · 수치가 없으면 0으로 채우고 결측 플래그를 함께 둠 |

임베딩을 캐시하는 것이 모델 A의 서빙을 가능하게 합니다. 공고 임베딩은 수집 시 한 번,
프로필 임베딩은 기록이 바뀔 때만 다시 계산합니다.

### 모델 A 특징 — 프로필 × 공고

| 번호 | 특징 | 설명 |
| --- | --- | --- |
| a1 | `cos_profile_posting` | 프로필 요약 ↔ 공고 본문 코사인 유사도 |
| a2 | `cos_skills_requirements` | 스킬 목록 ↔ 요구사항 목록 유사도 |
| a3 | `req_hit_ratio` | 요건 중 프로필 텍스트에 닿는 비율 (현행 규칙과 같은 신호) |
| a4 | `req_hit_ratio_idf` | IDF 가중 버전 |
| a5 | `axis_hit_technology` | 기술 축 충족률 |
| a6 | `axis_hit_impact` | 규모·지표 축 충족률 |
| a7 | `axis_hit_role` | 역할·연차 축 충족률 |
| a8 | `axis_hit_conditions` | 근무 조건 축 충족률 |

### 특징 분포

> `[그림 3.2] 클래스별 특징 분포 — seaborn으로 그린다. 다음 넷을 넣는다.`
>
> - `[3.2a]` 모델 B `idf_weighted_overlap`의 클래스별 히스토그램 — 현행 규칙의 실패 지점

> - `[3.2d]` 특징 간 상관 히트맵 (두 모델 각각)

확인할 것은 셋입니다.

1. **어휘 중첩만으로는 클래스가 겹칩니다.** 이것이 현행 규칙의 실패 원인입니다.
2. **의미 유사도는 겹침이 덜합니다.**
3. **두 신호의 상관이 낮습니다.** 함께 쓰면 단독보다 낫습니다.

셋이 확인되지 않으면 특징 설계를 다시 합니다.

## 3.3. 데이터세트 정의 및 생성

### 데이터세트 둘

| 항목 | `match-v1` (모델 A) | `coverage-v1` (모델 B) |
| --- | --- | --- |
| 단위 | (프로필, 공고) 쌍 | (요구사항, 기록) 쌍 |
| 특징 | 22차원 | 34차원 |
| 라벨 | 적합도 0–100 (+ 3구간 이산화) | covered / partial / missing |
| 목표 규모 | 20,000행 | 20,000행 |
| 사람 검수분 | 300행 | 300행 |
| 저장 형식 | Parquet(특징) + JSONL(원문·메타) | 같음 |

### 행 스키마 (공통)

| 컬럼 | 설명 |
| --- | --- |
| `pair_id` | 쌍 식별자 |
| `left_id` · `right_id` | 프로필/요구사항, 공고/기록 참조 |
| `f1` … `fN` | 특징 |
| `label` | 교사 라벨 |
| `label_source` | `teacher` / `human` / `consensus` |
| `teacher_model` | 교사 모델과 프롬프트 버전 |
| `split` | `train` / `valid` / `test` |
| `dataset_version` | `match-v1` · `coverage-v1` |

`teacher_model`을 남기는 이유는, 교사를 바꾸면 라벨의 성격이 바뀌기 때문입니다. 어떤
교사가 매긴 라벨인지 모르면 두 데이터세트를 비교할 수 없습니다.

### 클래스 균형

무작위 쌍은 대부분 부적합입니다. 그대로 학습하면 **전부 낮은 점수라 답하는 모델이 높은
정확도를 얻습니다.**

| 모델 | 구간 | 목표 비율 | 추출 방법 |
| --- | --- | --- | --- |
| A | 높음 | 25% | 같은 직군 · 스택 겹침 상위 쌍 |
| A | 중간 | 35% | 직군은 같고 스택이 일부 겹치는 쌍 |
| A | 낮음 | 40% | 다른 직군 + 무작위 쌍 혼합 |
| B | covered | 30% | 같은 프로필 기록 중 `max_sent_cos` 상위 |
| B | partial | 35% | 중간 구간 층화 추출 |
| B | missing | 35% | 하위 + 무작위 혼합 |

낮은 쪽에 무작위 쌍을 섞는 이유는, 어려운 음성만 쓰면 쉬운 음성에서 오히려 틀리기
때문입니다.

### 분할

| 분할 | 비율 |
| --- | --- |
| train | 70% |
| valid | 15% |
| test | 15% |

분할은 **프로필 단위와 공고 단위로 동시에** 합니다. 같은 사람의 기록이나 같은 공고의
요구사항이 학습과 시험에 나뉘어 들어가면 모델이 그 사람의 문체나 그 공고의 표현을 외우고,
성능이 실제보다 높게 나옵니다.

### 생성 절차

```text
1. 공고 수집          job_source 실행 → job_posting 3,000건
2. 요구사항 추출       LLM → job_posting_requirement
3. 프로필 구축         이력서 정규화 → record (마스킹)
4. 쌍 생성            A: 프로필 × 공고 / B: 요구사항 × 기록
5. 후보 축소          층화 추출로 각 20,000쌍
6. 교사 라벨링         Claude Batch API
7. 사람 검수          각 300쌍, 팀원 2인 독립 → 합의
8. 특징 추출          3.2의 a1–a14 / b1–b18
9. 분할               프로필 · 공고 단위 그룹 분할
10. 저장              Parquet + JSONL, 버전 태그
```

5단계를 건너뛰면 쌍이 폭발합니다. 프로필 60 × 공고 3,000 = 18만 쌍, 요구사항 24,000 ×
기록 600 = 1,440만 쌍입니다. 교사 비용으로도 감당되지 않습니다.
