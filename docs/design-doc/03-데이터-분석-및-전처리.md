# 3. 데이터 분석 및 전처리

2.1에서 정의한 바와 같이 본 프로젝트에서 개발하는 AI학습모델은 포트폴리오 생성 모델이 아닌 **채용 공고와 커리어 기록의 적합도 판정 모델**이다. 본 서비스의 모든 생성은 사용자 기록과 채용 공고를 연결하는 일에서 시작하며, 본 프로젝트는 그 연결을 두 방향으로 학습하고 사용한다.

> `[그림 3.1 채용 공고 추천 모델과 커리어 기록 추천 모델의 구성]` — HTML 본문의 SVG를 참조한다.

그림 3.1에서 채용 공고 추천 모델(모델 A)은 사용자의 기록 전체를 보고 적합한 공고의 순위를 산출한다. 전체 공고는 Bi-Encoder+MLP로 빠르게 선별하고, 선별된 상위 후보만 Cross-Encoder로 다시 평가한다. 커리어 기록 추천 모델(모델 B)은 지원할 공고 하나를 보고 포트폴리오에 담을 기록을 고른다. 모델 B는 모델 A의 Cross-Encoder를 재사용하여 공고와 기록 1건의 쌍을 채점하고, 그 점수로 기록의 선택 조합을 정한다.

### 현행 판정 방식과 그 한계

| 모델 | 현행 구현 | 판정 방법 |
| --- | --- | --- |
| A | `jobs/match-score.ts` `calculateExplainableMatch()` | `source.includes(normalized(item))` |
| B | `materials/ranking.ts` `rankMaterials()` | 요건과 기록의 토큰 중첩 및 검증 상태로 정렬 |

두 함수 모두 표기가 다르면 관련성을 낮게 평가한다. 현재 규칙 기반 순위가 학습 모델의 baseline이다.

```ts
// services/backend/src/modules/materials/ranking.ts
const matched = requirementTokens.filter((token) => normalized.includes(token));
const score = matched.length * 10 + (record.status === "verified" ? 3 : 0);
return { ...record, score };
```

예를 들어 React 경험을 다른 표현으로 적으면 겹치는 토큰이 줄어 순위가 낮아진다. 사전학습 문장 인코더는 표기가 달라도 의미가 가까운 문장을 가까운 벡터로 변환하므로 이 한계를 해소한다. 요건별 `covered/partial/missing` 값은 별도의 규칙 함수가 산출한다.

### 두 단계로 나누는 근거

| 축 | Bi-Encoder+MLP | Cross-Encoder |
| --- | --- | --- |
| 입력 | 프로필과 공고를 각각 인코딩 | 공고와 관련 기록을 한 입력으로 함께 인코딩 |
| 사전 계산 | 공고 벡터는 수집 시, 프로필 벡터는 기록 변경 시 계산 | 요청 시 쌍마다 계산 |
| 학습 범위 | 인코더 동결 · 비교 모듈(MLP)만 학습 | 마지막 4개 층과 점수 예측 헤드 학습 |
| 쓰이는 단계 | 모델 A 스크리닝 — 전체 공고에서 상위 후보 선별 | 모델 A 리랭킹 · 모델 B 기록 채점 |

처리가 빠른 Bi-Encoder를 대규모 스크리닝에, 정확한 Cross-Encoder를 상위 후보에 적용하여 추천 정확도와 처리 비용의 균형을 맞춘다.

| --- | --- | --- | --- |
| **A** | 00 | Home · 추천 공고 | `T11.1.1` 추천 공고 제시 |
|  | 06 | 공고 탐색 · 목록 정렬 | `T2.3.1` 점수 계산 |
|  | 00b | 공고 AI 검색 결과 | `T2.3.3` 축별 충족 내역 |
| **외부 LLM 설계** | 01 | 공고 분석 · 요건별 충족 | `T3.2.2` 기록 커버리지 판정 |
| **B** | 01b | 재료 고르기 · 자동 선택 | `T4.1.1` 매칭 순 정렬과 자동 선택 |
|  | 01b | 재료 고르기 · 제외 사유 | `T4.1.3` 제외 사유 제시 |

## 3.1. 데이터 수집출처 및 수집방법

AI학습에는 채용 공고와 사용자 커리어 기록, 그리고 둘의 적합도 라벨이 필요하다. 공고와 요건의 수집 경로는 구현돼 있다. 공개 데이터에서는 다수 사용자의 상세 커리어 기록을 충분히 확보하기 어려우므로, 실제 자료의 근거를 결합한 **합성 프로필**을 구축한다. 아래 표는 원천별 수집 방법과 학습에서 맡는 역할을 정리한 것이다.

| 원천 | 수집 방법 | 학습에서 맡는 역할 | 상태 |
| --- | --- | --- | --- |
| 채용 공고 | `job_sources`에 등록된 소스를 주기 실행. 목록 조회 후 상세 파싱 | 후보 공고와 요건 원문 | 구현됨 |
| 공고 요구사항 | LLM이 공고 본문을 역량 항목 단위로 분해 | 공고의 필수 · 업무 · 우대 요건 | 구현됨 |

### 합성 프로필 구축

합성 프로필은 실제 자료 두 가지를 조건으로 생성한다. 청년패널조사의 집계 분포로 가상 사용자의 학력 · 직업 · 경력 골격을 정하고, 채용면접 인터뷰의 실제 경험 서술을 근거로 커리어 기록의 내용을 작성한다. 아래 그림 3.2는 그 과정이다.

> `[그림 3.2 실제 자료 기반 합성 프로필의 구축 과정]` — HTML 본문의 SVG를 참조한다.

생성 모델은 원천 자료의 사건 · 연차 · 수치를 바꾸지 않고, 상황 · 작업 과정 · 회고만 확장한다. 생성된 기록은 입력 조건을 지켰는지, 필수 정보가 있는지, 기록 구조를 따르는지 검사하고 통과한 것만 데이터세트에 넣는다.

### 라벨 생성 방법

현재 실사용자가 없어 행동 로그가 0건이며, 사람이 1만 쌍을 직접 라벨링하는 것도 불가능하다. 따라서 프론티어 LLM을 교사로 사용하여 적합도 라벨을 생성하고, 학생 모델이 그 판단을 재현하도록 학습한다. 이를 지식 증류(distillation) 구조라고 한다. 교사는 Codex의 GPT-5.6 Luna와 Claude Sonnet이다.

교사가 점수를 직접 매기게 하면 같은 판단에도 점수가 흔들린다. 그래서 교사는 **근거 해석과 판정**만 수행하고, **가중 점수 계산과 오류 검사**는 코드가 수행한다. 교사는 공고에서 핵심 요구사항을 1–8개 추리고, 요구사항마다 종류와 충족 수준을 판정한 뒤 근거가 되는 기록의 ID를 연결한다.

| 요구사항 종류 | 가중치 | 대상 |
| --- | --- | --- |
| 필수요건 | 45% | 명시된 필수 기술 · 경력 · 학력 · 자격 · 언어 |
| 담당업무 | 40% | 해당 직무에서 실제로 수행할 핵심 업무 |
| 우대요건 | 15% | 공고가 우대 사항임을 명시한 것 |

근무지 · 고용형태 · 원격 여부 · 급여 같은 근무 조건은 점수에서 제외한다.

| 충족 수준 | 점수 | 기준 |
| --- | --- | --- |
| 강한 직접 근거 | 100 | 구체적인 행동 · 범위 · 결과가 있는 직접 근거 |
| 직접 근거 | 75 | 해당 요구를 수행했다고 볼 수 있는 직접 근거 |
| 부분 충족 | 50 | 일부만 충족하거나 깊이 · 범위가 부족한 직접 근거 |
| 전이 가능한 인접 경험 | 25 | 인접 경험은 있으나 해당 요구의 직접 경험은 아님 |
| 근거 없음 | 0 | 현재 프로필에서 확인할 수 없음. 근거 기록을 연결하지 않는다 |

근거 없음을 제외한 판정은 근거 기록 ID를 하나 이상 연결하여야 한다.

축 점수는 그 종류에 속한 요구사항 점수의 평균이다. 최종 적합도 라벨(0–100)은 요구사항이 있는 축만으로 가중 평균하여 구한다. 해당 요구사항이 없는 축은 제외하고 나머지 축의 가중치를 다시 합이 1이 되도록 맞춘다. 계산 규칙은 루브릭 버전 `job-profile-fit-v1`로 고정하며, 코드는 교사가 낸 점수와 이 규칙으로 계산한 점수가 다르면 그 라벨을 오류로 처리한다.

## 3.2. 데이터 특징추출 및 특징분포

본 프로젝트의 특징은 사람이 설계한 수치 특징이 아니라 **사전학습 문장 인코더가 만든 벡터**이다. 채용 공고와 사용자 프로필은 문서 구조가 서로 다르므로 각각을 텍스트로 구성한 뒤 같은 인코더로 벡터화한다.

| 입력 | 텍스트 구성 | 인코더 입력 형식 | 출력 |
| --- | --- | --- | --- |
| 채용 공고 | 직무 · 주요 업무 · 필수 자격 · 우대 요건 | `passage:` 접두어, 최대 512토큰 | 공고 벡터 v · 768차원 |
| 사용자 프로필 | 경력 연차 · 기록 제목 · 기본 프로퍼티 · 본문 | `query:` 접두어, 최대 512토큰 | 프로필 벡터 u · 768차원 |

기준 인코더는 `multilingual-e5-base`이다. 두 입력은 가중치를 공유하는 같은 인코더를 지나며, 평균 풀링 후 L2 정규화한다.

인코더는 동결하여 사용하고 학습하지 않는다. 공고 벡터는 수집할 때 한 번 계산하고, 프로필 벡터는 기록이 바뀔 때만 다시 계산한다. 적합도 예측에 쓰는 비교 특징은 `[u, v, |u−v|, u⊙v]`를 이어 붙인 3,072차원이며, 이를 받는 MLP는 4.2에 기술한다.

### 인코더 비교

인코더는 사전에 하나로 정하지 않고, 같은 데이터와 같은 평가 조건에서 아래 네 모델의 적합도 예측 성능을 비교하여 선정한다.

| 모델 | 특성 | 비교하려는 점 |
| --- | --- | --- |
| `multilingual-e5-base` | 기준 모델 | 현재 인코더와 동일한 조건의 출발점 |
| `KURE-v1` | 한국어 특화 | 한국어 검색 데이터 추가 학습의 효과 |
| `BGE-M3` | 다국어 · 긴 문서 | 다국어 문맥과 긴 경력 기록의 표현력 |
| `Qwen3-Embedding-0.6B` | 지시문 지원 | 과업 지시문과 가변 벡터 차원의 효과 |

주요 지표는 NDCG@10이며, MAE · 공고쌍 순서 일치율과 임베딩 생성 시간 · 처리량 · GPU 메모리 · 임베딩 저장 용량을 함께 비교한다.

> `[그림 3.3 적합도 라벨의 분포와 라벨 구간별 코사인 유사도 분포]` — HTML 본문의 SVG를 참조한다.

그림 3.3에서 확인하여야 할 것은 두 가지이다. 첫째, 적합도 라벨이 한쪽 구간에 몰리지 않아야 한다. 둘째, 라벨이 높은 쌍일수록 프로필 벡터와 공고 벡터의 코사인 유사도가 높아야 한다. 유사도 분포가 라벨 구간과 무관하면 인코더 입력의 텍스트 구성을 다시 설계한다.

## 3.3. 데이터세트 정의 및 생성

AI학습용으로 최종 결정한 데이터세트는 `fit-v1` 한 벌이다. 합성 프로필마다 후보 공고 10개를 연결하고, 교사가 각 공고의 적합도를 평가한다. 두 학생 모델은 같은 데이터세트로 학습하며, 커리어 기록 추천 모델의 평가에는 같은 판정에 남은 요구사항별 근거 기록을 사용한다. 데이터세트는 **MongoDB에 적재한 뒤 학습 시점에 Parquet 파일로 내보내어** 사용한다.

| 항목 | `fit-v1` |
| --- | --- |
| 단위 | (사용자 프로필, 채용 공고) 쌍 |
| 구성 | 프로필 1,000개 × 공고 10개 = 10,000쌍 |
