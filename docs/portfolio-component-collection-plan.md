# 포트폴리오 컴포넌트·레퍼런스 수집 계획

공식 목록에서 발견할 수 있는 자료를 넓게 조사하고, 이용 가능한 코드와 구현 사양을 축적해 포트폴리오 컴포넌트 라이브러리를 보강합니다.

- 각 사이트의 전체 분류와 공개 목록을 먼저 조사한 뒤, 포트폴리오와 관련된 항목의 상세 자료를 수집합니다.
- 코드, 디자인 사례, 프롬프트, 모션 분석, 아이콘을 서로 연결해 보관합니다.
- 수집량은 사이트별 고정 건수로 제한하지 않습니다. 확인한 목록 범위, 고유 항목 수, 미처리·중복·접근 제한 항목으로 진행 상황을 판단합니다.
- 검증된 컴포넌트만 json-render의 실행 목록에 등록합니다. 참고 자료와 코드 후보는 계속 확장합니다.
- 기존 개발포털에 라이브러리 탭을 추가해 컴포넌트·프롬프트·관련 자료를 시각적으로 탐색합니다.

작성일: 2026-09-22 · 버전: v1.2 · 상태: 2단계 자료 확보 · [결과와 검토 범위](./portfolio-component-collection-stage-2.md)

선행 자료: [포트폴리오 컴포넌트 레퍼런스 조사](./portfolio-component-reference-research.md)

## 1. 목표와 수집 범위

### 1.1 확보할 자료

| 자료 | 수집 내용 | 활용 결과 |
| --- | --- | --- |
| 구현 코드 | 컴포넌트·블록·레이아웃·스타일·의존성·예제·라이선스 | 익스프레소에 이식할 코드 후보 |
| 시각적 레퍼런스 | 상세 페이지·원본 사이트·배치·타이포·이미지 비율·반응형 동작 | 새 컴포넌트와 variant의 디자인 사양 |
| 프롬프트 | 허용된 원문·출처·적용 대상·필요 데이터·재현 조건 | 컴포넌트 제작용 지시와 비교 기준 |
| 모션 자료 | 시작 조건·시작/종료 상태·전환 순서·취소·모바일·정적 대체 | 재사용 가능한 모션 사양 |
| 아이콘·도식 | SVG·JSX·다이어그램 예제·데이터 구조·스타일 변형 | 기술 설명과 시각 요소 |
| 페이지 구성 | 섹션 순서·강약·배경 전환·내비게이션·연락처 연결 | 완성 페이지 조합 예제 |

공개 자료의 목록화, 원본 파일 저장, 제품 내 이용, 소스 내보내기는 각각 허용 범위를 기록합니다. 참조용으로만 사용할 항목도 URL과 분석을 보존하면 설계 자산이 됩니다. 사이트가 카탈로그 복제나 메타데이터 재배포를 제한하면 허용된 범위의 링크·자체 분석을 기록하고 대량 복제는 별도 허용 대상으로 관리합니다.

1단계에서 공개 목록과 출처를 수집했습니다. 2단계에서 허용된 원본 소스·자산, 공식 참고 이미지, 자체 프롬프트를 확보하고 포털 상세에 연결했습니다. 실제 경력 콘텐츠의 품질 검증은 후속 단계입니다.

### 1.2 포트폴리오 역할 분류

사이트의 원래 분류를 보존하면서 아래 역할을 함께 붙입니다. 현재 인기 있는 카드·히어로에만 자료가 몰리지 않도록 역할별 누락을 확인합니다.

| 역할 | 필요한 표현 |
| --- | --- |
| 소개·프로필 | 타이포 중심, 인물 이미지, 대표 성과, 짧은 경력 요약 |
| 프로젝트 목록 | 목록, 썸네일 격자, 대표 사례와 보조 사례, 필터 |
| 프로젝트 상세 | 문제–행동–결과, 긴 사례, 과정, 전후 비교, 기여 범위 |
| 경력·학력 | 연대순, 조직별, 역할별, 프로젝트와 연결된 이력 |
| 연구·출판 | 논문, 실험 과정, 연구 질문, 결과 그림, 출처 |
| 성과·데이터 | 단일 수치, 전후 변화, 시계열, 비교표, 주석 있는 차트 |
| 기술·근거 | 기술별 관련 작업, 링크·문서·코드·근거 카드 |
| 아키텍처·과정 | 시스템 구조, 데이터 흐름, 시퀀스, 상태 전이, 타임라인 |
| 미디어 | 이미지 갤러리, 스크린샷 프레임, 영상, 문서 미리보기 |
| 내비게이션 | 상단 앵커, 고정 목차, 사이드바, 모바일 메뉴 |
| 연락·다음 행동 | 연락처, 이력서 다운로드, GitHub·논문 링크, 푸터 |
| 보조 화면 | 404, 빈 상태, 로딩·완료·실패, 수정 비교 |

위 역할과 함께 콘텐츠 길이, 항목 수, 이미지 유무, 디자인 방향, 정적 출력 가능 여부를 분류합니다. 장식 효과만 다른 항목은 구조가 다른 컴포넌트와 구분해 셉니다.

## 2. 단계별 실행 계획

### 0단계. 기준과 저장 구조 확정

1. 실행 ID와 조사 시점을 정하고 기존 수집 목록이 있는지 확인합니다.
2. 사이트별 공식 진입점, 분류 목록, 저장소, 이용 조건, 계정 필요 여부를 기록합니다.
3. 공개 포트폴리오의 호스팅, 사용자별 생성, 소스 내보내기, 내부 참고라는 이용 목적을 구분합니다.
4. 자료 형식과 상태 값을 통일하고 원본 자료·가공 사양·제품 코드를 나눠 저장합니다.
5. 실제 경력과 비슷한 길이를 가진 비식별 예제 콘텐츠를 준비합니다. 외부 서비스에 보내는 탐색 요청은 일반적인 컴포넌트 요구로 작성합니다.

**산출물:** 사이트별 수집 명세, 분류표, 저장 규칙, 예제 콘텐츠 목록, 포털 목록 데이터 계약.

**완료 조건:** 모든 사이트에 탐색 방법, 수집 가능 자료, 제약, 다음 행동이 기록됩니다. 권한 미확인 항목은 상태로 남기고 다른 사이트 조사는 진행합니다.

### 1단계. 전체 목록 탐색

1. 공식 저장소의 registry·파일 목록, 공개 API, 사이트맵, 사이트의 카테고리·목록 순서로 접근 방법을 선택합니다.
2. 제목, 공급자 식별자, 상세 URL, 원본 URL, 분류, 변형 식별자, 발견 위치를 기록합니다.
3. 페이지·커서·필터마다 처리 위치를 저장합니다. 무한 스크롤은 실제 UI가 제공하는 다음 항목을 확인합니다.
4. 한 항목이 여러 분류·사이트에 나타나도 발견 경로를 보존하고 대표 항목에 연결합니다.
5. 공식 총수가 있으면 집계 단위를 확인합니다. 컴포넌트, 변형, 템플릿, 아이콘 수를 섞지 않습니다.
6. 실패한 페이지와 접근 제한 항목도 목록에 남깁니다. 일부 응답을 전체 카탈로그로 보고하지 않습니다.

**산출물:** 정규화한 항목 목록, 사이트별 탐색 기록, 미처리 목록, 중복 관계, 포털용 공개 목록.

**완료 조건:** 수집 시점에 확인한 분류·페이지를 모두 처리하거나, 처리하지 못한 범위와 이유를 명시합니다. 전체 규모를 알 수 없는 사이트는 발견한 범위만 보고합니다.

### 2단계. 상세 자료 확보

1. 각 항목을 포트폴리오 역할에 연결하고 관련성의 근거를 적습니다.
2. 코드 제공 항목은 소스, 설치 정보, 의존성, props, 사용 예제, 라이선스와 해당 버전을 확보합니다.
3. 갤러리 항목은 상세 페이지와 원본 사이트를 대조하고 배치·정보 위계·반응형·상호작용을 기록합니다.
4. 프롬프트와 영상은 제공자가 허용한 방식으로 확보합니다. 원본 저장 권한이 불명확하면 링크, 시점, 자체 분석을 저장합니다.
5. 허용된 캡처에는 화면 크기와 상태를 기록합니다. 데모 이미지를 제품에 실을 자산과 구분합니다.
6. 라이선스·접근 조건이 확인되지 않은 자료는 후속 확인 목록으로 옮기고 확보한 공개 정보까지 보존합니다.

**산출물:** 항목별 자료 묶음과 출처 기록.

**완료 조건:** 상세 처리 대상마다 코드 확보, 참고 분석, 권한 대기, 접근 실패, 대상 제외 중 결과가 기록됩니다.

### 3단계. 중복 정리와 부족한 유형 보강

1. URL·원본 저장소 경로·공급자 ID·파일 해시로 동일 자료를 묶습니다.
2. 테마만 바뀐 항목은 같은 계열의 variant로 연결합니다. 구조와 읽기 흐름이 다르면 별도 후보로 유지합니다.
3. 역할 × 콘텐츠 형태 × 디자인 방향의 분포를 확인합니다.
4. 연구·경력·긴 사례·이미지 없는 포트폴리오처럼 부족한 조합을 찾아 다시 검색합니다.
5. Shoogle에서 발견한 새 registry는 출처 명세를 먼저 만든 뒤 다음 수집 대상으로 추가합니다. 탐색 범위 확장은 실행 기록에 남깁니다.

**산출물:** 고유 후보 목록, 변형 관계, 부족한 유형 목록, 추가 탐색 큐.

**완료 조건:** 아직 비어 있는 역할과 대응 계획을 설명할 수 있고, 중복을 실제 컴포넌트 증가로 계산하지 않습니다.

### 4단계. 구현 가능한 컴포넌트 후보 정리

1. 이식 가능한 코드는 원본과 익스프레소 수정본을 분리하고 출처·버전·고지를 연결합니다.
2. 참고 자료는 props, 슬롯, 콘텐츠 제한, 디자인 변형, 모바일 동작이 담긴 구현 사양으로 작성합니다.
3. 작은 UI 요소는 포트폴리오 섹션 안에 조합합니다. AI에 노출할 단위는 Hero, ProjectCaseStudy, CareerTimeline처럼 의미가 있는 단위로 정합니다.
4. 기존 화면의 레이아웃과 컴포넌트를 재사용하고, 앱 UI 토큰과 공개 포트폴리오 디자인 토큰의 적용 범위를 구분합니다.
5. 정적 HTML/SVG/CSS와 JavaScript·Canvas·WebGL이 필요한 동작을 구분합니다. 동적 항목은 정적 대체 상태를 함께 정의합니다.

**산출물:** 이식 작업 목록, 신규 구현 사양, 컴포넌트 카탈로그 초안.

**완료 조건:** 각 후보의 구현 방법, 이용 범위, 데이터 요구, 검증 방법을 알 수 있습니다. 이 단계 이후의 구현은 별도 개발 작업으로 진행합니다.

### 5단계. 실제 콘텐츠와 페이지 조합 검증

1. 고정 JSON과 비식별 예제 콘텐츠로 컴포넌트를 렌더합니다.
2. 긴 한국어 제목, 본문 증가, 긴 URL, 이미지 누락, 항목 수 변화, 작은 화면을 확인합니다.
3. 개별 컴포넌트와 완성 페이지를 함께 검토합니다. 서체·간격·배경·읽기 순서의 일관성을 확인합니다.
4. 정적 출력, 모션 감소, 키보드 접근, 이미지 확대·복귀를 확인합니다.
5. 결함을 컴포넌트 자체, 콘텐츠 부적합, 테마 부적합, 섹션 조합 문제로 분류합니다.

**산출물:** 화면 검증 자료, 결함 목록, 사용 가능한 콘텐츠 범위, 검증된 페이지 구성 예제.

**완료 조건:** 후보마다 사용 가능 범위와 남은 결함이 기록됩니다. 컴파일 성공만으로 디자인 품질을 통과 처리하지 않습니다.

### 6단계. json-render 연결과 점진적 확장

1. 검증된 props를 Catalog에 정의하고 실제 구현을 Registry에 연결합니다.
2. 레시피의 내용·수치·이미지·근거는 별도 상태로 공급합니다. AI는 컴포넌트·변형·순서·데이터 참조를 선택합니다.
3. 콘텐츠 요구와 디자인 조건으로 후보를 좁힌 뒤 모델에 전달합니다. 전체 라이브러리 설명을 매 요청마다 전달할 필요는 없습니다.
4. 고정 JSON 결과와 AI 구성 결과를 같은 입력으로 비교합니다.
5. 부분 수정의 범위, 이전 판과의 차이, 배포 결과를 검증합니다.
6. 새 레시피에서 드러난 부족한 유형을 1~3단계의 수집 큐로 되돌립니다.

**산출물:** 버전이 있는 내부 Catalog·Registry, 후보 선별 규칙, 생성·편집 평가 결과.

**완료 조건:** 선택 가능 항목의 이용 조건과 검증 상태가 명확하고, 사용자 내용과 근거를 유지한 채 생성·편집·출력됩니다.

## 3. 사이트별 수집 계획

각 사이트는 목록 탐색과 상세 수집을 나누어 진행합니다. 우선순위가 낮은 유형도 목록을 남기고 이후 처리 대상으로 보존합니다. 공급자의 허용 범위가 확인되는 대로 상세 수집 범위를 확장합니다.

### 3.1 Watermelon UI

**주요 결과:** 설치 가능한 코드, 블록 구성, 페이지 조합 예제.

1. [공식 llms.txt](https://ui.watermelon.sh/llms.txt)와 [OpenAPI](https://ui.watermelon.sh/openapi.json)를 기준으로 animated components·blocks·dashboards·templates·showcases의 분류를 확인합니다.
2. 현재 명세의 `/api/v1/catalog/summary`, `/api/v1/catalog/entries`, `/api/v1/catalog/entries/{kind}/{slug}`를 사용 후보로 기록합니다. 목록은 `limit` 최대 50이며 명세에 offset·cursor가 없어 저장소·사이트맵과 대조합니다. 이전 조사에서 API 직접 호출은 403이었으므로 접근 검증을 먼저 수행합니다.
3. [Registry 저장소](https://github.com/WatermelonCorp/watermellon-registry)의 항목 목록과 공식 사이트를 대조합니다. 허용된 저장소의 commit을 고정해 코드·예제·LICENSE를 확보합니다. 설치 단계에서는 확인한 registry 이름으로 shadcn CLI의 조회·차이 확인 절차를 사용합니다.
4. Hero, Feature, Gallery, Timeline, Stats, Contact, Footer, Navbar뿐 아니라 전체 페이지에서 이 요소가 함께 쓰인 Showcases를 연결합니다. 대시보드의 차트·표·기기 프레임도 재사용 후보로 조사합니다.
5. 컴포넌트마다 props, 파일 목록, 외부 이미지, Motion 등 의존성, Tailwind 버전, 정적 출력 가능 여부를 기록합니다.

**수집 범위:** 확인한 공개 목록과 MIT 적용 코드 전체를 목록화하고, 포트폴리오 역할에 연결 가능한 모든 고유 후보를 상세 처리합니다. API 상한에 걸린 결과는 부분 목록으로 표시합니다.

**검증:** 목록 종류별 개수와 저장소 항목을 대조하고, 사이트 전용 Showcase가 registry 설치 항목과 다르면 두 관계를 보존합니다.

### 3.2 OriginKit

**주요 결과:** 갤러리·텍스트·배경·모션 후보와 이용 조건별 도입 목록.

1. [공식 소개](https://www.originkit.dev/intro), Components·Sections·Templates 분류와 [라이선스](https://www.originkit.dev/docs/licensing)를 확인합니다.
2. Image Gallery, Text, Image, Animations, Interactive Elements, Background를 우선 탐색하고 Button·Loader·Cursor 등의 보조 유형을 이어서 조사합니다. 작품 확대, 사진 목록, 제목·성과 강조 등 포트폴리오 목적을 붙입니다.
3. 허용 범위에서 상세 페이지의 props, 변수 편집 항목, React·Framer 제공 형식, 의존성, 정적·모션 감소 동작을 기록합니다.
4. 일반 앱 사용, 사용자별 생성 결과 제공, 템플릿·소스 내보내기, 카탈로그 노출의 이용 범위를 구분합니다. 카탈로그 복제와 메타데이터 재사용 제한을 고려해 대량 확보 전 적용 범위를 확인합니다.
5. 확보가 허용된 항목은 버전·출처와 함께 저장합니다. 그 외 항목은 개별 참조 URL과 자체 동작 분석을 축적합니다.

**수집 범위:** 범주별 표현 유형을 넓게 조사합니다. 전체 코드·메타데이터 복제는 공급자 허용 범위가 확정된 뒤 진행합니다.

**검증:** 라이브러리 미러링, 익스프레소 내부 이용, 생성 결과 배포를 같은 권한으로 처리하지 않습니다. 접근 가능한 기능과 실제 내려받은 자료를 구분합니다.

### 3.3 Motion / motionin.design

**주요 결과:** 인터랙티브 섹션의 구현 사양과 허용된 프롬프트.

1. [공식 갤러리](https://www.motionin.design)의 Portfolio·Hero·Interactive·Product Showcase·Immersive와 Free·Paid 분류를 조사합니다.
2. 상세 URL과 제목, 콘텐츠 유형, 요구 이미지·영상 수, 동작 목적을 기록합니다. 비슷한 사진 효과도 배치·확대·복귀 방식이 다르면 별도 패턴으로 남깁니다.
3. Copy Prompt 기능으로 제공되는 자료는 이용 조건을 확인하고 허용 범위에서 확보합니다. 무료·유료·외부 서비스 전용 제공을 구분합니다.
4. 동작을 시작 조건, 이동 순서, 전환 도중 입력, 종료·취소, 모바일, 모션 감소, 정적 화면으로 분해합니다.
5. 재현 사양을 프로젝트 갤러리, 사례 확대, 작품 인덱스 등의 컴포넌트 요구로 옮깁니다. 구현 시 일반 포트폴리오의 스크롤과 충돌하는지도 검사합니다.

**수집 범위:** 공개 목록에서 발견한 관련 섹션을 전부 분류하고, 서로 다른 표현·상호작용을 빠짐없이 분석합니다. 유료 원문과 외부 서비스 결과의 저장 권한은 별도로 확인합니다.

**검증:** 프롬프트 확보를 실행 가능한 코드 확보로 계산하지 않습니다. 재현 성능은 후속 구현에서 측정합니다.

### 3.4 CodedVisuals

**주요 결과:** 기술 프로젝트를 설명할 시각 요소의 분류와 개별 이용 가능한 코드 후보.

1. [전체 분류](https://codedvisuals.com/visuals)에서 Browser·Devices·Charts·Metrics·Connections·AI·Git·Code·Images·Sections를 우선 조사하고 나머지 분류도 목록에 기록합니다.
2. 스크린샷 프레임, 전후 수치, 과정·연결 구조, 코드·터미널 표현의 데이터 요구를 분석합니다. 장식용 예시 수치와 실제 근거를 구분합니다.
3. [상용 라이선스](https://codedvisuals.com/license)의 AI 빌더 제한을 수집 명세에 기록합니다. 상용 전체 라이브러리의 생성기 편입은 별도 허용 확인 대상으로 둡니다.
4. [무료 저장소](https://github.com/pixelcave/codedvisuals-free)의 지정 파일은 [별도 LICENSE](https://github.com/pixelcave/codedvisuals-free/blob/main/LICENSE)를 기준으로 검토합니다. 대상 5개 파일과 데모 사이트 코드를 구분합니다.
5. 허용된 자료는 props·의존성·정적 상태·접근성 처리를 기록하고, 참고 전용 자료는 자체 구현할 일반 표현의 사양으로 정리합니다.

**수집 범위:** 공개 분류와 설명에서 필요한 표현을 넓게 확보합니다. 코드 원본은 무료 지정 파일 또는 별도 허용을 받은 범위로 관리합니다.

**검증:** 장식용 `aria-hidden` 시각 요소를 실제 성과의 유일한 전달 수단으로 사용하지 않습니다. 도표의 실제 데이터와 접근 가능한 설명을 따로 설계합니다.

### 3.5 diagram-design

**주요 결과:** 기술·연구 포트폴리오용 SVG 구조와 다이어그램 사양.

1. [공식 저장소](https://github.com/cathrynlavery/diagram-design)의 commit과 [MIT LICENSE](https://github.com/cathrynlavery/diagram-design/blob/main/LICENSE)를 고정합니다.
2. 유형별 문서·예제·레이아웃 문법·테마·출력 도구·검증 지침을 파일 목록으로 정리합니다. 스킬은 이 단계에서 실행하지 않고 자료로 읽습니다.
3. Architecture, Data Flow, Sequence, State Machine, Timeline, Process, Before/After에 해당하는 표현을 포트폴리오 역할에 연결하고 나머지 유형도 검색 가능한 상태로 남깁니다.
4. 노드·연결·라벨·강조·그룹과 배치 결정을 구분해 props 사양을 만듭니다. 고정 샘플 문구와 실제 데이터 자리를 구분합니다.
5. 한국어 라벨, 노드 증가, 긴 관계 설명, 좁은 화면과 인쇄 상태를 검증할 예제를 준비합니다.

**수집 범위:** 라이선스가 적용되는 예제·규칙·도구를 전체 목록화하고 구조가 다른 모든 다이어그램 계열을 확보합니다. 테마 변형은 같은 구조에 연결합니다.

**검증:** 관계 데이터와 SVG의 의미가 일치하는지 확인하고, React 컴포넌트 전환 작업량을 기록합니다.

**검증:** 무료 열람, 코드 접근, 상업 사용, 결과물 내보내기의 상태를 각각 기록합니다.

### 3.7 Shoogle

**수집 범위:** 관련 검색 결과와 발견한 공급자의 허용된 목록을 단계적으로 확장합니다. 검색 점수나 첫 페이지 결과를 전체 자료의 품질 순위로 해석하지 않습니다.

**검증:** 설치 주소와 소유자를 확인한 뒤 shadcn CLI의 `view`·차이 확인 절차로 상세 파일을 검토합니다. 설치와 원본 코드 수집은 별도의 실행 단계입니다.

**수집 범위:** 공개 히어로 목록을 가능한 범위에서 전부 확인하고, 제품·브랜드 사례도 일반화할 수 있는 구조가 있으면 후보로 보존합니다.

**검증:** 특정 사진·로고·영문 문구에 의존하는 효과와 재사용 가능한 구조를 나누어 기록합니다.

| 1 | 전체 사이트 명세 + Watermelon·diagram-design·Rune Icons | 접근·이용 조건이 비교적 명확한 코드·도식·아이콘 기반을 확보합니다. | 재현 가능한 소스 목록과 원본 판 |
| 2 | Shoogle + Supahero·Unsection·Bento Grids | 구현 후보를 넓히고 히어로·프로젝트·성과 표현을 확장합니다. | 새 공급자 목록과 구조별 사양 |

OriginKit·CodedVisuals·Kobra의 이용 범위 검토는 0단계부터 시작합니다. 답변이나 접근 권한을 기다리는 항목 때문에 공개 자료 수집 전체를 멈추지 않습니다. 이 표는 작업 순서이며 서브에이전트나 병렬 실행을 지정하지 않습니다.

### 4.2 재개 가능한 작업 묶음

작업은 `사이트 → 분류 → 목록 구간 → 상세 항목` 단위로 나눕니다. 묶음 크기는 각 공급자의 제한과 응답 시간에 맞춰 조정하며, 전체 수집량의 상한으로 쓰지 않습니다.

각 묶음에 다음을 남깁니다.

- 시작·종료 시각, 목록 URL, 필터, 실제 제공된 페이지·커서·offset.
- 새로 발견한 항목, 기존 항목, 상세 처리 결과와 오류.
- 다음 시작 위치, 남은 목록, 접근·이용 조건 확인 항목.
- 수행한 도구와 버전, 저장한 파일의 해시, 원본 버전.

429 응답은 서버의 Retry-After·RateLimit 안내에 맞춰 처리합니다. 반복되는 403·인증 요구는 접근 제한으로 기록하고 공식 저장소·다운로드 등 허용된 경로를 확인합니다. 존재가 확인되지 않은 API·페이지 인자는 추측해 사용하지 않습니다.

## 5. 자료 구조와 중복 관리

아래 경로는 전체 단계의 저장 구조입니다. 1단계는 `artifacts/portfolio-library/cache/`에 로컬 응답을, `docs/library/`에 공개 목록과 실행 기록을 저장합니다.

```text
artifacts/portfolio-library/<run-id>/
  source-manifests/       # 사이트별 접근·이용 조건·탐색 기록
  inventory/             # 발견한 항목과 원본 URL
  source-materials/      # 저장이 허용된 원본 코드·문서
  observations/          # 자체 분석, 허용된 캡처와 상태 기록
  normalized/            # 통일된 메타데이터와 중복 관계
  specifications/        # 새 컴포넌트·variant·모션 사양
  evaluation/            # 콘텐츠별 렌더링 결과와 결함
  reports/               # 수집 범위·부족 유형·후속 작업
```

대용량 자료와 이용 범위가 제한된 원본은 Git 추적 범위를 별도로 정합니다. 저장소에는 계획·출처 명세·자체 사양·도입이 허용된 코드와 고지를 중심으로 남깁니다. API 키·세션·토큰은 수집 산출물에서 제외합니다.

### 5.1 항목 메타데이터

| 구분 | 필드 | 기록 목적 |
| --- | --- | --- |
| 식별 | `id`, `sourceSite`, `sourceItemId`, `canonicalUrl` | 동일 항목을 반복 수집하지 않습니다. |
| 출처 | `discoveredFrom`, `originalUrl`, `sourceRevision`, `fetchedAt` | 발견 경로와 원본 판을 추적합니다. |
| 자료 | `artifactKind`, `paths`, `contentHash` | 코드·프롬프트·분석·아이콘을 구분합니다. |
| 권한 | `licenseUrl`, `licenseVersion`, `allowedUses`, `rightsStatus` | 저장·제품 사용·생성·소스 배포 범위를 구분합니다. |
| 의미 | `roles`, `contentKinds`, `styleTraits` | 포트폴리오 목적과 디자인 특성으로 검색합니다. |
| 기술 | `framework`, `dependencies`, `runtime`, `staticFallback` | 실제 실행·배포 조건을 파악합니다. |
| 데이터 | `propsSchema`, `contentLimits`, `mediaRequirements` | 레시피에 맞는 후보를 선택합니다. |
| 관계 | `familyId`, `variantOf`, `duplicateOf`, `pageCompositionId` | 변형·중복·페이지 구성을 보존합니다. |
| 상태 | `collectionStatus`, `reviewStatus`, `integrationStatus` | 수집과 품질·제품 적용의 진행을 구분합니다. |
| 검증 | `observationMethod`, `viewports`, `testCases`, `defects` | 직접 확인한 상태와 추정을 구분합니다. |

원본 문자열과 정규화한 값을 함께 보존합니다. URL의 추적 파라미터를 제거할 때 실제 버전·변형·콘텐츠를 가리키는 파라미터는 유지합니다. 파일 해시가 같아도 공급자와 라이선스 관계를 버리지 않습니다.

### 5.2 상태 체계

- 수집: `discovered → metadata_ready → material_ready` 또는 `access_blocked / failed / out_of_scope`.
- 이용 조건: `unreviewed / allowed / reference_only / permission_needed / restricted`.
- 검토: `unreviewed / needs_adaptation / validated / rejected`.
- 제품 연결: `not_started / specified / implemented / registered`.

참고용 분석이 완료된 항목은 `material_ready + reference_only`일 수 있습니다. 코드 사용이 제한돼도 조사 자료의 가치는 남습니다. `registered`에는 제품 이용 범위와 기술 검증이 확인된 컴포넌트만 들어갑니다.

## 6. 수집량과 완료 판단

### 6.1 집계

| 지표 | 정의 |
| --- | --- |
| 발견 수 | 수집 시점에 발견한 공급자별 항목 수 |
| 고유 항목 수 | 동일 공급자 ID·원본 경로·중복 관계를 정리한 수 |
| 구조 계열 수 | 테마·색상 변형을 묶은 레이아웃·동작 계열 수 |
| 목록 처리율 | 확인한 목록 구간 중 처리한 구간의 비율 |
| 상세 처리율 | 상세 처리 대상으로 정한 고유 항목 중 결과가 기록된 비율 |
| 코드 확보 수 | 실제 파일·버전·라이선스가 연결된 항목 수 |
| 참고 사양 수 | 직접 작성한 배치·모션·컴포넌트 사양 수 |
| 역할 대응 범위 | 역할 × 콘텐츠 형태 × 디자인 방향 중 자료가 확보된 조합 |
| 접근·권한 대기 | 미처리 범위와 해결에 필요한 조건 |
| 제품 등록 수 | json-render에서 실제로 사용 가능한 검증된 항목 수 |

첫 전체 목록 조사 후 실제 기준 수를 확정합니다. 홈페이지의 홍보 수치와 서로 다른 단위의 자료 수는 완료율의 분모로 사용하지 않습니다. 전체 규모를 확인하지 못한 사이트는 목록 처리율과 발견 수를 보고합니다.

### 6.2 단계 종료 기준

- 확인한 공개 분류·목록 구간을 처리했거나 미처리 사유와 다음 행동을 기록했습니다.
- 상세 대상의 결과는 확보·참고·중복·범위 제외·접근 실패·권한 대기로 설명됩니다.
- 포트폴리오 역할의 누락을 확인하고 추가 탐색 또는 자체 구현 대상을 정했습니다.
- 다음 실행에서 마지막 성공 지점부터 재개할 수 있습니다.
- 수집 성과와 제품 등록 성과를 따로 보고합니다.

한 차례의 종료는 해당 시점과 허용 범위에 대한 종료입니다. 새 분류·새 항목·권한 해소가 있으면 다음 실행에서 확장합니다. 재수집은 내용 해시·버전·갱신 시각을 비교해 변경된 항목부터 처리합니다.

## 7. 품질 검증과 라이브러리 전환

기존 v2 파이프라인은 결과물의 디자인 품질 때문에 보류됐습니다. 새 수집 작업의 평가는 실제 경력 내용과 완성 페이지에서 수행합니다.

| 평가 영역 | 확인할 내용 |
| --- | --- |
| 콘텐츠 | 문장·수치·근거·이미지가 보존되고 과장된 샘플 데이터가 제거되는지 확인합니다. |
| 조판 | 긴 한국어, 다양한 항목 수, 이미지 누락에서도 읽기 순서와 위계가 유지되는지 확인합니다. |
| 디자인 | 선택한 방향의 타이포·면·여백과 프로젝트 표현이 유지되는지 확인합니다. |
| 페이지 조합 | 서로 다른 출처의 섹션 사이에 폭·배경·간격·강조가 어긋나지 않는지 확인합니다. |
| 상호작용 | 키보드·터치·취소·복귀·모션 감소에서 의미와 동작이 유지되는지 확인합니다. |
| 출력 | 미리보기와 공개 페이지, 정적 상태와 인쇄 결과를 확인합니다. |
| 수정 | 특정 문장·순서·변형 변경이 다른 내용과 근거에 영향을 주지 않는지 확인합니다. |

JSON의 구조 유효성과 표시된 내용의 사실성은 각각 검사합니다. 시각 평가에는 실제 브라우저 결과와 결함 설명을 남깁니다. 스타일만 다른 컴포넌트를 많이 확보한 경우에도, 이미지 없는 연구 사례나 긴 경력 설명을 처리할 수 없다면 해당 유형의 보강을 계속합니다.

## 8. 개발포털 라이브러리 탭

수집한 자료와 구축한 컴포넌트를 기존 개발포털의 **라이브러리** 탭에서 시각적으로 탐색합니다. 이 탭은 수집 초반부터 연결해 확보 현황과 품질을 확인하는 화면으로 사용합니다.

### 8.1 기존 포털 연결

현재 포털의 원본은 [Expresso 개발 포털.dc.html](./Expresso%20개발%20포털.dc.html)입니다. 상단 탭은 `NAV`와 `navLinks`, 공유 주소는 `routeOf`·`parseRoute`·`applyRoute`에서 처리합니다. `services/dev-portal`에는 제작 자료와 설명이 있고, 실제 화면은 `docs/`에서 제공합니다.

- 기존 상단 탭에 `라이브러리`를 추가하고 헤더·검색·색상·서체·간격을 재사용합니다.
- 탭 안에 자료 유형, 필터, 카드 목록, 상세 패널을 연결합니다.
- 기존 탭 이동, 브라우저 뒤로 가기, 새로고침, 공유 링크의 동작을 유지합니다.
- 포털의 내부 화면으로 연결하고, 목록과 선택 상태가 기존 포털 내비게이션에 반영되도록 구현합니다.

주소의 제안 형태는 `#/library`, `#/library/components`, `#/library/prompts`, `#/library/components/<id>`입니다. 검색·필터도 공유 가능한 형태로 직렬화하고, 현재 라우트 파서를 확장해 해석합니다. 기존에 없는 주소 형식이므로 구현 시 정합성을 검증합니다.

### 8.2 자료 유형과 화면

| 유형 | 카드 미리보기 | 상세 정보와 동작 |
| --- | --- | --- |
| 컴포넌트 | 실제 렌더링 썸네일, 이름, 역할, variant 수 | 큰 미리보기, 예제 데이터, props, 코드 위치, 정적·동적 상태, 출처, 검증 결과 |
| 프롬프트 | 목적, 입력 변수, 출력 유형, 연결된 결과 미리보기 | 허용된 프롬프트 원문 또는 자체 작성본, 변수 설명, 버전, 평가 결과, 복사 |
| 디자인 참고 | 허용된 이미지 또는 원본 링크 카드, 디자인 특성 | 원본 사이트, 배치·타이포 분석, 연결한 컴포넌트와 구현 사양 |
| 모션 | 정지 썸네일과 재생 표시 | 시작 조건, 재생·정지·다시 보기, 정적 상태, 모션 감소, 연결 컴포넌트 |
| 아이콘·다이어그램 | SVG와 테마별 변형 | 크기·스타일·실제 예제, 데이터 구조, 이용 조건 |
| 페이지 구성 | 완성 페이지 축소판 | 사용 컴포넌트·레시피 예제·테마, 데스크톱·모바일 비교 |

처음에는 `전체`에서 자료 유형을 함께 보고, 유형 선택으로 목록을 좁힙니다. 자료가 늘어나면 그리드와 밀도 높은 목록 보기를 전환합니다.

**공통 필터:** 자료 유형, 원본 사이트, 포트폴리오 역할, 디자인 방향, 콘텐츠 종류, 이미지 필요 여부, 프레임워크, 정적 출력 가능 여부, 수집 상태, 이용 상태, 검증 상태.

**정렬:** 최근 확보, 최근 검증, 이름, 역할. 페이지 이동과 지연 로딩을 적용해 전체 자료의 미리보기를 한 번에 실행하지 않습니다. 모션 카드는 사용자가 재생한 항목만 활성화합니다.

**카드에 표시할 상태:** 수집됨, 참고 전용, 코드 확보, 이식 필요, 검증 완료, 제품 등록, 이용 범위 확인 필요. 색상과 함께 텍스트를 표시합니다. 코드가 존재한다는 사실과 품질 검증 완료를 구분합니다.

### 8.3 상세 패널과 자료 연결

상세 패널은 선택한 자료의 사용 가능성을 판단할 수 있게 구성합니다.

1. **미리보기:** 현재 variant, 화면 크기, 테마, 예제 콘텐츠, 정적·동적 상태를 선택합니다.
2. **사용 정보:** 컴포넌트 역할, 적합한 콘텐츠, 길이·항목 수·이미지 제약을 표시합니다.
3. **구현 자료:** 이용이 허용된 코드·props·설치 정보·프롬프트를 제공합니다. 복사는 허용된 자료에만 제공합니다.
4. **연결 자료:** 해당 컴포넌트의 제작 프롬프트, 참고 사례, 모션 사양, 포함된 페이지 구성을 연결합니다.
5. **출처와 버전:** 공급자, 원본 URL·commit, 수집일, 라이선스, 변경 내역을 표시합니다.
6. **검증:** 어떤 콘텐츠와 화면 크기로 확인했는지, 발견한 결함과 사용 가능 범위를 보여줍니다.

원본 참고 이미지, 자체 구현 결과, AI가 생성한 결과는 미리보기의 출처를 표시합니다. 미리보기가 없는 항목은 `미리보기 준비 중`으로 표시하고 해당 자료의 상태와 원본 링크를 제공합니다. 실제 검증을 수행하지 않은 화면에 검증 완료 표시를 붙이지 않습니다.

### 8.4 프롬프트 라이브러리

프롬프트도 검색·비교·버전 관리가 가능한 독립 자료로 저장합니다.

| 필드 | 내용 |
| --- | --- |
| 목적 | 컴포넌트 제작, variant 추가, 모션 구현, 콘텐츠 적합성 검사, 품질 검토 |
| 입력 | 필요한 디자인·콘텐츠·이미지·상태 변수와 입력 스키마 |
| 본문 | 허용된 원문 또는 익스프레소 자체 작성본 |
| 출력 | 기대하는 코드·JSON·SVG·검토 결과의 형식 |
| 버전 | 프롬프트 판, 변경 이유, 공급자 원본과 자체 수정본의 관계 |
| 실행 근거 | 실행했을 때의 모델·설정·입력 예제·일시·결과 ID |
| 연결 | 참고 자료 ID, 만들어진 컴포넌트·variant·미리보기 ID |
| 이용 상태 | 원문 표시·복사·수정·공개 가능 여부 |

각 프롬프트 카드에는 목적과 연결된 결과를 함께 보여줍니다. 아직 실행하지 않은 프롬프트는 `실행 전`으로 표시합니다. 초기 포털은 탐색·비교·복사를 지원하고, 모델 실행은 이후 별도 기능으로 정의합니다.

### 8.5 데이터 공급과 공개 범위

수집 목록을 정규화한 데이터에서 포털용 목록을 생성합니다. 포털 목록을 손으로 다시 작성하면 수집 결과와 어긋나므로 같은 항목 ID와 버전을 사용합니다.

```text
사이트별 수집 결과
        ↓
정규화한 항목·중복·이용 조건·검증 기록
        ↓
공개 가능 필드와 자료 선택
        ↓
포털용 catalog + 항목 상세 + 미리보기 산출물
        ↓
기존 개발포털의 라이브러리 탭
```

초기 구현은 정적 포털 구조에 맞춰 다음 산출물을 제안합니다.

- `docs/library/catalog.json`: 공개 가능한 요약 목록, 분류, 버전, 상세 파일 경로.
- `docs/library/items/<id>.json`: 공개 가능한 상세·출처·검증·관련 자료.
- `docs/library/previews/`: 자체 생성하거나 공개 배포가 허용된 미리보기.
- 포털에서 사용하는 라이브러리 표시 모듈: 기존 포털 셸 안에 로드하며 데이터와 표시 코드를 분리합니다.

1단계에서는 `catalog.json`에 목록과 메타데이터 상세를 함께 저장하고 기존 포털 안에서 페이지별 카드를 표시합니다. 원문·미리보기가 확보되면 `items/`·`previews/` 분리를 진행합니다. 실제 컴포넌트 미리보기에는 빌드·검증한 산출물을 사용하고 격리된 영역에서 실행합니다. 수집 원본 소스와 프롬프트는 텍스트로 취급합니다.

현재 [포털 설명](../services/dev-portal/README.md)과 [배포 워크플로](../.github/workflows/dev-portal-oracle.yml)에 따르면 `docs/`는 공개 배포 대상입니다. 제한된 원본·유료 프롬프트·비공개 예제는 공개용 산출물에 넣지 않습니다. 전체 내부 자료를 포털에서 제공하려면 인증된 API·저장소를 별도로 연결해야 하며, 화면에서 숨기는 방식만으로 접근을 제한하지 않습니다.

공유 목록의 원본은 버전이 있는 수집 데이터입니다. localStorage는 보기 설정처럼 개인 선호를 저장하는 데만 사용합니다. 팀이 공유하는 검토 상태를 수정하는 기능이 필요해지면 인증과 저장 API를 추가합니다.

### 8.6 수집 단계와 함께 개발할 순서

| 시점 | 포털 작업 | 확인할 결과 |
| --- | --- | --- |
| 0~1단계 | 라이브러리 탭, 데이터 계약, 빈 상태, 자료 유형·필터·공유 주소 | 기존 탭에서 진입하고 빈 목록을 사실대로 표시합니다. |
| 첫 목록 확보 | 정규화 결과를 포털용 catalog로 생성 | 수집 데이터와 카드 목록의 항목 ID·개수가 일치합니다. |
| 상세 자료 확보 | 출처·이용 조건·프롬프트·관련 자료 상세 연결 | 카드에서 원본과 관련 자료까지 이동합니다. |
| 컴포넌트 검증 | 실제 썸네일·variant·화면 크기·정적/모션 미리보기 | 수집 후보와 검증 완료 항목의 차이를 시각적으로 확인합니다. |
| 자료 확대 | 검색·필터 성능, 지연 로딩, 중복 관계, 페이지 구성 비교 | 전체 목록 증가 후에도 탐색과 미리보기가 안정적으로 동작합니다. |

### 8.7 포털 완료 기준

- 기존 포털의 라이브러리 탭으로 진입하고 다른 탭으로 돌아옵니다.
- 컴포넌트·프롬프트·참고·모션·아이콘·페이지 구성 목록을 탐색합니다.
- 검색·필터·선택 상태가 뒤로 가기와 새로고침, 공유 주소에서 유지됩니다.
- 실제 목록, 수집 요약, 자료 상태가 같은 데이터를 가리킵니다.
- 미리보기와 코드·프롬프트의 판이 일치하고 연결된 자료를 확인합니다.
- 빈 목록·검색 결과 없음·로딩·실패·미리보기 없음 상태를 처리합니다.
- 키보드 탐색, 작은 화면, 다량 항목의 지연 로딩과 모션 정지를 확인합니다.
- 공개 산출물의 모든 필드와 자산이 공개 허용 범위에 들어갑니다.
- 수집을 다시 수행하면 catalog와 미리보기를 갱신하는 경로가 재현됩니다.

## 10. 근거와 확인 범위

사이트별 성격과 이용 조건은 [선행 조사](./portfolio-component-reference-research.md)의 공식 출처를 기준으로 했습니다. 실행 전 약관과 제공 범위를 다시 확인합니다. 본문에 제안한 필드·단계·완료 기준은 익스프레소의 수집 운영안입니다.

이번 계획에서 추가 확인한 자료:

- [Watermelon OpenAPI](https://ui.watermelon.sh/openapi.json): v1 경로, 목록 최대 50개, 명세의 목록 인자와 rate-limit 헤더.
- [Shoogle CLI 안내](https://shoogle.dev/mcp/cli): registry 검색 경로와 제공 옵션.
- [shadcn registry.json](https://ui.shadcn.com/docs/registry/registry-json): registry 항목 목록 구조.
- [json-render Specs](https://json-render.dev/docs/specs), [Registry](https://json-render.dev/docs/registry): 수집한 구현과 실행 명세의 연결.

1단계에서 Watermelon 사이트맵과 고정 registry 목록을 수집했습니다. 목록 API와의 대조는 후속 확인 대상으로 남겼습니다. 사이트별 실제 처리 범위와 오류는 실행 결과 문서에 기록했습니다.
